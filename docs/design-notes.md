# ソフトウェア設計メモ

[VGM_multi_MCU_design.md](../VGM_multi_MCU_design.md) の方針をどう実装に落としたか、
および既知の制約をまとめたもの。回路/配線は [circuit.md](circuit.md) 参照。

## 1. リポジトリ構成

ファームウェアのソースは `src/` にまとめてあります(third_party/・tools/ はルート直下のまま)。

```
src/
  protocol/          master<->slave共通の通信プロトコル定義 (ヘッダのみ)
  slave_common/      SPIスレーブ受信 + サンプル駆動オーディオエンジン + PWM出力 (全スレーブ共通)
  slave_sn76489/     SN76489 (自作エミュレータ)
  slave_ay8910/      AY-3-8910 (自作エミュレータ)
  slave_ym2612/      YM2612 (third_party/ymfm を使用)
  slave_ym2413/      YM2413 (third_party/ymfm を使用)
  slave_ym2151/      YM2151/OPM (third_party/ymfm を使用)
  slave_ym2203/      YM2203/OPN (FM3ch+SSG3ch, third_party/ymfm を使用)
  slave_scc/         K051649/SCC (自作エミュレータ、MSXカートリッジ用5ch波形メモリ音源)
  slave_segapcm/     Sega PCM (自作エミュレータ、16ch 8bit PCM。サンプルROMは実行時アップロード)
  master/            SDカード読込 + VGMパース + スレーブへのSPI配信
                     (player_config.c = SDの vgmplay.ini(無ければ vgmplay*.ini)でチップ
                      有効/無効・CSピンを上書き、
                      ssd1306.c/oled_ui.c = 任意のSSD1306ステータス表示をcore1で描画)
third_party/         ymfm (FM音源コア, BSD-3), no-OS-FatFS-SD-SPI-RPi-Pico (FatFs+SDドライバ,
                     Apache-2.0/FatFsライセンス), miniz_tinfl (gzip展開, MIT)
tools/               ホスト検証プログラム (host_tests/)、設定GUI (config_gui/)、
                     SPI疎通テスト (spi_bringup_test/)、ymfmキャリブレーション (probes/)
```

## 2. 通信プロトコル

`src/protocol/vgm_spi_protocol.h` 参照。1フレーム=3バイト固定 (`opcode, reg, data`)、CS毎にSPIバスを
共有 (マスター側はソフトウェアCS、スレーブ側はハードウェアSPIスレーブモード)。MISOは配線しない
片方向バスなので、配線数を絞れる代わりにスレーブからマスターへの状態通知はできません
(ヘルスチェック等が必要になったら要拡張)。

**バスは SPI モード1 (CPOL=0, CPHA=1)、フレームは CS 保持のバースト送信**:
`src/master/src/slave_bus.c` の `slave_bus_init()` と `src/slave_common/src/slave_spi_rx.c` は
どちらも `spi_set_format(..., SPI_CPOL_0, SPI_CPHA_1, ...)` を使います。`send_frame()` は
`gap_us == 0`(既定 / YM2151)で **3バイトを 1回の CS アサートのまま連送**(約6µs/フレーム
@4MHz)、`gap_us > 0` で従来の 1バイトごと CS パルス+ギャップ(約370µs/フレーム @gap_us=120)。

**経緯**: 当初は SPI モード0 (CPHA=0) で、CS を low に保ったまま 3バイト連送すると
**1バイト目しかスレーブに届かず 2・3バイト目が無警告で欠落**しました(マスター送信自体は
`VGM_MASTER_VERBOSE_LOG` で正しいと確認済み。`tools/spi_bringup_test/` で切り分け)。
モード0の PL022 スレーブは各バイトの先頭ビットを CS アサート時にサンプルするため、
バイト間に CS エッジが必須だったためです。対処として 1バイトごとに CS をパルスしていましたが、
これだと FM 密度の高い曲(OutRun の YM2151、1サンプル=22µs の wait 内に約30回のレジスタ書き込み)
を送りきれず、マスターが数秒遅れて走り気味になり音程・テンポが崩れました(`gap_us` を上げると悪化)。
2026-09-02 に **SPI モード1 (CPHA=1) なら CS 保持の連続バーストを取りこぼさない**ことを
実機(Pico2 の YM2151 リンク)で確認し、バス全体をモード1へ移行、YM2151 は既定でバースト
(`gap_us=0`)にしました。1フレーム約6µs なので 30書き込みバーストでも約180µs で収まります。
マスターとスレーブは必ず同じモードにする必要があります(モード不一致=全バイト化け)。
配線が弱い個体があれば `vgmplay.ini` の `gap` を非ゼロにして 1バイトパルス方式に戻せます。

パルス間隔(20µs)は実機での実測に基づく値です: 最初は安全側に50µsで固定しましたが、和音や
アルペジオのようにVGMの`wait`コマンドの間に何個もレジスタ書き込みが連続する場面で、1フレーム
あたり最低150µs(3パルス×50µs)のオーバーヘッドが`wait_samples()`の実時間ペーシングを乱し、
体感できるレベルの「テンポの乱れ」として現れました。5µsまで詰めるとバイト欠落が再発(ノイズと
して聴こえる)したため、20µsが実機で確認できた安定値です。別のRP2040個体・配線では再度調整が
必要になる可能性があります(問題の再現有無は`VGM_SLAVE_VERBOSE_LOG`で確認できます)。

- `VGMSPI_OP_RESET` の `reg` はクロックプリセット番号 (各スレーブがコンパイル時に持つ数個の
  実クロック値のうちどれに近いか)。masterがVGMヘッダのクロック値から一番近いプリセットを選んで送る
  (`src/master/src/vgm_chips.c: vgm_pick_clock_preset`)。全チップ(SCCを除く)がこれを使ってプリセットを
  選択する(SCCは実機がMSXの単一クロックでしか使われないため1択のみ)。

  **注意 (2026-08-27修正)**: 以前はYM2612/YM2413/YM2151/YM2203/Sega PCMについて「ymfmはクロックを
  取らないのでプリセットはno-op」としていましたが、これは不正確でした。ymfmのFMエンジンは
  レジスタ値→位相増分の変換自体はクロック非依存ですが、**その結果を正しい実時間Hzで聴くには
  「実クロックに対応するネイティブサンプルレートちょうどでレンダリングする」ことが必須**です
  (`chip.sample_rate(clock)`が実際に意味するのはこれ)。以前は全チップともプリセット0(デフォルト
  クロック)決め打ちでレンダリングしていたため、VGMファイルの実クロックがデフォルトと異なる場合
  (例: YM2151の3579545Hz vs 4000000Hzは多くのアーケード基板で両方一般的、差は約192セント=ほぼ
  2半音)、音程・テンポ全体が均一にズレるバグがありました。エラーやクラッシュを伴わないため
  実機テストで気づきにくく、YM2151/YM2413で実際に踏んだ実機テストで発覚しました。
  現在は`src/master/src/vgm_player.c`がVGMヘッダから各チップの実クロックを読み(YM2413=0x10, YM2612=0x2C,
  YM2151=0x30, Sega PCM=0x38, YM2203=0x44, AY-3-8910=0x74)、対応するプリセットを選択して送信します。
  **注意 (2026-09-04修正)**: これらのフィールドは、VGMデータ開始オフセット(ヘッダ0x34から算出)が
  `フィールド末尾(offset+4)`以上のときだけ有効です。VGM仕様では「データ開始が0x40のファイルは
  ヘッダが0x3Fまでしか無い」= 0x40以降のクロック欄は実体がコマンド列。v1.50のメガドライブ系リップ
  (SN76489+YM2612、データ開始0x40)は先頭のYM2612レジスタ書き込み(`52 28 00 52 …`)がちょうど
  0x44(YM2203欄)に来るため、`hdr_clock()`の`data_start`ガードが無いと**YM2203を誤検出**します
  (OLEDに"YM2203"、かつ`vgmplay.ini`で`[ym2203] enabled = no`なら曲ごと誤スキップ)。
  `調査用/04 - Water.vgm`で実際に発生。`vgm_player.c`の`hdr_clock()`参照。
  スレーブ側は`chip_ops_t.sample_rate_hz(clock_preset)`(`src/slave_common/include/slave_engine.h`)を
  `RESET`のたびに問い合わせ、レンダリングループのペーシング(`src/slave_common/src/slave_engine.c`)を
  動的に再計算します。SN76489/AY-3-8910/SCCは元々自前のtick-budget方式で固定44.1kHz出力に
  リサンプリングしているため、この問題自体がなく`sample_rate_hz`は常に同じ値を返すだけです。
  - **`VGMSPI_OP_CLOCK` を毎秒再送する**。`RESET` は曲頭で1回だけ送る一発フレームなので、
    その瞬間にスレーブがまだ SPI を聞いていない(起動が遅い／セッション中に再フラッシュ)と
    電源投入時の既定プリセット(ymfm 系は 0 = 別サンプルレート)のまま**曲全体が一様に
    ピッチずれ**します(YM2151 は 55930 vs 62500Hz で約 −1.9 半音)。他症状なし・`gap_us`
    非依存・オフラインレンダには出ない。対策として `VGMSPI_OP_CLOCK`(チップをリセットせず
    レートだけ再設定)を追加し、`src/master/src/vgm_player.c: reassert_clocks()` が曲の
    1秒ごとに YM2413/2612/2151/2203/SegaPCM へ再送。遅れて起動したスレーブは次の1秒で
    自動的に正しいレートへ矯正されます。`slave_bus_reset` も3回送出(`sleep_us(300)` 間隔、
    保険)。2026-09-03、OutRun `03 Splash Wave.vgm` の「音程がズレる」がこれでした
    (音色歪みの調査 §5 とは別件)。同時に、250MHz では YM2151 が 62500Hz の描画に間に合わない
    ことも判明し、YM2151 スレーブを 320MHz/1.15V(YM2203 と同じ)へ引き上げました。
- `VGMSPI_OP_WRITE0`/`WRITE1` がチップのport0/port1相当。SN76489は生バイトをそのまま流し込み、
  チップ側で本物同様のラッチ/データバイト処理をする。
- SCCのみ `VGMSPI_OP_SCC_WAVEFORM`/`FREQ`/`VOLUME`/`KEYON` という専用オペコードを4つ追加している。
  実チップは「サブアドレスをラッチしてから書き込む」2サイクルの1ポート方式だが、masterが
  VGMコマンド`0xD2 pp aa dd`の`pp`(領域選択)を見てどのオペコードか事前に判定して1フレームで送る
  ことで、ラッチの2サイクル分を1回のSPI転送にまとめている(機能的には実ハードウェアと等価)。
  フレームサイズ(3バイト固定)を変えずに済むための設計。詳細は`src/protocol/vgm_spi_protocol.h`と
  `src/master/src/vgm_player.c`の`0xD2`処理、`src/slave_scc/src/chip_scc.c`を参照。
- Sega PCMのみ性質の異なる `VGMSPI_OP_PCM_UPLOAD_RESET`/`VGMSPI_OP_PCM_UPLOAD_BYTE` を持つ。
  他のオペコードが「制御レートのレジスタ書き込み」なのに対し、これは「曲の頭に1回だけ起きる
  数万バイト規模のバルク転送」で、既存の3バイトフレームを1バイト単位で使い回している(新しい
  可変長バスモードは作らず、スレーブ側にオートインクリメントする書き込みカーソルを持たせることで
  対応)。1バイトごとにCSをパルスする方式(上記)のため1フレームあたり約65µs(3パルス×約20µsの
  間隔が支配的)かかり、192KBの上限いっぱいまで使うと曲の頭に12〜13秒程度のロード待ちが生じ得ます。
  レジスタ書き込み自体は通常の`VGMSPI_OP_WRITE0`を使う(意味のあるレジスタ空間が0x00-0xFFに
  収まるため、追加オペコードは不要だった)。詳細は`src/slave_segapcm/src/chip_segapcm.c`参照。
  なお `VGMSPI_OP_SEGAPCM_ROM_BASE` を曲頭に1回送り、スレーブがサンプルアドレスからその値を引いて
  固定バッファに収める「ROMウィンドウのリベース」を行っています(512KB級ROM曲対策、§5参照)。

## 3. コア分担 (各スレーブ)

- core0: `slave_spi_rx_run()` -- SPIスレーブ受信をブロッキングで回し、受信フレームを
  `multicore_fifo` でcore1へ転送するだけ
- core1: `slave_audio_engine_run()` -- 44.1kHz (チップによっては別レート、下記) でサンプル生成 + PWM出力。
  各サンプルの直前にFIFOに溜まっているレジスタ書き込みを全部適用してからレンダリングする

YM2612/YM2413/YM2151/YM2203は ymfm が生成するネイティブなサンプルレート
(それぞれ約53267Hz / 49715Hz / 55930Hz / 166400Hz、`chip.sample_rate(clock)` で実測・固定値化:
`tools/probes/ym2612_probe.cpp` 等参照) でそのまま駆動しており、44.1kHzへのリサンプリングは
していません(スレーブごとにサンプルレートが違っても、各スレーブは独立に自分のPWM出力を鳴らす
だけなので問題なし。アナログ段でミキシングする設計だからこそ成立する単純化)。SN76489/AY-3-8910/SCC
は素直に44.1kHzで駆動しています(SCCの音程は実機と同じ f = clock / (32 * (period+1)) で、位相アキュムレータ
のステップ幅をレジスタ書き込み時に再計算する設計にしたので、任意のサンプルレートで駆動できます。
`src/slave_scc/src/chip_scc.c`の`recompute_step`参照)。Sega PCMはさらにシンプルで、実チップの
ネイティブレート(クロック/128。プリセット0の4,000,000Hzで31250Hz、プリセット2の8,000,000Hzで
62500Hz)をそのままエンジンのサンプルレートとして使っており、レート変換の計算が一切不要です。

## 4. VGMコマンド対応状況

| コマンド | 対応 |
|---|---|
| 0x50 (SN76489) | ○ 転送 |
| 0x51 (YM2413) | ○ 転送 |
| 0x52/0x53 (YM2612 port0/1) | ○ 転送 |
| 0x54 (YM2151) | ○ 転送 |
| 0x55 (YM2203) | ○ 転送 (FM/SSGとも同一レジスタ空間、ymfmが内部で振り分け) |
| 0xA0 (AY-3-8910) | ○ 転送 (register上位ビットの2chip目セレクトは無視、1chip固定) |
| 0xD2 (K051649/SCC) | ○ 転送 (領域を事前デコードして専用オペコードで送信。SCC+/052539の
  非共有波形モードは未対応、常に旧SCC互換のch3/ch4波形共有として扱う) |
| 0xC0 (Sega PCM register write) | ○ 転送 (16bitオフセットの下位バイトのみ使用。レジスタ空間が
  0x00-0xFFに収まるため上位バイトは無視。ROMバンクはCTRLレジスタ経由で扱う(下記0x67の行/§5参照)) |
| 0x67 type=0x80 (Sega PCM ROMデータブロック) | ○ 先頭8バイトのヘッダ(全ROMサイズ+ROM内開始
  アドレス)を解釈し、`VGMSPI_OP_PCM_UPLOAD_RESET`で開始アドレスの256バイト境界へシーク→
  端数(`start & 0xFF`)を0x80(無音)で詰めてバイト単位に合わせてから
  実データを1バイトずつアップロード(`VGMSPI_OP_PCM_UPLOAD_BYTE`)。複数ブロックにも対応。曲頭で
  ヘッダ0x3Cのバンク設定を`VGMSPI_OP_SEGAPCM_BANK`で転送。全ブロックを事前スキャンして最小開始
  アドレス(64KB切り下げ)を`VGMSPI_OP_SEGAPCM_ROM_BASE`で通知し、スレーブはこれを引いて~192KB
  バッファに収める(§5「ROMウィンドウのリベース」)。リベース後もなお192KB超のスパンは無音 |
| 0x61/0x62/0x63/0x70-0x7F (wait) | ○ |
| 0x66 (end) + ループポイント | ○ (loop_enabled時、ループ区間を`opts.max_loops`回再生してから終了し次曲へ。`main.c`は2回。0=無制限。スキップボタンでいつでも次曲へ) |
| 0x67 (その他のtypeのdata block) | バイト数だけ正しく読み飛ばし、実際の再生はしない |
| 0x80-0x8F (YM2612 DAC+wait) | waitのみ処理、DAC書き込みは無視 |
| 0x90-0x95 (PCMストリーム制御) | 正しい長さで読み飛ばすのみ |
| その他 (YM2608/YMF262等、上記以外の未対応チップ) | libvgmのコマンド長テーブル
  (`player/vgmplayer_cmdhandler.cpp`)を参照して正確な長さで読み飛ばし。0x30-0xDFの主要な
  範囲は実装元と突き合わせ済みで、0xE2-0xFF等ごく一部の予約領域のみ「4バイト」という
  VGM1.71仕様の一般的なパターンに基づく推定。万一長さを誤ってもクラッシュはせず、最悪その曲の
  残りが無音/破綻するだけ |

対応チップは SN76489 / YM2612 / YM2413 / AY-3-8910 / YM2151 / YM2203 / K051649(SCC) / Sega PCM の
8種類で、8/16bit世代の定番機種はおおむね上記コマンド体系に収まります。Sega PCMのROMアップロードに
ついては次章および[circuit.md §4](circuit.md#4-sega-pcmスレーブについて-romアップロード)参照。

## 5. 既知の簡略化・精度に関する注記

- **クロック精度**: 各チップはコンパイル時に2〜3種類の実クロック値しか持たず、VGMヘッダの実際の値には
  完全追従しません(最も近いプリセットを選ぶだけ)。SN76489/AY-3-8910/YM2612/YM2413はNTSC/PAL程度の差
  (〜1%)なので誤差として許容する設計方針([design doc §5](../VGM_multi_MCU_design.md#5-クロック同期に関する方針)
  と同じ考え方)。YM2151(3579545Hz vs 4000000Hz)/YM2203(3993600Hz vs 4000000Hz)/Sega PCM
  (4000000 / 3579545 / 8000000Hz。8MHzはX-Board・System 18世代で描画は62500Hzになる。
  プリセット違いで最大2倍のピッチ/テンポずれ)はもっと差の大きいプリセットを用意しています(YM2151の2値は
  約192セント=ほぼ2半音相当の差があるので、この2値のどちらかで実際に近似できていれば誤差は
  最大でも1値との差の半分程度に収まりますが、3値目以降が必要な実機が相手だと近似の限界を超えます)。
  §2で述べた通り、以前はこのプリセット選択自体がYM2612/YM2413/YM2151/YM2203/Sega PCMで機能して
  いなかった(常にプリセット0固定)バグがあり、2026-08-27に修正済みです。
- **AY-3-8910エンベロープ**: 16種類の波形のうち、繰り返し系 (Continue=1) は実機とほぼ一致しますが、
  Continue=0やHold絡みの一部の組み合わせは簡略化した近似です (`src/slave_ay8910/src/chip_ay8910.c` の
  `envelope_tick`/`env_level` 参照)。
- **音量テーブル**: SN76489/AY-3-8910とも「2dB/step」を模した近似テーブルで、実チップの正確なdBカーブ
  ではありません。
- **AY出力レベルのスルー(2026-09-02追加)**: `04 Hot Summer Riding.vgm`(MSX、AY+SCC)で「0:09から
  AYがワンテンポ遅れる」という指摘を、`tools/offline_render/`で当機演奏をWAV化し原曲録音と
  数値A/B比較して調査。テンポ・タイミングは原曲と完全一致(ドリフト<0.01%)で、実体はAY
  エミュレータがエンベロープ段(R13再トリガや音量レジスタ書き込み)ごとに1サンプルで瞬時に
  レベルを飛ばす=実機より当たりが硬く、繁忙部でオンセット密度が約1.5倍多いことだった。対策として
  AYのチャンネル出力レベルにワンポールのスルー(平滑)を入れ、`chip_ay8910.c`の
  `AY8910_LEVEL_SLEW_HZ`(CMake `VGM_AY8910_LEVEL_SLEW_HZ`、既定**10Hz**)で制御。実機試聴で
  AYの遅れ感は解消・副作用なしを確認済み。SCCは元々ずれておらず、スルーを入れると音色が
  原曲から離れたため`SCC_VOLUME_SLEW_HZ`(`VGM_SCC_VOLUME_SLEW_HZ`)は既定0(=従来どおり瞬時)。
  どちらも0でスルー前と完全にバイト一致。
- **FM音源勢のCPU負荷**: [design doc §3](../VGM_multi_MCU_design.md#3-スレーブrp2040-zeroの役割)
  で指摘の通りFM音源は負荷が高め。参考までにホスト上での相対比較
  (`tools/probes/ym2151_ym2203_probe.cpp`、絶対値はRP2040とは無関係だがチップ間の相対比較として
  有用): 1秒の音声を生成するのに要したホストCPU時間はYM2612が最も重く、YM2151・YM2203(MIN
  fidelity)はそれよりむしろ軽い、という結果でした。ただしYM2203はネイティブサンプルレートが
  166kHz超とYM2612(53kHz)よりずっと高く、call-per-second自体は最も多いため、FM音源勢の中で最も
  リスクが高いと見ています(SN76489/AY-3-8910/SCC/Sega PCMはいずれも単純なカウンタ/波形テーブル
  読み出しで、計算負荷は軽いはずです)。

  **実機確認済み(2026-08-27)**: YM2151スレーブをRP2040標準133MHzで実機テストしたところ、
  `src/slave_common/src/slave_engine.c`に追加した`RATE CHECK`計測ログ(`VGM_SLAVE_VERBOSE_LOG`時のみ、
  約1秒ごとに実測サンプルレートを出力)により、**実時間に対して2.32倍遅れる**(全ティックで
  処理落ち)ことを確認しました。音程・テンポが均一に低く聞こえる形で現れ、エラーや音飛びは
  一切伴わないため、気づきにくい種類の不具合です。ビルドは`-O3`最適化済みであることを確認済みで、
  ymfmのOPM(YM2151)にはYM2203の`OPN_FIDELITY_MIN`に相当する軽量化オプションが存在しない
  (実機のOPMがプリスケール固定だったため)ことも確認済みです。つまりこれはソフトウェア側の
  バグではなく、RP2040標準クロックでの純粋な処理能力不足です。

  対策は2つ:
  1. `set_sys_clock_khz()`でのオーバークロック(200MHz超も多くの個体で動作実績あり) -- ただし
     今回不足していた2.32倍を埋めるには理屈上300MHz超が必要で、これだけでは不十分な可能性が
     高いです
  2. **Pico 2(RP2350)へのスレーブ基板の置き換え**: 標準クロックが高く(150MHz)、コア
     (Cortex-M33)もRP2040のCortex-M0+よりIPCが高いため、より有望です。`firmware/pico2/`に
     YM2151/YM2203/YM2612(このセクションでリスクが高いとしている3チップ)のRP2350向けビルドを
     用意しています。ソースコードの変更は不要で、`cmake -DPICO_BOARD=pico2`で再ビルドするだけ
     でした(ピン配置・フォームファクタもPico 1と互換なので配線変更も不要)。詳細は
     `firmware/pico2/README.md`参照。RP2040向けのビルド・設定はそのまま残しているので、
     オーバークロックの選択肢も引き続き検討できます。

  **実機確認済み(2026-09-05)**: 音割れ解消、音量バランスも問題なしとの報告を受領。

  **YM2413の曲が時々まったく再生されない不具合(2026-09-05、調査中)**: `main.c`の無効チップ
  自動スキップ機能(上記VGMSPI関連ではなく、`vgm_player_scan_chips()`が返すチップマスクに基づく)
  が、実際には使っていないチップを誤検出して曲ごとスキップしている可能性が濃厚。原因は
  YM2203の件(データ開始位置より後ろを読む)とは逆方向で、**VGM変換ツールがヘッダを新しい
  バージョン相当の長さまで確保しつつ、使わない拡張フィールド(AY-3-8910クロック@0x74、
  SCCクロック@0x9C 等)をゼロ埋めせずゴミ値のまま残す**既知の事例がある。`data_start`による
  ガードは「宣言されたヘッダ長の中」なので通り抜けてしまう。対策として`hdr_clock()`に
  実在するチップのクロックとしてあり得ない値(1kHz未満 or 100MHz超)を弾くレンジチェックを
  追加。この時点では理論的な修正で、実機ログでの確定(`skipping <曲名> -- needs
  disabled/absent chip(s): <チップ名>`の有無)待ち。

  **↑は的外れだった、本当の原因が判明(2026-09-05)**: 「同じVGMファイルでも、複数曲を
  ループ再生していると鳴ったり鳴らなかったりする」という追加報告で上記仮説は否定された
  ——ヘッダの中身は毎回同じバイト列なので、ヘッダ解析由来なら常に同じ結果になるはず。
  実際の原因は`src/slave_common/src/slave_engine.c`の **MUTE状態が次のRESET受信でしか
  解除されない**という設計上の穴だった:

  - 曲の終わりに master は全チップへ`VGMSPI_OP_MUTE`を送り、スレーブは`muted=true`にして
    PWM出力を強制的に0にする(即座に音を止めるため)。
  - 次の曲の頭で master は`VGMSPI_OP_RESET`を(冗長化のため)3連続で送り、これを受信して
    初めて`muted=false`に戻る。
  - この3連発が**SPIのタイミング起因で稀に全て取りこぼされる**と、`muted`を戻す手段が
    どこにも無い。以降のVGMSPI_OP_WRITE0はスレーブへ正しく届き`ops->write()`もチップの
    状態も正常に更新され続けるが、`audio_pwm_write(pin, muted ? 0 : sample)`により
    **PWM出力だけが曲の最後までゼロに固定される**。「レジスタは鳴らしているのに無音」
    という、ファイルの中身に依存しない現象になる。
  - 唯一の周期的な保険である`VGMSPI_OP_CLOCK`(FM系5チップへ毎秒再送)はクロック再設定のみで
    `muted`に触れない。SN76489/AY-3-8910/SCCの3チップは周期メッセージ自体が無いので
    なおさら自己修復手段が無かった。YM2413固有の不具合ではなく、8チップ全部に共通する
    アーキテクチャ上の穴で、たまたまYM2413で顕在化しやすかった(あるいは最初に報告された)
    だけの可能性が高い。

  **修正**: NOPとMUTE以外の全オペコード受信時に`muted=false`を戻すよう変更(RESETの成否に
  依存しない)。実際に音を鳴らす系のコマンドを受け取っている時点でそのチップは能動的に
  駆動されている、という判断。曲間の2秒の無音区間はmasterが何も送らないため`muted`は
  正しく維持され、次の曲の最初の書き込みが届いた時点で解除される。全8スレーブ共通の
  `slave_engine.c`を直したので再ビルド・再フラッシュが必要(`firmware/pico1/`・
  `firmware/pico2/`とも更新済み)。実機での確定はまだ。

  **実機確認済み(2026-08-28、YM2151)**: Pico 2標準クロック(150MHz)では1.257倍不足、
  200MHzオーバークロックでも実測ではまだ僅かに不足(かつ`VGM_SLAVE_VERBOSE_LOG`自体のprintf
  オーバーヘッドが計測値を悪化させる影響も判明)。250MHzオーバークロックで実際にピッチ・
  テンポとも正常になることをユーザーが確認しました。またこの過程で、200MHz時にYM2151の
  CSライン(GPIO20)で新規基板特有のSPIバイト欠落(80µsでもまだ発生)が見つかり、120µsまで
  拡大して解消しています(`src/master/src/slave_bus.c`の`s_routes`テーブル)。**新しいスレーブ
  基板を追加するたびに、CS間隔(`gap_us`)はその基板固有の配線マージンとして個別にチューニング
  が必要になる**、というのがこのプロジェクトを通じて繰り返し確認された教訓です。

  **オペコード衝突による音色歪み(2026-08-31、YM2151、OutRun `03 Splash Wave.vgm`)**:
  キーオンの多い曲で YM2151 の音色が歪む症状。verbose ログに `[YM2151] SCC_KEYON data=..` が
  混入していたことで判明。YM2151 のキーオンレジスタは 0x08 で、`{WRITE0, reg=0x08, data}` の
  **オペコードバイト(0x02)が欠落**すると、`slave_spi_rx.c` の再同期が次の `reg` バイト(0x08)を
  有効オペコード(`VGMSPI_OP_SCC_KEYON`=0x08)と誤認 → `SCC_KEYON` として誤ディスパッチされます。
  さらに `ym2151_write()` が `port` 引数を無視していたため、誤ディスパッチされたフレームも
  そのまま生の(ゴミ)レジスタ書き込みとして適用され、FMパッチが壊れて歪みになっていました。
  対策は3段構え:
  (1) 4つのymfm系ラッパー(`chip_ym{2151,2203,2413,2612}.cpp`)で `port` が正規値
  (YM2612は0/1、他は0のみ)でなければ書き込みを捨てる = 誤ディスパッチされたフレームを適用しない。
  (2) **`slave_spi_rx.c` の再同期をチップごとの有効オペコードマスクに変更**
  (`VGMSPI_MASK_<CHIP>`、`vgm_spi_protocol.h`)。YM2151 は 0x08 を受け取らないので、
  オペコードバイト欠落で `reg`=0x08 がオペコード位置に来ても**無効として弾き**、`SCC_KEYON`
  として3バイト消費して整列を崩すことがなくなる(stray 1バイトだけ捨てて次を探す)。
  以前の `< VGMSPI_OP__COUNT` より大幅に厳しい。
  (3) `gap_us` の拡大は **逆効果だったので 120 に戻した**: OutRun 系は 1サンプル(22µs)の wait の
  中に FM レジスタ書き込みが 20〜30 個続く箇所が多数あり、`send_frame` は 1バイトごとに CS を
  パルス+`gap_us` 待ちなので 1フレーム ≈ 3×(gap_us+2µs)。gap_us=120 でも 30書き込みバースト =
  約11ms を 22µs 枠に流し込めず、マスターが曲全体で秒単位に遅れて**追いつこうと早送り**し、
  音符がずれて聞こえる(gap_us=160/200 で悪化した)。
  切り分け: shipped の `chip_ym2151.cpp` ラッパーで Splash Wave をホストレンダリング → **完全に
  クリーン**(サンプル跳び 0、レベル正常、連続)。ymfm-OPM と振り分けは正しい。基板入れ替えで
  スレーブ側配線も除外済み → **残る原因はマスターの SPI 送出／3バイト+CSパルス方式が FM 密曲に
  対して遅すぎること**。
  **根治は「フレームを ~100倍速くする」**: (a) 3バイトを CS 保持のまま連送、(b) 4バイト化+
  同期マーカ、(c) gap_us を下げる、の3案。**2026-09-02〜03 に (a) を実施し解決**:
  - まず (c) を実機で `gap = 2` まで試したが「少し良くなるが歪みは残る」。
  - `VGM_SPI_BAUD_HZ` を 8MHz に上げる案は、Pico2 スレーブが `slave_overclock.h` で
    `clk_peri` を 48MHz 固定にしており PL022 スレーブは `clk_peri ≥ SPIclk×12` が要るため
    48/12 = **4MHz が YM2151 スレーブの上限**で不可。
  - `tools/spi_bringup_test` で、**SPI モード0 の CS 保持バーストは 1バイト目しか届かない**
    ことを Pico2 の YM2151 リンクで再確認(`調査用/spi_bring_up_test1.log`)。次に
    `-DBRINGUP_MODE1` を足して **SPI モード1 (CPHA=1) のバーストは 3バイトとも届く**ことを
    実機確認。
  - 本番反映(2行): `slave_spi_rx.c` / `slave_bus.c` の `spi_set_format` を `SPI_CPHA_1` に。
    YM2151 の `s_routes` 既定 `gap_us` を `0`(バースト)に。master + 全8スレーブを再ビルド・
    再フラッシュ(モード不一致=全化けなのでフラグデー)。1フレーム約6µs。
  RATE CHECK 上は 250MHz で描画は足りている(`62500 samples in ~1010000us`、`fell_behind`≈0。
  verbose時の18〜20%はprintf storm)。
  さらにYM2151の音量がSN76489/AY-3-8910/SCCと比べて小さく聞こえる問題も報告されました。
  当初 `>>7` → `>>6` を「音量」目的で試し、A/Bで音量差が分からず `>>7` に戻していましたが、
  **2026-08-31再考: これは音量ではなく分解能の問題**。OutRun `03 Splash Wave.vgm` の YM2151
  出力はホストレンダリングでピーク 294/2048(実効約6bit)しかなく、10bit PWM に対して量子化歪み
  ＋ ほぼ無音デューティでの搬送波漏れが「音色の歪み」として乗ります(持続系のFM音で顕著。
  YM2203 は出力がずっと大きいので出ない)。切り分け: 蓄積でない(1曲目でも歪む)、SPI化けでない
  (YM2203基板にYM2151ファームを載せCS=21にしても同じ=配線は正常)、SegaPCM無効化でも変化なし、
  デジタルはクランプ0。→ `ym2151_render` を **`>>6`(2倍)** に変更(1chフルで約1020、クランプ
  余裕あり)。効かなければ `>>5` かディザ。

  **実機確認済み(2026-08-29、YM2203)**: `調査用/02 Theme.vgm`(スペースハリアー、YM2203 +
  Sega PCM)で、**Pico 2 + 250MHzでもYM2203が下ずる**ことを確認(ユーザーがVGMPlayとA/Bして
  YM2203側の音程が低いと確認。Sega PCM側は正しい)。ホスト実測(`ym2151_ym2203_probe.cpp`)では
  YM2203の1サンプルあたりコストはYM2151より軽い(86ns vs 160ns)が、レートが166400Hz(YM2151は
  55930Hz)なので**総演算量はYM2151の約1.6倍**。YM2151が250MHzでようやく間に合う以上、YM2203は
  250MHzでは足りない計算になります。ymfmの`ym2203`は`OPN_FIDELITY_MIN`=`clock/24`が下限で、
  これ以上レートは下げられません(下げると`generate()`の呼び出しレート=チップ内部時間の進みが
  変わり音程がずれる)。CMake変数`VGM_RP2350_SYSCLK_KHZ`(既定250000)/`VGM_RP2350_VREG_MV`
  (既定0=SDK標準1.10V)でオーバークロック値とコア電圧を変えられます(実装は
  `src/slave_common/include/slave_overclock.h`、RP2040ではno-op)。

  **実測(2026-08-29、Pico 2、YM2203、`調査用/02 Theme.vgm`)**:
  - 250MHz: 明確に下ずる
  - 300MHz + verbose: `RATE CHECK: 166400 samples in 1025402us, fell_behind=21/166400` =
    2.5%遅い(≈43セント)。だが`fell_behind`=21なので描画自体はほぼ間に合っており、2.5%の大半は
    `VGM_SLAVE_VERBOSE_LOG`のprintfオーバーヘッド。preset=1(166666Hz)で走行していることも確認。
    当初のホスト見積り「400MHz必要」は外れ(M33のキャッシュ/分岐予測の効きを過小評価)。
  - 非verbose 300MHz: 「かなり近い。気持ちだけまだ低め」(ユーザー試聴)
  - **320/360MHz(電圧1.10Vのまま): 音が出ない** → 300MHz超は`VGM_RP2350_VREG_MV=1150`〜`1250`で
    コア電圧を上げる必要あり
  - **320MHz/1.15V: それでも無音。ただしcore1は生きていて`RATE CHECK`は出続ける**(かつ
    `@166400Hz`=起動時レートのまま=RESETを受信できていない)。原因は**`set_sys_clock_khz()`後は
    `clk_peri`が`clk_sys`に追従する**ため、オーバークロック時にPL022 SPI(とUART)まで300MHz超で
    駆動され、SPIスレーブがフレームをデコードできなくなること。`slave_overclock.h`で
    オーバークロック後に`clk_peri`をPLL_USB由来の48MHz固定に張り直すよう修正(2026-08-30)。
    これで250MHzの既存ビルドも含めペリフェラルは常にin-specで動く。
  - **320MHz/1.15V +clk_peri修正: 正常動作をユーザー確認(2026-08-31)**。軽量OPNコアの自作は不要。
    この設定を YM2203 の既定として確定(`VGM_YM2203_SYSCLK_KHZ`=320000 /
    `VGM_YM2203_VREG_MV`=1150、`src/slave_ym2203/CMakeLists.txt`)。他の重量スレーブ
    (YM2151/YM2612/SegaPCM)は `VGM_RP2350_SYSCLK_KHZ`=250000 / `VGM_RP2350_VREG_MV`=0 のまま
    (YM2151は250MHzで実機確認済み、他は同等以下)。`clk_peri`の48MHz固定は全RP2350ビルド共通。
    まだ僅かに低ければ `firmware/pico2/debug/slave_ym2203_350MHz_1v20.uf2`(要1.20V)。
    安定する最小電圧を使うこと(電圧を上げると発熱増)。
  - **YM2612**: 1サンプルあたりのコストはFM勢で最も重い(design-notes冒頭の相対比較)が、
    レートが約53kHz(YM2203の1/3)なので総演算量はYM2151と同程度で、250MHzで足りるはず(未実測)。
    疑わしいときは `firmware/pico2/debug/slave_ym2612_{250,300}MHz_VERBOSE.uf2` で RATE CHECK を比較。
- **SCC+/052539の波形共有**: `src/slave_scc/src/chip_scc.c`は旧SCC(K051649)のch3/ch4波形共有仕様のみ
  実装しています。052539(SCC+)の非共有モードを使うVGMファイルでは、ch3とch4が異なる波形のはずの
  場面で同じ波形が鳴ります。
- **Sega PCMのロード時間とROM容量上限**: サンプルROMを1バイトずつ、1バイトごとにCSをパルスする
  方式でアップロードするため(上記§2参照、1フレーム約65µs)、曲の頭に数秒〜最大12〜13秒程度の
  無音のロード待ちが発生します(design doc の想定していた「即座に反映」の前提からは外れる、この
  機能特有の例外)。アップロード先バッファは約192KBに固定(RP2040のRAM上限)です。
  **ROMウィンドウのリベース (2026-08-30)**: 512KB級ROM(OutRun等)の曲は、サンプルが
  ROMアドレス空間の上の方(例:`調査用/01 Magical Sound Shower.vgm`は全12ブロックが
  0x40000〜0x56000)に置かれていて、そのままだと全ブロックが192KB境界を超えて捨てられ**完全に
  無音**になっていました。対策として、masterは再生前に曲の全`0x67` type-0x80ブロックを事前スキャン
  して最小開始アドレスを求め、64KB(Sega PCMバンクの最小粒度)に切り下げた値を
  `VGMSPI_OP_SEGAPCM_ROM_BASE`でスレーブへ通知します。スレーブは以降すべてのサンプルアドレスから
  このベースを引いて`s_rom[]`を読み書きするので、**曲が実際に参照する範囲が192KB未満なら、それが
  512KB空間のどこにあっても鳴る**ようになります(Magical Sound Showerの使用スパンは約88KB)。
  ベース0(=非Sega-PCM曲や低位ROM曲)ではリベースなし=従来と同一動作。リベース後もなお192KBを
  超えてスパンする曲は超過分が欠けます(その場合はPico 2ビルドの`SEGAPCM_ROM_BUDGET`拡大が次の手)。
  バンク切り替えの仕組み自体(0x3Cのbankshift/bankmaskデコード)は従来通り。
- **Sega PCMの出力音量**: 実曲は音量レジスタに小さめの値を使う(例:`調査用/02 Theme.vgm`は最大
  48/127、同時発音数も少ない)ため、当初の`>>6`ではFM勢より20〜50倍小さくなっていました。
  `src/slave_segapcm/src/chip_segapcm.c`の最終シフトを`>>4`に変更(02 Themeで実測ピーク約2148・
  RMS約323、クリップは全体の0.0008%で他チップと同じ「稀なピークだけクランプ」水準)。フル音量の
  曲が耳につくほど歪む場合は`>>5`へ。
- **Sega PCM 8MHzクロック**: `調査用/02 Theme.vgm`のようにヘッダ0x38が8,000,000Hz
  (X-Board・System 18世代)の曲はプリセット2で62500Hz描画になります。一度これで実機のSega PCM
  出力が無音になったことがありますが配線不良の可能性が高く、対応は残しています。再発したら
  `VGM_SLAVE_VERBOSE_LOG`の`RATE CHECK`(処理落ちの有無)を確認してからレートを疑ってください。
- **PCM/DACストリーミング未対応 (YM2612/汎用)**: design doc §6のロードマップ通り、YM2612の
  DAC書き込み(VGM 0x8x)や汎用PCMストリーム制御(0x90-0x95)は実再生しません。Sega PCM専用の
  0x67 type=0x80だけは上記の通り対応済みです。

## 6. テスト

実機(RP2040ボード)がない状態でも検証できる範囲はホスト側でテスト済みです:

- `tools/host_tests/`: `src/master/src/vgm_player.c`/`vgz_inflate.c` を実ソースのまま
  (FatFsとpico-sdkの薄いstdioシム経由で)ホストでビルドし、合成VGM/gzipファイルに対して実行。
  ヘッダ解析・コマンド振り分け(YM2151/YM2203/SCCの`0xD2`領域デコード、Sega PCMの`0xC0`register
  writeとPCMデータブロックのアップロードを含む)・未対応コマンドの正しい読み飛ばし
  (libvgmの長さテーブルに合わせて修正した`0x40-0x4E`範囲を含む)・データブロックスキップ・
  ループポイントへのシーク・gzipストリーミング展開(32KB窓の折り返しを含む)を確認済み。
  `test_vgm_segapcm_block.c`はSega PCMのROMイメージブロック(0x67 type=0x80)処理を検証:
  先頭8バイトヘッダの除去、開始アドレスへの`UPLOAD_RESET`シーク、`size-8`バイトのデータ転送、
  転送後もパーサがストリーム同期を保つこと
- `tools/probes/`: ymfm (YM2612/YM2413/YM2151/YM2203) の実際の出力サンプルレートと振幅レンジを
  ホストで実測し、各`chip_*.cpp`のスケーリング定数の根拠にしている
- `tools/host_tests/test_segapcm_render.c`: `chip_segapcm.c`はymfmに依存しない素のCコードなので、
  ホストで直接ビルド+実行し、アドレスの16.8固定小数点アキュムレータの進み方・サンプル読み出し・
  チャンネル無効化が仕様通りであることを確認済み

一方、RP2040実機での動作(SPIタイミング、PWM音質、FM音源勢のリアルタイム性能、Sega PCMアップロード
の実測所要時間など)は未検証です。9つのファームウェア(`master`と8スレーブ)はいずれも実際に
arm-none-eabi-gccでクロスビルドが通ることを確認済みです。

## 7. ビルド方法

```sh
# pico-sdkはこのリポジトリの外(Google Drive同期対象外の場所)に置く
git clone --branch 2.1.1 https://github.com/raspberrypi/pico-sdk.git ~/pico-sdk
cd ~/pico-sdk && git submodule update --init --depth 1 lib/tinyusb lib/mbedtls lib/cyw43-driver lib/lwip lib/btstack lib/cmsis

export PICO_SDK_PATH=~/pico-sdk
cmake -S . -B ~/build-vgmplay   # ビルド出力もリポジトリ外に置く
cmake --build ~/build-vgmplay -j$(nproc)
```

生成物: `~/build-vgmplay/src/master/master.uf2`,
`~/build-vgmplay/src/slave_sn76489/slave_sn76489.uf2`,
`~/build-vgmplay/src/slave_ym2612/slave_ym2612.uf2`,
`~/build-vgmplay/src/slave_ay8910/slave_ay8910.uf2`,
`~/build-vgmplay/src/slave_ym2413/slave_ym2413.uf2`,
`~/build-vgmplay/src/slave_ym2151/slave_ym2151.uf2`,
`~/build-vgmplay/src/slave_ym2203/slave_ym2203.uf2`,
`~/build-vgmplay/src/slave_scc/slave_scc.uf2`,
`~/build-vgmplay/src/slave_segapcm/slave_segapcm.uf2`。各Pico/RP2040-ZeroをBOOTSELボタンを押しながら
USB接続してUF2ドライブとしてマウントし、対応する`.uf2`をコピーすれば書き込み完了です。

SDカードのルート直下に`.vgm`/`.vgz`ファイルを置いてください。ファイル名を大文字小文字を区別せず
ソートした順(`src/master/src/main.c`で列挙後に`qsort`)に再生し、末尾まで行くと最初の曲に戻ります。
数値順に並べたい場合はファイル名の番号をゼロ埋め(`01`,`02`,…`10`)してください(単純な文字列比較の
ため`10`は`2`より前になります)。1周あたり最大`MAX_FILES`件(既定256)/名前バッファ`NAMES_BUF_SZ`
(既定12KB)まで。

## 8. ログの確認方法

スレーブは`stdio`を**UARTとUSB CDCの両方**で有効化しています(各`CMakeLists.txt`の
`pico_enable_stdio_uart`/`pico_enable_stdio_usb`)。**masterはUSB CDCのみ**です — GPIO0/1を
OLEDステータス表示のI2C0に転用したため`pico_enable_stdio_uart(master 0)`にしてあります
(`docs/circuit.md`1章)。書き込み・給電に使うUSBケーブルをそのまま挿した状態で、以下で
ログが見られます。

「音が出ない」等、SPI疎通そのものを疑う場合はまず`tools/spi_bringup_test/`
(`firmware/debug/spi_bringup_test_master.uf2`/`spi_bringup_test_slave.uf2`)を試してください。
VGM解析・チップエミュレーション・マルチコア連携を全部取り除いた最小構成で、マスターが送った
生バイトとスレーブが受信した生バイトをそのまま突き合わせられます(詳細は`firmware/debug/README.md`)。

### 8.1 master

**常時ログ**: 起動時のバナー、SDマウント成否、再生中のファイル名、vgz展開エラー、VGMパース
エラーなど(`src/master/src/main.c`と`vgm_player.c`のprintf呼び出し)。

**OLED (任意)**: SSD1306 (I2C0, GPIO0 SDA / GPIO1 SCL) を繋ぐと、再生中のファイル名・経過時間
(MM:SS、ループをまたいでも加算)・使用チップ名を表示します。描画は core1 が担当し、全画面転送
(約23ms)を core0 の再生タイミングから切り離しています。配線と仕様は `docs/circuit.md` 1.1 章、
実装は `src/master/src/oled_ui.c` / `ssd1306.c`。パネルが無い/ACKしない場合は自動で無効化され、
再生には影響しません。

**詳細ログ(オプトイン)**: `VGM_MASTER_VERBOSE_LOG`というCMakeオプションで、VGMファイルから
読み取った生の値(`[VGM ] 0x50 dd=0x9F`のように、コマンドとその引数バイト)と、実際にSPIへ
送信した値(`[SPI ] cs=GPIO12 opcode=0x02 reg=0x00 data=0x9F`のように、宛先CS・オペコード・
reg・data)を1コマンドごとに出せます。スレーブ側の`VGM_SLAVE_VERBOSE_LOG`ログと突き合わせれば、
「VGM解析」「SPI送信(マスター)」「SPI受信(スレーブ)」のどの段階で値が変わってしまっているかを
切り分けられます。スレーブ側と同様、大量のログ出力が`wait_samples()`のタイミングを乱しうるので
デバッグ専用です。

```sh
cmake -S . -B ~/build-vgmplay-verbose -DVGM_MASTER_VERBOSE_LOG=ON
cmake --build ~/build-vgmplay-verbose --target master
```

**USB CDC (追加配線不要、推奨)**

書き込みに使うUSBケーブルをPCに挿したまま、シリアルターミナルで開くだけです。

```sh
# Linux/ChromeOS: 認識されたデバイスを確認 (例: /dev/ttyACM0)
ls /dev/ttyACM*
screen /dev/ttyACM0    # 抜けるには Ctrl-A, K, Y
# または
picocom /dev/ttyACM0
```

Windows/macOSでは、デバイスマネージャ/`ls /dev/tty.usbmodem*`等でポート名を確認し、PuTTYや
`screen`で開いてください。ボーレートはUSB CDCでは実質無視されるので適当な値(例: 115200)で
構いません。

**UART (デフォルトで無効)**

GPIO0/1 は OLED 用 I2C0 に割り当てているため、master の UART ログはビルドで無効化しています
(`src/master/CMakeLists.txt` の `pico_enable_stdio_uart(master 0)`)。OLED を使わず物理 UART で
ログを取りたい場合は、そこを `1` に戻し、`src/master/src/main.c` の `oled_ui_init()` 呼び出しを
外す(または OLED を接続しなければ自動で無効化されるのでそのままでも可)。その上で
GPIO0(TX)/GPIO1(RX)/GND を USB-TTL シリアル変換アダプタ(3.3V対応)の RX/TX/GND にクロス接続
(master の TX→アダプタの RX)し、115200bps 8N1 で開きます。master は送信専用なので TX と GND
だけでもログは見られます。

### 8.2 スレーブ (RP2040-Zero / Pico)

スレーブも同じUSB CDC/UARTの仕組みでログを見られますが、masterと違い**core1が44.1kHz〜166kHz
というシビアなリアルタイムループでPWM出力を生成している**ため、ログの出し方に制約があります。

- **常時ログ(デフォルトで出る、音声への影響なし)**: 起動時のバナー(`[SN76489] audio engine
  running at 44100 Hz`のような1行)、`RESET`、`MUTE`。これらは曲の切り替わり時などごく低頻度
  にしか発生しないので、printfのブロッキング時間が音声のタイミングを乱す心配はほぼありません。
- **詳細ログ(オプトイン、音声が乱れる前提のデバッグ専用)**: レジスタ書き込み1件ごとに1行
  ログを出す`VGM_SLAVE_VERBOSE_LOG`というCMakeオプションを用意しています。マスターから来る
  SPIフレームを本当に受け取れているか、値は正しいかを配線確認したいときに使ってください。
  ただしUART/USB CDCへの出力は1行あたり数百µs〜数msかかるため、**有効にすると音声のタイミングが
  確実に乱れます**(音を聴く用途では無効のまま使ってください)。Sega PCMのROMアップロードだけは
  1バイトごとではなく4096バイトごとの進捗ログになります(全バイト出すと1曲で数万行になるため)。

```sh
# 詳細ログを有効にした別ビルドを用意する例 (通常ビルドとは別ディレクトリにするのが無難)
export PICO_SDK_PATH=~/pico-sdk
cmake -S . -B ~/build-vgmplay-verbose -DVGM_SLAVE_VERBOSE_LOG=ON
cmake --build ~/build-vgmplay-verbose --target slave_sn76489   # 確認したいスレーブだけでよい
# できた slave_sn76489.uf2 を書き込んで配線確認 → 終わったら firmware/ の通常版に戻す
```

`firmware/`に置いてある`.uf2`はすべて`VGM_SLAVE_VERBOSE_LOG=OFF`(デフォルト)でビルドしたもの
です。詳細ログ版は配線確認用の一時的なビルドとして使い、本番の書き込みには使わないでください。

**注意**: どちらの方法でも、電源投入直後の最初の数行(起動バナーなど)はターミナルの接続タイミング
によっては表示されないことがあります。メインループは曲の再生ごとにログを出すので、そのまま
見ていれば追いつけます。

## 9. 未実装・今後の拡張候補

- スレーブ側のクロックプリセットをVGMヘッダの実クロックに完全追従させる(現状は全チップとも
  2〜3値程度のプリセットから一番近いものを選ぶだけ。2026-08-27時点でプリセット選択自体は
  全チップで機能するようになったが、プリセットに無い任意のHz値には対応しない)
- YM2612 DAC (0x8x) / 汎用PCMストリーム (0x90-0x95) の実再生対応 (design doc §6のロードマップ通り。
  Sega PCM専用の0x67 type=0x80は対応済み、上記参照)
- Sega PCMで**リベース後もなお192KBを超えてスパンする曲**への対応(2026-08-30のROMウィンドウ
  リベースで、512KB空間のどこにあっても使用スパンが192KB未満なら鳴るようになった。それでも
  足りない曲はPico 2ビルドで`SEGAPCM_ROM_BUDGET`を拡大するのが次の手 — RP2350は520KB RAM)、および
  アップロードの高速化(現状1バイト/フレーム。CSを張ったまま複数バイトを連続送信するバルク転送
  モードを別途設ければ、数百ms〜数秒のロード待ちを大幅に短縮できる見込み)
- SCC+/052539の非共有波形モード対応
- 一時停止ボタン(現状スキップボタンのみ実装。`src/master/src/main.c`にpause実装の余地あり)
- サンプルクロックのハード同期 (design doc §5の拡張案: 44.1kHz基準パルスをGPIOで全スレーブへ配線)
- SPIフレームへのCRC/パリティ追加 (現状ノーチェック。ノイズの多い配線では要検討)
