# ソフトウェア設計メモ

[VGM_multi_MCU_design.md](../VGM_multi_MCU_design.md) の方針をどう実装に落としたか、
および既知の制約をまとめたもの。回路/配線は [circuit.md](circuit.md) 参照。

## 1. リポジトリ構成

ファームウェアのソースは `src/` にまとめてあります(third_party/・tools/ はルート直下のまま)。

```
src/
  protocol/          master<->slave共通の通信プロトコル定義 (ヘッダのみ)
  slave_common/      SPIスレーブ受信 + サンプル駆動オーディオエンジン + PWM出力 (全スレーブ共通)
  slave_sn76489/     SN76489 (自作エミュレータ)
  slave_ay8910/      AY-3-8910 (自作エミュレータ)
  slave_ym2612/      YM2612 (third_party/ymfm を使用)
  slave_ym2413/      YM2413 (third_party/ymfm を使用)
  slave_ym2151/      YM2151/OPM (third_party/ymfm を使用)
  slave_ym2203/      YM2203/OPN (FM3ch+SSG3ch, third_party/ymfm を使用)
  slave_scc/         K051649/SCC (自作エミュレータ、MSXカートリッジ用5ch波形メモリ音源)
  slave_segapcm/     Sega PCM (自作エミュレータ、16ch 8bit PCM。サンプルROMは実行時アップロード)
  master/            SDカード読込 + VGMパース + スレーブへのSPI配信
                     (player_config.c = SDの vgmplay.ini(無ければ vgmplay*.ini)でチップ
                      有効/無効・CSピンを上書き、
                      ssd1306.c/oled_ui.c = 任意のSSD1306ステータス表示をcore1で描画)
third_party/         ymfm (FM音源コア, BSD-3), no-OS-FatFS-SD-SPI-RPi-Pico (FatFs+SDドライバ,
                     Apache-2.0/FatFsライセンス), miniz_tinfl (gzip展開, MIT)
tools/               ホスト検証プログラム (host_tests/)、設定GUI (config_gui/)、
                     SPI疎通テスト (spi_bringup_test/)、ymfmキャリブレーション (probes/)
```

## 2. 通信プロトコル

`src/protocol/vgm_spi_protocol.h` 参照。1フレーム=3バイト固定 (`opcode, reg, data`)、CS毎にSPIバスを
共有 (マスター側はソフトウェアCS、スレーブ側はハードウェアSPIスレーブモード)。MISOは配線しない
片方向バスなので、配線数を絞れる代わりにスレーブからマスターへの状態通知はできません
(ヘルスチェック等が必要になったら要拡張)。

**バスは SPI モード1 (CPOL=0, CPHA=1)、フレームは CS 保持のバースト送信**:
`src/master/src/slave_bus.c` の `slave_bus_init()` と `src/slave_common/src/slave_spi_rx.c` は
どちらも `spi_set_format(..., SPI_CPOL_0, SPI_CPHA_1, ...)` を使います。`send_frame()` は
`gap_us == 0`(既定 / YM2151)で **3バイトを 1回の CS アサートのまま連送**(約6µs/フレーム
@4MHz)、`gap_us > 0` で従来の 1バイトごと CS パルス+ギャップ(約370µs/フレーム @gap_us=120)。

**経緯**: 当初は SPI モード0 (CPHA=0) で、CS を low に保ったまま 3バイト連送すると
**1バイト目しかスレーブに届かず 2・3バイト目が無警告で欠落**しました(マスター送信自体は
`VGM_MASTER_VERBOSE_LOG` で正しいと確認済み。`tools/spi_bringup_test/` で切り分け)。
モード0の PL022 スレーブは各バイトの先頭ビットを CS アサート時にサンプルするため、
バイト間に CS エッジが必須だったためです。対処として 1バイトごとに CS をパルスしていましたが、
これだと FM 密度の高い曲(OutRun の YM2151、1サンプル=22µs の wait 内に約30回のレジスタ書き込み)
を送りきれず、マスターが数秒遅れて走り気味になり音程・テンポが崩れました(`gap_us` を上げると悪化)。
2026-09-02 に **SPI モード1 (CPHA=1) なら CS 保持の連続バーストを取りこぼさない**ことを
実機(Pico2 の YM2151 リンク)で確認し、バス全体をモード1へ移行、YM2151 は既定でバースト
(`gap_us=0`)にしました。1フレーム約6µs なので 30書き込みバーストでも約180µs で収まります。
マスターとスレーブは必ず同じモードにする必要があります(モード不一致=全バイト化け)。
配線が弱い個体があれば `vgmplay.ini` の `gap` を非ゼロにして 1バイトパルス方式に戻せます。

パルス間隔(20µs)は実機での実測に基づく値です: 最初は安全側に50µsで固定しましたが、和音や
アルペジオのようにVGMの`wait`コマンドの間に何個もレジスタ書き込みが連続する場面で、1フレーム
あたり最低150µs(3パルス×50µs)のオーバーヘッドが`wait_samples()`の実時間ペーシングを乱し、
体感できるレベルの「テンポの乱れ」として現れました。5µsまで詰めるとバイト欠落が再発(ノイズと
して聴こえる)したため、20µsが実機で確認できた安定値です。別のRP2040個体・配線では再度調整が
必要になる可能性があります(問題の再現有無は`VGM_SLAVE_VERBOSE_LOG`で確認できます)。

- `VGMSPI_OP_RESET` の `reg` はクロックプリセット番号 (各スレーブがコンパイル時に持つ数個の
  実クロック値のうちどれに近いか)。masterがVGMヘッダのクロック値から一番近いプリセットを選んで送る
  (`src/master/src/vgm_chips.c: vgm_pick_clock_preset`)。全チップ(SCCを除く)がこれを使ってプリセットを
  選択する(SCCは実機がMSXの単一クロックでしか使われないため1択のみ)。

  **注意 (2026-08-27修正)**: 以前はYM2612/YM2413/YM2151/YM2203/Sega PCMについて「ymfmはクロックを
  取らないのでプリセットはno-op」としていましたが、これは不正確でした。ymfmのFMエンジンは
  レジスタ値→位相増分の変換自体はクロック非依存ですが、**その結果を正しい実時間Hzで聴くには
  「実クロックに対応するネイティブサンプルレートちょうどでレンダリングする」ことが必須**です
  (`chip.sample_rate(clock)`が実際に意味するのはこれ)。以前は全チップともプリセット0(デフォルト
  クロック)決め打ちでレンダリングしていたため、VGMファイルの実クロックがデフォルトと異なる場合
  (例: YM2151の3579545Hz vs 4000000Hzは多くのアーケード基板で両方一般的、差は約192セント=ほぼ
  2半音)、音程・テンポ全体が均一にズレるバグがありました。エラーやクラッシュを伴わないため
  実機テストで気づきにくく、YM2151/YM2413で実際に踏んだ実機テストで発覚しました。
  現在は`src/master/src/vgm_player.c`がVGMヘッダから各チップの実クロックを読み(YM2413=0x10, YM2612=0x2C,
  YM2151=0x30, Sega PCM=0x38, YM2203=0x44, AY-3-8910=0x74)、対応するプリセットを選択して送信します。
  **注意 (2026-09-04修正)**: これらのフィールドは、VGMデータ開始オフセット(ヘッダ0x34から算出)が
  `フィールド末尾(offset+4)`以上のときだけ有効です。VGM仕様では「データ開始が0x40のファイルは
  ヘッダが0x3Fまでしか無い」= 0x40以降のクロック欄は実体がコマンド列。v1.50のメガドライブ系リップ
  (SN76489+YM2612、データ開始0x40)は先頭のYM2612レジスタ書き込み(`52 28 00 52 …`)がちょうど
  0x44(YM2203欄)に来るため、`hdr_clock()`の`data_start`ガードが無いと**YM2203を誤検出**します
  (OLEDに"YM2203"、かつ`vgmplay.ini`で`[ym2203] enabled = no`なら曲ごと誤スキップ)。
  `調査用/04 - Water.vgm`で実際に発生。`vgm_player.c`の`hdr_clock()`参照。
  スレーブ側は`chip_ops_t.sample_rate_hz(clock_preset)`(`src/slave_common/include/slave_engine.h`)を
  `RESET`のたびに問い合わせ、レンダリングループのペーシング(`src/slave_common/src/slave_engine.c`)を
  動的に再計算します。SN76489/AY-3-8910/SCCは元々自前のtick-budget方式で固定44.1kHz出力に
  リサンプリングしているため、この問題自体がなく`sample_rate_hz`は常に同じ値を返すだけです。
  - **`VGMSPI_OP_CLOCK` を毎秒再送する**。`RESET` は曲頭で1回だけ送る一発フレームなので、
    その瞬間にスレーブがまだ SPI を聞いていない(起動が遅い／セッション中に再フラッシュ)と
    電源投入時の既定プリセット(ymfm 系は 0 = 別サンプルレート)のまま**曲全体が一様に
    ピッチずれ**します(YM2151 は 55930 vs 62500Hz で約 −1.9 半音)。他症状なし・`gap_us`
    非依存・オフラインレンダには出ない。対策として `VGMSPI_OP_CLOCK`(チップをリセットせず
    レートだけ再設定)を追加し、`src/master/src/vgm_player.c: reassert_clocks()` が曲の
    1秒ごとに YM2413/2612/2151/2203/SegaPCM へ再送。遅れて起動したスレーブは次の1秒で
    自動的に正しいレートへ矯正されます。`slave_bus_reset` も3回送出(`sleep_us(300)` 間隔、
    保険)。2026-09-03、OutRun `03 Splash Wave.vgm` の「音程がズレる」がこれでした
    (音色歪みの調査 §5 とは別件)。同時に、250MHz では YM2151 が 62500Hz の描画に間に合わない
    ことも判明し、YM2151 スレーブを 320MHz/1.15V(YM2203 と同じ)へ引き上げました。
- `VGMSPI_OP_WRITE0`/`WRITE1` がチップのport0/port1相当。SN76489は生バイトをそのまま流し込み、
  チップ側で本物同様のラッチ/データバイト処理をする。
- SCCのみ `VGMSPI_OP_SCC_WAVEFORM`/`FREQ`/`VOLUME`/`KEYON` という専用オペコードを4つ追加している。
  実チップは「サブアドレスをラッチしてから書き込む」2サイクルの1ポート方式だが、masterが
  VGMコマンド`0xD2 pp aa dd`の`pp`(領域選択)を見てどのオペコードか事前に判定して1フレームで送る
  ことで、ラッチの2サイクル分を1回のSPI転送にまとめている(機能的には実ハードウェアと等価)。
  フレームサイズ(3バイト固定)を変えずに済むための設計。詳細は`src/protocol/vgm_spi_protocol.h`と
  `src/master/src/vgm_player.c`の`0xD2`処理、`src/slave_scc/src/chip_scc.c`を参照。
- Sega PCMのみ性質の異なる `VGMSPI_OP_PCM_UPLOAD_RESET`/`VGMSPI_OP_PCM_UPLOAD_BYTE` を持つ。
  他のオペコードが「制御レートのレジスタ書き込み」なのに対し、これは「曲の頭に1回だけ起きる
  数万バイト規模のバルク転送」で、既存の3バイトフレームを1バイト単位で使い回している(新しい
  可変長バスモードは作らず、スレーブ側にオートインクリメントする書き込みカーソルを持たせることで
  対応)。1バイトごとにCSをパルスする方式(上記)のため1フレームあたり約65µs(3パルス×約20µsの
  間隔が支配的)かかり、192KBの上限いっぱいまで使うと曲の頭に12〜13秒程度のロード待ちが生じ得ます。
  レジスタ書き込み自体は通常の`VGMSPI_OP_WRITE0`を使う(意味のあるレジスタ空間が0x00-0xFFに
  収まるため、追加オペコードは不要だった)。詳細は`src/slave_segapcm/src/chip_segapcm.c`参照。
  なお `VGMSPI_OP_SEGAPCM_ROM_BASE` を曲頭に1回送り、スレーブがサンプルアドレスからその値を引いて
  固定バッファに収める「ROMウィンドウのリベース」を行っています(512KB級ROM曲対策、§5参照)。

## 3. コア分担 (各スレーブ)

- core0: `slave_spi_rx_run()` -- SPIスレーブ受信をブロッキングで回し、受信フレームを
  `multicore_fifo` でcore1へ転送するだけ
- core1: `slave_audio_engine_run()` -- 44.1kHz (チップによっては別レート、下記) でサンプル生成 + PWM出力。
  各サンプルの直前にFIFOに溜まっているレジスタ書き込みを全部適用してからレンダリングする

YM2612/YM2413/YM2151/YM2203は ymfm が生成するネイティブなサンプルレート
(それぞれ約53267Hz / 49715Hz / 55930Hz / 166400Hz、`chip.sample_rate(clock)` で実測・固定値化:
`tools/probes/ym2612_probe.cpp` 等参照) でそのまま駆動しており、44.1kHzへのリサンプリングは
していません(スレーブごとにサンプルレートが違っても、各スレーブは独立に自分のPWM出力を鳴らす
だけなので問題なし。アナログ段でミキシングする設計だからこそ成立する単純化)。SN76489/AY-3-8910/SCC
は素直に44.1kHzで駆動しています(SCCの音程は実機と同じ f = clock / (32 * (period+1)) で、位相アキュムレータ
のステップ幅をレジスタ書き込み時に再計算する設計にしたので、任意のサンプルレートで駆動できます。
`src/slave_scc/src/chip_scc.c`の`recompute_step`参照)。Sega PCMはさらにシンプルで、実チップの
ネイティブレート(クロック/128。プリセット0の4,000,000Hzで31250Hz、プリセット2の8,000,000Hzで
62500Hz)をそのままエンジンのサンプルレートとして使っており、レート変換の計算が一切不要です。

## 4. VGMコマンド対応状況

| コマンド | 対応 |
|---|---|
| 0x50 (SN76489) | ○ 転送 |
| 0x30 (SN76489 2台目、VGM仕様 "Dual Chip Support") | ○ 転送 (`0x50`と同じデータ形式で
  `VGM_CHIP_SN76489_2`へ。ヘッダのSN76489クロック欄(0x0C)のbit30がデュアルチップ宣言。
  クロックは1台目と共用(専用のヘッダ欄は無い)ため`s_chip_preset`もそのまま複製。
  詳細は[circuit.md §1.3](circuit.md#13-sn76489の2台目-dual-chip-support任意)参照) |
| 0x51 (YM2413) | ○ 転送 |
| 0x52/0x53 (YM2612 port0/1) | ○ 転送 |
| 0x54 (YM2151) | ○ 転送 |
| 0x55 (YM2203) | ○ 転送 (FM/SSGとも同一レジスタ空間、ymfmが内部で振り分け) |
| 0xA0 (AY-3-8910) | ○ 転送 (register上位ビットの2chip目セレクトは無視、1chip固定) |
| 0xD2 (K051649/SCC) | ○ 転送 (領域を事前デコードして専用オペコードで送信。SCC+/052539の
  非共有波形モードは未対応、常に旧SCC互換のch3/ch4波形共有として扱う) |
| 0xC0 (Sega PCM register write) | ○ 転送 (16bitオフセットの下位バイトのみ使用。レジスタ空間が
  0x00-0xFFに収まるため上位バイトは無視。ROMバンクはCTRLレジスタ経由で扱う(下記0x67の行/§5参照)) |
| 0x67 type=0x80 (Sega PCM ROMデータブロック) | ○ 先頭8バイトのヘッダ(全ROMサイズ+ROM内開始
  アドレス)を解釈し、`VGMSPI_OP_PCM_UPLOAD_RESET`で開始アドレスの256バイト境界へシーク→
  端数(`start & 0xFF`)を0x80(無音)で詰めてバイト単位に合わせてから
  実データを1バイトずつアップロード(`VGMSPI_OP_PCM_UPLOAD_BYTE`)。複数ブロックにも対応。曲頭で
  ヘッダ0x3Cのバンク設定を`VGMSPI_OP_SEGAPCM_BANK`で転送。全ブロックを事前スキャンして最小開始
  アドレス(64KB切り下げ)を`VGMSPI_OP_SEGAPCM_ROM_BASE`で通知し、スレーブはこれを引いて~192KB
  バッファに収める(§5「ROMウィンドウのリベース」)。リベース後もなお192KB超のスパンは無音 |
| 0x61/0x62/0x63/0x70-0x7F (wait) | ○ |
| 0x66 (end) + ループポイント | ○ (loop_enabled時、ループ区間を`opts.max_loops`回再生してから終了し次曲へ。`main.c`は2回。0=無制限。スキップボタンでいつでも次曲へ) |
| 0x67 type=0x00 (YM2612 PCMデータバンク) | ○ 全type-0ブロックを連結して1つのバンクとし、
  YM2612スレーブへアップロード(`VGMSPI_OP_YM2612_PCM_*`)。以降のDAC再生はスレーブが自前で行う。
  上限は`YM2612_PCM_BUDGET`(既定192KB、CMake `-DVGM_YM2612_PCM_BUDGET`で変更可)、超過分は末尾を捨てる |
| 0x67 (その他のtypeのdata block) | バイト数だけ正しく読み飛ばし、実際の再生はしない |
| 0x80-0x8F (YM2612 DAC step + wait) | ○ バンクの読み出しカーソルを1進めて`DAC_START`/`DAC_RATE`を
  スレーブへ送る(連続する0x8nを1つの「run」として、レートはウィンドウ平均で数百fpsに間引く)。
  自身の`n`サンプルのwaitはFM/PSG同期のため従来通り処理。runが途切れると`DAC_STOP` |
| 0xE0 (PCMデータバンクseek) | ○ 4バイトLEオフセットを読み、次の0x8n runの開始位置に反映 |
| 0x90-0x95 (DACストリーム制御) | 正しい長さで読み飛ばすのみ(0x8n方式のみ対応、こちらの汎用ストリーム制御は未対応) |
| その他 (YM2608/YMF262等、上記以外の未対応チップ) | libvgmのコマンド長テーブル
  (`player/vgmplayer_cmdhandler.cpp`)を参照して正確な長さで読み飛ばし。0x30-0xDFの主要な
  範囲は実装元と突き合わせ済みで、0xE2-0xFF等ごく一部の予約領域のみ「4バイト」という
  VGM1.71仕様の一般的なパターンに基づく推定。万一長さを誤ってもクラッシュはせず、最悪その曲の
  残りが無音/破綻するだけ |

対応チップは SN76489 / YM2612 / YM2413 / AY-3-8910 / YM2151 / YM2203 / K051649(SCC) / Sega PCM の
8種類(+ 任意でSN76489の2台目)で、8/16bit世代の定番機種はおおむね上記コマンド体系に収まります。
Sega PCMのROMアップロードについては次章および
[circuit.md §4](circuit.md#4-sega-pcmスレーブについて-romアップロード)参照。

**`hdr_clock()`のビットマスク修正 (2026-09-26)**: SN76489デュアルチップ対応の実装中に見つかった
既存バグ。VGM仕様のヘッダクロック欄は、bit31がT6W28(SN76489のバリアント)フラグ、bit30が
デュアルチップフラグとして予約されている。`hdr_clock()`は以前`& 0x7FFFFFFF`(bit31のみクリア)
でこれを剥がしていたが、実際にクリアすべきはbit30の方だった。この不一致自体は単体では無害
(そもそもこのプロジェクトはデュアルチップ宣言のあるファイルを扱っていなかった)だったが、
SN76489の2台目対応でヘッダのbit30を実際にチェックする段になって発覚: **デュアルチップを
宣言したVGMファイルは、クロック値にbit30が混入したまま`clock < 1000 || clock > 100000000`の
サニティチェックに通されるため1億Hzの上限を超えて弾かれ、1台目のSN76489自体が「未使用」と
誤判定されていた**(=そのファイルがチップ欠落判定で丸ごとスキップされていた可能性がある)。
`0x3FFFFFFF`(bit30・31とも クリア)に修正。

## 5. 既知の簡略化・精度に関する注記

- **クロック精度**: 各チップはコンパイル時に2〜3種類の実クロック値しか持たず、VGMヘッダの実際の値には
  完全追従しません(最も近いプリセットを選ぶだけ)。SN76489/AY-3-8910/YM2612/YM2413はNTSC/PAL程度の差
  (〜1%)なので誤差として許容する設計方針([design doc §5](../VGM_multi_MCU_design.md#5-クロック同期に関する方針)
  と同じ考え方)。YM2151(3579545Hz vs 4000000Hz)/YM2203(3993600Hz vs 4000000Hz)/Sega PCM

  で指摘の通りFM音源は負荷が高め。参考までにホスト上での相対比較
  (`tools/probes/ym2151_ym2203_probe.cpp`、絶対値はRP2040とは無関係だがチップ間の相対比較として
  有用): 1秒の音声を生成するのに要したホストCPU時間はYM2612が最も重く、YM2151・YM2203(MIN
  fidelity)はそれよりむしろ軽い、という結果でした。ただしYM2203はネイティブサンプルレートが
  166kHz超とYM2612(53kHz)よりずっと高く、call-per-second自体は最も多いため、FM音源勢の中で最も
  リスクが高いと見ています(SN76489/AY-3-8910/SCC/Sega PCMはいずれも単純なカウンタ/波形テーブル
  読み出しで、計算負荷は軽いはずです)。

  **実機確認済み(2026-08-27)**: YM2151スレーブをRP2040標準133MHzで実機テストしたところ、
  `src/slave_common/src/slave_engine.c`に追加した`RATE CHECK`計測ログ(`VGM_SLAVE_VERBOSE_LOG`時のみ、
  約1秒ごとに実測サンプルレートを出力)により、**実時間に対して2.32倍遅れる**(全ティックで
  処理落ち)ことを確認しました。音程・テンポが均一に低く聞こえる形で現れ、エラーや音飛びは
  一切伴わないため、気づきにくい種類の不具合です。ビルドは`-O3`最適化済みであることを確認済みで、
  ymfmのOPM(YM2151)にはYM2203の`OPN_FIDELITY_MIN`に相当する軽量化オプションが存在しない
  (実機のOPMがプリスケール固定だったため)ことも確認済みです。つまりこれはソフトウェア側の
  バグではなく、RP2040標準クロックでの純粋な処理能力不足です。

  対策は2つ:
  1. `set_sys_clock_khz()`でのオーバークロック(200MHz超も多くの個体で動作実績あり) -- ただし
     今回不足していた2.32倍を埋めるには理屈上300MHz超が必要で、これだけでは不十分な可能性が
     高いです
  2. **Pico 2(RP2350)へのスレーブ基板の置き換え**: 標準クロックが高く(150MHz)、コア

     YM2151/YM2203/YM2612(このセクションでリスクが高いとしている3チップ)のRP2350向けビルドを

     でした(ピン配置・フォームファクタもPico 1と互換なので配線変更も不要)。詳細は
     `firmware/pico2/README.md`参照。RP2040向けのビルド・設定はそのまま残しているので、
     オーバークロックの選択肢も引き続き検討できます。

  **↑は的外れだった、本当の原因が判明(2026-09-05)**: 「同じVGMファイルでも、複数曲を
  ループ再生していると鳴ったり鳴らなかったりする」という追加報告で上記仮説は否定された
  ——ヘッダの中身は毎回同じバイト列なので、ヘッダ解析由来なら常に同じ結果になるはず。
  実際の原因は`src/slave_common/src/slave_engine.c`の **MUTE状態が次のRESET受信でしか
  解除されない**という設計上の穴だった:

  - 曲の終わりに master は全チップへ`VGMSPI_OP_MUTE`を送り、スレーブは`muted=true`にして
    PWM出力を強制的に0にする(即座に音を止めるため)。
  - 次の曲の頭で master は`VGMSPI_OP_RESET`を(冗長化のため)3連続で送り、これを受信して
    初めて`muted=false`に戻る。
  - この3連発が**SPIのタイミング起因で稀に全て取りこぼされる**と、`muted`を戻す手段が
    どこにも無い。以降のVGMSPI_OP_WRITE0はスレーブへ正しく届き`ops->write()`もチップの
    状態も正常に更新され続けるが、`audio_pwm_write(pin, muted ? 0 : sample)`により
    **PWM出力だけが曲の最後までゼロに固定される**。「レジスタは鳴らしているのに無音」
    という、ファイルの中身に依存しない現象になる。
  - 唯一の周期的な保険である`VGMSPI_OP_CLOCK`(FM系5チップへ毎秒再送)はクロック再設定のみで
    `muted`に触れない。SN76489/AY-3-8910/SCCの3チップは周期メッセージ自体が無いので
    なおさら自己修復手段が無かった。YM2413固有の不具合ではなく、8チップ全部に共通する
    アーキテクチャ上の穴で、たまたまYM2413で顕在化しやすかった(あるいは最初に報告された)
    だけの可能性が高い。

  **修正**: NOPとMUTE以外の全オペコード受信時に`muted=false`を戻すよう変更(RESETの成否に
  依存しない)。実際に音を鳴らす系のコマンドを受け取っている時点でそのチップは能動的に
  駆動されている、という判断。曲間の2秒の無音区間はmasterが何も送らないため`muted`は
  正しく維持され、次の曲の最初の書き込みが届いた時点で解除される。全8スレーブ共通の
  `slave_engine.c`を直したので再ビルド・再フラッシュが必要(`firmware/pico1/`・
  `firmware/pico2/`とも更新済み)。実機での確定はまだ。

  **実機確認済み(2026-08-28、YM2151)**: Pico 2標準クロック(150MHz)では1.257倍不足、
  200MHzオーバークロックでも実測ではまだ僅かに不足(かつ`VGM_SLAVE_VERBOSE_LOG`自体のprintf
  オーバーヘッドが計測値を悪化させる影響も判明)。250MHzオーバークロックで実際にピッチ・
  テンポとも正常になることをユーザーが確認しました。またこの過程で、200MHz時にYM2151の
  CSライン(GPIO20)で新規基板特有のSPIバイト欠落(80µsでもまだ発生)が見つかり、120µsまで
  拡大して解消しています(`src/master/src/slave_bus.c`の`s_routes`テーブル)。**新しいスレーブ
  基板を追加するたびに、CS間隔(`gap_us`)はその基板固有の配線マージンとして個別にチューニング
  が必要になる**、というのがこのプロジェクトを通じて繰り返し確認された教訓です。

  **オペコード衝突による音色歪み(2026-08-31、YM2151、OutRun `03 Splash Wave.vgm`)**:
  キーオンの多い曲で YM2151 の音色が歪む症状。verbose ログに `[YM2151] SCC_KEYON data=..` が
  混入していたことで判明。YM2151 のキーオンレジスタは 0x08 で、`{WRITE0, reg=0x08, data}` の
  **オペコードバイト(0x02)が欠落**すると、`slave_spi_rx.c` の再同期が次の `reg` バイト(0x08)を
  有効オペコード(`VGMSPI_OP_SCC_KEYON`=0x08)と誤認 → `SCC_KEYON` として誤ディスパッチされます。
  さらに `ym2151_write()` が `port` 引数を無視していたため、誤ディスパッチされたフレームも
  そのまま生の(ゴミ)レジスタ書き込みとして適用され、FMパッチが壊れて歪みになっていました。
  対策は3段構え:
  (1) 4つのymfm系ラッパー(`chip_ym{2151,2203,2413,2612}.cpp`)で `port` が正規値
  (YM2612は0/1、他は0のみ)でなければ書き込みを捨てる = 誤ディスパッチされたフレームを適用しない。
  (2) **`slave_spi_rx.c` の再同期をチップごとの有効オペコードマスクに変更**
  (`VGMSPI_MASK_<CHIP>`、`vgm_spi_protocol.h`)。YM2151 は 0x08 を受け取らないので、
  オペコードバイト欠落で `reg`=0x08 がオペコード位置に来ても**無効として弾き**、`SCC_KEYON`
  として3バイト消費して整列を崩すことがなくなる(stray 1バイトだけ捨てて次を探す)。
  以前の `< VGMSPI_OP__COUNT` より大幅に厳しい。
  (3) `gap_us` の拡大は **逆効果だったので 120 に戻した**: OutRun 系は 1サンプル(22µs)の wait の
  中に FM レジスタ書き込みが 20〜30 個続く箇所が多数あり、`send_frame` は 1バイトごとに CS を
  パルス+`gap_us` 待ちなので 1フレーム ≈ 3×(gap_us+2µs)。gap_us=120 でも 30書き込みバースト =
  約11ms を 22µs 枠に流し込めず、マスターが曲全体で秒単位に遅れて**追いつこうと早送り**し、
  音符がずれて聞こえる(gap_us=160/200 で悪化した)。
  切り分け: shipped の `chip_ym2151.cpp` ラッパーで Splash Wave をホストレンダリング → **完全に
  クリーン**(サンプル跳び 0、レベル正常、連続)。ymfm-OPM と振り分けは正しい。基板入れ替えで
  スレーブ側配線も除外済み → **残る原因はマスターの SPI 送出／3バイト+CSパルス方式が FM 密曲に
  対して遅すぎること**。
  **根治は「フレームを ~100倍速くする」**: (a) 3バイトを CS 保持のまま連送、(b) 4バイト化+
  同期マーカ、(c) gap_us を下げる、の3案。**2026-09-02〜03 に (a) を実施し解決**:
  - まず (c) を実機で `gap = 2` まで試したが「少し良くなるが歪みは残る」。
  - `VGM_SPI_BAUD_HZ` を 8MHz に上げる案は、Pico2 スレーブが `slave_overclock.h` で
    `clk_peri` を 48MHz 固定にしており PL022 スレーブは `clk_peri ≥ SPIclk×12` が要るため
    48/12 = **4MHz が YM2151 スレーブの上限**で不可。
  - `tools/spi_bringup_test` で、**SPI モード0 の CS 保持バーストは 1バイト目しか届かない**
    ことを Pico2 の YM2151 リンクで再確認(`調査用/spi_bring_up_test1.log`)。次に
    `-DBRINGUP_MODE1` を足して **SPI モード1 (CPHA=1) のバーストは 3バイトとも届く**ことを
    実機確認。
  - 本番反映(2行): `slave_spi_rx.c` / `slave_bus.c` の `spi_set_format` を `SPI_CPHA_1` に。
    YM2151 の `s_routes` 既定 `gap_us` を `0`(バースト)に。master + 全8スレーブを再ビルド・
    再フラッシュ(モード不一致=全化けなのでフラグデー)。1フレーム約6µs。
  RATE CHECK 上は 250MHz で描画は足りている(`62500 samples in ~1010000us`、`fell_behind`≈0。
  verbose時の18〜20%はprintf storm)。
  さらにYM2151の音量がSN76489/AY-3-8910/SCCと比べて小さく聞こえる問題も報告されました。
  当初 `>>7` → `>>6` を「音量」目的で試し、A/Bで音量差が分からず `>>7` に戻していましたが、
  **2026-08-31再考: これは音量ではなく分解能の問題**。OutRun `03 Splash Wave.vgm` の YM2151
  出力はホストレンダリングでピーク 294/2048(実効約6bit)しかなく、10bit PWM に対して量子化歪み
  ＋ ほぼ無音デューティでの搬送波漏れが「音色の歪み」として乗ります(持続系のFM音で顕著。
  YM2203 は出力がずっと大きいので出ない)。切り分け: 蓄積でない(1曲目でも歪む)、SPI化けでない
  (YM2203基板にYM2151ファームを載せCS=21にしても同じ=配線は正常)、SegaPCM無効化でも変化なし、
  デジタルはクランプ0。→ `ym2151_render` を **`>>6`(2倍)** に変更(1chフルで約1020、クランプ
  余裕あり)。効かなければ `>>5` かディザ。

  **実機確認済み(2026-08-29、YM2203)**: `調査用/02 Theme.vgm`(スペースハリアー、YM2203 +
  Sega PCM)で、**Pico 2 + 250MHzでもYM2203が下ずる**ことを確認(ユーザーがVGMPlayとA/Bして
  YM2203側の音程が低いと確認。Sega PCM側は正しい)。ホスト実測(`ym2151_ym2203_probe.cpp`)では
  YM2203の1サンプルあたりコストはYM2151より軽い(86ns vs 160ns)が、レートが166400Hz(YM2151は
  55930Hz)なので**総演算量はYM2151の約1.6倍**。YM2151が250MHzでようやく間に合う以上、YM2203は
  250MHzでは足りない計算になります。ymfmの`ym2203`は`OPN_FIDELITY_MIN`=`clock/24`が下限で、
  これ以上レートは下げられません(下げると`generate()`の呼び出しレート=チップ内部時間の進みが
  変わり音程がずれる)。CMake変数`VGM_RP2350_SYSCLK_KHZ`(既定250000)/`VGM_RP2350_VREG_MV`
  (既定0=SDK標準1.10V)でオーバークロック値とコア電圧を変えられます(実装は
  `src/slave_common/include/slave_overclock.h`、RP2040ではno-op)。

  **実測(2026-08-29、Pico 2、YM2203、`調査用/02 Theme.vgm`)**:
  - 250MHz: 明確に下ずる
  - 300MHz + verbose: `RATE CHECK: 166400 samples in 1025402us, fell_behind=21/166400` =
    2.5%遅い(≈43セント)。だが`fell_behind`=21なので描画自体はほぼ間に合っており、2.5%の大半は
    `VGM_SLAVE_VERBOSE_LOG`のprintfオーバーヘッド。preset=1(166666Hz)で走行していることも確認。
    当初のホスト見積り「400MHz必要」は外れ(M33のキャッシュ/分岐予測の効きを過小評価)。
  - 非verbose 300MHz: 「かなり近い。気持ちだけまだ低め」(ユーザー試聴)
  - **320/360MHz(電圧1.10Vのまま): 音が出ない** → 300MHz超は`VGM_RP2350_VREG_MV=1150`〜`1250`で
    コア電圧を上げる必要あり
  - **320MHz/1.15V: それでも無音。ただしcore1は生きていて`RATE CHECK`は出続ける**(かつ
    `@166400Hz`=起動時レートのまま=RESETを受信できていない)。原因は**`set_sys_clock_khz()`後は
    `clk_peri`が`clk_sys`に追従する**ため、オーバークロック時にPL022 SPI(とUART)まで300MHz超で
    駆動され、SPIスレーブがフレームをデコードできなくなること。`slave_overclock.h`で
    オーバークロック後に`clk_peri`をPLL_USB由来の48MHz固定に張り直すよう修正(2026-08-30)。
    これで250MHzの既存ビルドも含めペリフェラルは常にin-specで動く。
  - **320MHz/1.15V +clk_peri修正: 正常動作をユーザー確認(2026-08-31)**。軽量OPNコアの自作は不要。
    この設定を YM2203 の既定として確定(`VGM_YM2203_SYSCLK_KHZ`=320000 /
    `VGM_YM2203_VREG_MV`=1150、`src/slave_ym2203/CMakeLists.txt`)。他の重量スレーブ
    (YM2151/YM2612/SegaPCM)は `VGM_RP2350_SYSCLK_KHZ`=250000 / `VGM_RP2350_VREG_MV`=0 のまま
    (YM2151は250MHzで実機確認済み、他は同等以下)。`clk_peri`の48MHz固定は全RP2350ビルド共通。
    まだ僅かに低ければ `firmware/pico2/debug/slave_ym2203_350MHz_1v20.uf2`(要1.20V)。
    安定する最小電圧を使うこと(電圧を上げると発熱増)。
  - **YM2612**: 1サンプルあたりのコストはFM勢で最も重い(design-notes冒頭の相対比較)が、
    レートが約53kHz(YM2203の1/3)なので総演算量はYM2151と同程度で、250MHzで足りるはず(未実測)。
    疑わしいときは `firmware/pico2/debug/slave_ym2612_{250,300}MHz_VERBOSE.uf2` で RATE CHECK を比較。
- **SCC+/052539の波形共有**: `src/slave_scc/src/chip_scc.c`は旧SCC(K051649)のch3/ch4波形共有仕様のみ
  実装しています。052539(SCC+)の非共有モードを使うVGMファイルでは、ch3とch4が異なる波形のはずの
  場面で同じ波形が鳴ります。
- **Sega PCMのロード時間とROM容量上限**: サンプルROMを1バイトずつ、1バイトごとにCSをパルスする
  方式でアップロードするため(上記§2参照、1フレーム約65µs)、曲の頭に数秒〜最大12〜13秒程度の
  無音のロード待ちが発生します(design doc の想定していた「即座に反映」の前提からは外れる、この
  機能特有の例外)。アップロード先バッファは約192KBに固定(RP2040のRAM上限)です。
  **ROMウィンドウのリベース (2026-08-30)**: 512KB級ROM(OutRun等)の曲は、サンプルが
  ROMアドレス空間の上の方(例:`調査用/01 Magical Sound Shower.vgm`は全12ブロックが
  0x40000〜0x56000)に置かれていて、そのままだと全ブロックが192KB境界を超えて捨てられ**完全に
  無音**になっていました。対策として、masterは再生前に曲の全`0x67` type-0x80ブロックを事前スキャン
  して最小開始アドレスを求め、64KB(Sega PCMバンクの最小粒度)に切り下げた値を
  `VGMSPI_OP_SEGAPCM_ROM_BASE`でスレーブへ通知します。スレーブは以降すべてのサンプルアドレスから
  このベースを引いて`s_rom[]`を読み書きするので、**曲が実際に参照する範囲が192KB未満なら、それが
  512KB空間のどこにあっても鳴る**ようになります(Magical Sound Showerの使用スパンは約88KB)。
  ベース0(=非Sega-PCM曲や低位ROM曲)ではリベースなし=従来と同一動作。リベース後もなお192KBを
  超えてスパンする曲は超過分が欠けます(その場合はPico 2ビルドの`SEGAPCM_ROM_BUDGET`拡大が次の手)。
  バンク切り替えの仕組み自体(0x3Cのbankshift/bankmaskデコード)は従来通り。
- **Sega PCMの出力音量**: 実曲は音量レジスタに小さめの値を使う(例:`調査用/02 Theme.vgm`は最大
  48/127、同時発音数も少ない)ため、当初の`>>6`ではFM勢より20〜50倍小さくなっていました。
  `src/slave_segapcm/src/chip_segapcm.c`の最終シフトを`>>4`に変更(02 Themeで実測ピーク約2148・
  RMS約323、クリップは全体の0.0008%で他チップと同じ「稀なピークだけクランプ」水準)。フル音量の
  曲が耳につくほど歪む場合は`>>5`へ。
- **Sega PCM 8MHzクロック**: `調査用/02 Theme.vgm`のようにヘッダ0x38が8,000,000Hz
  (X-Board・System 18世代)の曲はプリセット2で62500Hz描画になります。一度これで実機のSega PCM
  出力が無音になったことがありますが配線不良の可能性が高く、対応は残しています。再発したら
  `VGM_SLAVE_VERBOSE_LOG`の`RATE CHECK`(処理落ちの有無)を確認してからレートを疑ってください。
- **Sega PCMの余計なドラム音(ROMアップロードのバイト欠落) (2026-09-19)**: `調査用/
  Space_Harrier_原曲.wav`と実機録音の比較で、Space Harrier(YM2203+Sega PCM、`02 Theme.vgm`)
  の再生に本来ないドラムのような音が曲の頭から最後まで鳴り続ける、という報告。切り分けの経過:
  1. まずSPI転送側を疑った。1音の発音は「音量L/R・ループアドレス・再生アドレス・END・DELTA・
     CTRL(有効化)」の9レジスタを個別の3バイトSPIフレームで連続送信するため、(a) `gap_us`
     40→120(AY-3-8910と同種のバイト破損対策)、(b) `gap_us=0`のバースト化(レジスタ更新が
     アトミックでないことによる「ティアリング」= レンダースレッドが更新途中の中途半端な
     レジスタ状態を読む可能性への対策、Space Harrierはプリセット2=62500Hz描画なので理論上
     ここが最も疑わしかった)を実機で試したが、**どちらも症状に変化なし**。
  2. `vgmplay.ini`の`[segapcm] present=false`でSega PCMを切り分けようとしたが、`main.c`の
     「必要チップが無効なら曲ごとスキップ」ロジックに引っかかり曲自体が再生されなくなった
     (この機能は`present`しか見ておらず`volume`は見ない)。代わりに`[segapcm] volume=0`
     (曲選択にもレジスタ処理にも影響しない、スレーブ側の出力音量だけを0%にスケール)で
     切り分けたところ、無効化すると余計な音が消えることを確認 = **Sega PCM由来と確定**。
  3. `02 Theme.vgm`を静的解析(ヘッダのクロック8MHz・バンクレジスタ0x3C=0x0Bはどちらも
     正しく解釈されており、コマンドストリームにも未知のopcodeなし。使用チャンネルはch8〜15、
     バンク切り替えは全音符でbank=0固定=未使用と判明、バンク関連の疑いは晴れた)。
  4. 転送を一切介さない新規オフラインレンダラー`tools/offline_render/render_segapcm.c`
     (`render_ym2151.cpp`と同じ設計: shipped `vgm_player.c` + shipped `chip_segapcm.c`を
     host上でリンクし、SPI・コア間FIFO・PWMなしで同じレジスタ列を再生)で`02 Theme.vgm`を
     再レンダリングしたところ、原曲相当のオンセット密度(約5.5/秒、190〜200ms間隔=曲のテンポに
     一致)のクリーンな音声が出力され、クリップも皆無(peak 1959 < クランプ閾値2047)。
     **`chip_segapcm.c`自体のロジックは無罪と確定**、残る真因は実機特有の転送経路にあると判明。
  5. `slave_spi_rx.c`を再読すると、コア間FIFOへの書き込みは`multicore_fifo_push_timeout_us(event, 0)`
     という**ノンブロッキング**実装で、core1が詰まっていれば黙ってそのフレームを1つ捨てる
     (§8.2 / CHANGELOG「YM2612 PCM」の項参照、フレーム単位で綺麗に捨てる方がSPIハードFIFO
     溢れによるバイト単位の破損より安全、という意図的なトレードオフ)。ところが
     `vgm_player.c`の`handle_data_block()`は、Sega PCMのROMイメージブロック(`0x67` type=0x80、
     今回は17408バイト)を**開始時に1回だけ`VGMSPI_OP_PCM_UPLOAD_RESET`でシークした後、
     再アンカーなしで`VGMSPI_OP_PCM_UPLOAD_BYTE`を1バイトずつ数千〜1万数千回送り続ける**
     実装だった。YM2612のPCMバンクアップロード(同じ型のブロック、同じ非ブロッキングFIFOの
     上に乗っている)は既に128バイトごとの絶対カーソル再送で保護済みだったが、Sega PCM側には
     同じ保護が入っていなかった。アップロード中にどこか1バイトでもFIFO満杯で落ちると、
     `chip_segapcm.c`の`upload_byte()`は単純にカーソルをインクリメントするだけなので、
     **それ以降の全バイトが1つ前のROMアドレスにズレて書き込まれ**、そのROM領域を参照する
     全チャンネルが曲の最後までズレたデータ(=別の場所のサンプル)を再生し続ける。ドロップは
     1曲の再生開始時に1回きりのアップロードで起きるので、症状が「冒頭から終始」なのはこれで
     説明がつく。SPIのタイミング(gap_us/バースト)をいくら変えても改善しなかったのも道理で、
     ドロップの原因はSPIワイヤの信頼性ではなくスレーブ側コア間FIFOの空き具合だったため。
  **修正**: `vgm_player.c`の`handle_data_block()`(type=0x80)を、YM2612側と同じ考え方で
  256バイト(`VGMSPI_OP_PCM_UPLOAD_RESET`の2バイトアドレスが表現できる最小粒度)ごとに
  絶対アドレスを再送(2重送信)するよう変更。1バイト欠落時の被害を「アップロード全体」から
  「最大256バイト」に縮小する。ロスがない環境(オフラインレンダラー)ではバイト単位で出力が
  完全一致することを確認済み(純粋な保険であり通常時は無影響)。実機で改善を確認
  (2026-09-19、ユーザー確認)。`tools/host_tests/test_vgm_segapcm_block.c`は既存アサーションを
  維持したまま合格(再アンカーによる余分な`UPLOAD_RESET`送信を許容する形でテストのインデックス
  検出ロジックが元々書かれていたため、変更不要だった)。
- **YM2612 DAC/PCM(メガドライブの「PCM」)対応 (2026-09-07初版、2026-09-11チェックポイント方式へ全面刷新)**:
  MDのドラム/ボイスはYM2612の6chをDACモードにして8bit PCMを流し込むもの。DACレートは8〜25kHzで、
  1サンプル=1フレームでSPI送信すると帯域を超えて破綻するため、`0x67` type-0ブロック(全て連結)を
  曲頭にYM2612スレーブへ一括アップロード(`VGMSPI_OP_YM2612_PCM_RESET`/`_BYTE`、上限
  `YM2612_PCM_BUDGET`既定192KB)し、再生自体はスレーブに任せる、という基本方針は最初から
  変わっていないが、**「どう再生させるか」のプロトコルは2回作り直した**。

  **初版(フリーランのリサンプラ、2026-09-07)**: `0x8n` runごとに`DAC_START`(バンク内オフセット)+
  `DAC_RATE`(バイト/*出力サンプル*×65536の16bit固定小数、マスターが32コマンドのウィンドウ平均で
  VGMサンプル単位に計算)を送り、スレーブは`ym2612_render()`内で毎サンプルその固定レート分
  カーソルを進める方式。実機で無音は解消したが、そのすぐ後で複数の不具合が連鎖して発覚した:
  1. **ノイズ**: マスターが計算するレートはVGMのサンプルレート(44100Hz)基準だが、スレーブは
     YM2612ネイティブレート(クロック/144 ≈ 53267Hz)で描画しており、両者は**リサンプルされず**
     一致しない(±20.8%)。さらにメガドライブの音楽ドライバは1バイトのPCM書き込みとFM
     レジスタ書き込みを交互に発行することが多く、当初の実装はFM書き込みを見るたびに
     `DAC_STOP`+`DAC_START`+`DAC_STEP`の3フレームを送っていたため(1バイトあたりの
     SPI予算〜45µsに対しper-byte-CSフレームは〜130µs)、マスターが遅れて追いつこうと
     詰め送りし、スレーブが描画前に複数の`0x2A`書き込みを受けてPCMサンプルを間引く。
  2. **テンポのもたつき**: 上と同じ「1バイトあたりのフレームコストが大きすぎる」ことが
     そもそもの原因で、DACフレームをバースト送信(gap=0、〜7µs/フレーム)に変更してひとまず解消。
  3. **ドラム/ボイスの欠落**: バーストフレームはこのリンクで時々失われる。特に`DAC_START`
     (再生の頭出し)が丸ごと落ちると、そのラン全体が無音になる。バーストにする範囲をFM書き込みまで
     広げた際は逆にSPI受信を溢れさせて全体が壊れる、という往復も経験した。
  4. **PCMバンクアップロード自体の脆さ**: `PCM_RESET`(アップロードカーソルを0に戻す)を1回だけ
     送っていたため、これが落ちると新しい曲のバンクが前の曲のバンクの後ろに追記され、DACが
     オフセット0から前の曲のデータを再生する(「PCMが鳴らない/違う音が鳴る」)。
  5. **電源投入直後の起動レース**: マスター(SDマウント+プレイリスト走査)とスレーブ(クロック/vreg
     安定+core1起動+SPI RX同期)は独立に起動するため、非圧縮`.vgm`など早く1曲目に到達する条件だと
     スレーブが聞き始める前に一度きりのPCMバンクアップロードが送られ、そのスレーブだけ曲の間ずっと
     無音になる。電源投入ごとに勝敗が入れ替わるため非決定的に再現した。

  **チェックポイント方式(2026-09-11、現行)**: 上記の教訓を踏まえた再設計。
  - マスターは毎`0x8n`ごとにフレームを送らず、バンク読み取りカーソルを内部で追跡するだけにして、
    **約2ms(`0x8n` 32個)ごとに`DAC_SYNC`1フレーム**(カーソル位置を4で割って16bitに収めた
    もの)をチェックポイントとして送る。従来の「毎`0x8n`1フレーム」の1/30程度のSPIトラフィックで
    済むため、マスターが遅れて詰め送りする状況そのものが発生しない。
  - スレーブは`DAC_SYNC`を受けるたびに、**自分自身の描画クロックで**前回のチェックポイントから
    何サンプル経過したかを測り、そこから再生レート(バンクのバイト/出力サンプル)を実測・EMA平滑化
    (1/4)する。VGMのサンプルレートを一切参照しないため、44100Hzと約53267Hzのクロック差も
    `0x8n`の`n`ジッタも自動的に吸収される。
  - 読み取り位置は前回チェックポイントを**絶対に超えて進まない**(ランウェイなし)。チェックポイント
    未到達のバイトはまだ「本物」と確信が持てないため。位相のずれは、大きければスナップ、小さければ
    レートを微調整する比例制御で滑らかに閉じる(位置を直接動かさない)。
  - 読み取りインデックス(`s_dac_read_idx`)は**厳密に単調増加**。位相補正でどう動いても既読
    バイトを再度書き込むことは絶対にしない — これが後方向の再生(=波形の一瞬の逆行、聴感上の
    「プチッ」)を原理的に排除する鍵だった。
  - **ラン開始の頑健化**: `DAC_START`(絶対位置)と`DAC_SEEK`(24bit目のオフセット上位バイト)は
    バーストで各×2〜3送信し、かつ`DAC_SEEK`は値が変わらなくても毎回送り直す(長いバイト単位
    アップロード中に偶然0x13バイトが出現して`DAC_SEEK`として誤デコードされ上位バイトにゴミが
    残る、というケースの自己修復のため)。さらに`DAC_START`が全て失われても`DAC_SYNC`単体で
    DACを有効化できるようにした(有効化を`DAC_START`だけに頼ると、それが全滅した曲の先頭ボイスが
    無音になる)。ラン先頭の約2msだけは実測レートがまだ無いため、その`0x8n`の`n`から計算した
    推定レートを`DAC_RATE`(新設、reg:data=16.16固定小数)で種として送る。
  - **PCMバンクアップロードの頑健化**: `PCM_RESET`に絶対カーソル値(4で割った16bit)を持たせ、
    曲頭に×3、アップロード中も**128バイトごとに×2で再送**。1フレーム(`PCM_RESET`または
    `PCM_BYTE`)が失われても、次の再アンカーで128バイト以内にずれが収まる(バンク全体が
    壊れることがなくなった)。
  - **起動レースの対策**: (1) `slave_bus_init()`直後・1曲目の前に**2秒の起動待機窓**を設け、
    250msごとにRESETを再送信 — 遅く起動したスレーブも同期・リセットされてから再生が始まる。
    (2) スレーブの`slave_spi_rx.c`のコア間FIFO push を`multicore_fifo_push_blocking`から
    **ノンブロッキング**(`multicore_fifo_push_timeout_us(event, 0)`)に変更。ブロッキングだと
    core1がまだドレインしていない間にcore0がSPIを読まなくなり、ハードウェアのSPI受信FIFO
    (8バイト)が溢れて**バイト単位で欠落**し、以降の全バイトがずれて誤デコードされる連鎖が
    起きていた(電源投入後1回目だけ、長いPCMバンクをアップロード中にこれが発生していた)。
    フレーム単位の欠落(ノンブロッキングの結果)は上記の再アンカー/冗長送信で復旧可能だが、
    バイト単位の欠落は復旧不能、という非対称性が鍵。
  - 未対応: 汎用DACストリーム制御(`0x90`-`0x95`)。ホストテスト:
    `tools/host_tests/test_vgm_ym2612_dac.c`(チェックポイントプロトコルを検証)。
  - **既知の残課題(2026-09-11時点、未解決)**: PCMバンクアップロード直後の最初の発音
    (`調査用/13 - Janken Match (Voice).vgm`の「じゃん」)だけ、2回目以降の発音(「けん」「ぽん」)
    と比べてやや濁った音色に聞こえる。`DAC_RATE`シード値を`0x8n`の`n`から計算するよう対応した後も
    残っている。RESET直後の`s_dac_local`基準点、アップロード直後のSPI受信のコンディション、
    レートseed式の精度など、要因の切り分けが済んでいない。
  - **実機確認済み(2026-09-11)**: プレイリスト複数曲・電源再投入10回以上で、ドラム/ボイスの
    欠落なし・テンポのもたつきなし・上記①②のノイズ解消を確認。上記残課題のみ open。

- **OLEDが「starting...」で固まる不具合(2026-09-11修正、当初2026-09-07にcore1のprintfが原因と誤診断)**:
  症状は「音声は正常だがOLEDが起動画面のまま更新されない」。

  当初(2026-09-07)は`src/master/src/oled_ui.c`の**core1(描画ループ)からの`printf`**が原因と
  診断し、core1の`printf`全廃(`s_oled_answered`等のvolatileフラグに記録し必要ならcore0が出力)
  で対応した。改善しないとの報告を受けて再調査したところ、これは誤診断だったと判明。

  **真因**: `src/master/src/vgz_inflate.c`の`tinfl_decompressor decomp`(miniz_tinflのハフマン
  復号器、内部に1024エントリの高速検索テーブル×3面などを持ち**約8KB**)が、`vgz_inflate_file()`
  内の**スタックローカル変数**だった。RP2040のスタック配置は次の通り:

  | 領域 | アドレス | 用途 |
  |---|---|---|
  | SCRATCH_Y上半分 | `0x20041800`–`0x20042000` | **core0スタック(2KB)** |
  | SCRATCH_Y下半分 | `0x20041000`–`0x20041800` | 未使用スラック |
  | SCRATCH_X | `0x20040800`–`0x20041000` | **core1スタック(2KB)、OLED描画ループ** |

  `.vgz`を1曲展開するたびにcore0のスタックが約6KBあふれ、SCRATCH_Yを突き抜けて**SCRATCH_X
  (=core1のスタック全域)**に到達。core0がハフマンテーブルを構築している間、`busy_wait_us()`で
  待機中のcore1のスタック(戻りアドレスを含む)をハフマンのバイト列で上書きしてしまい、core1が
  次の関数リターンで存在しないアドレスへジャンプして**HardFault**、そのまま停止する
  (デフォルトのフォールトハンドラは無限ループ)。音声再生は別コア/別タイミングなので影響を
  受けず鳴り続けるため、「音は正常だがOLEDだけ固まる」という症状に一致する。

  **発見の経緯**: core1用の軽量HardFaultキャッチャ(`src/master/src/core_fault.c`、恒久的に
  同梱)を追加し、フォールト時の`PC`/`LR`/レジスタを記録するようにしたところ、`PC`が
  `busy_wait_us()`呼び出し直後の存在しないアドレスを指しており、そのアドレスがハフマン
  テーブル(`m_look_up`)の隣接する2エントリの値と一致することから特定した。

  **修正**: `tinfl_decompressor decomp;` を `static tinfl_decompressor decomp;` に変更するのみ
  (`.bss`へ移動、+約8KB)。`vgz_inflate_file()`はcore0の再生ループから非再帰・逐次にしか
  呼ばれないため共有インスタンスで問題ない。

  2026-09-07時点の対応(core1の`printf`全廃、`sleep_ms`/`sleep_us`→`busy_wait_us`化)は
  それ自体は妥当な補強(pico-sdkの`sleep_*`がデフォルトアラームプール経由でcore0のタイマー
  IRQに依存する件、core1からのUSB CDC `printf`がTinyUSBと競合しうる件は共に事実)だが、
  今回のハング再発が示す通り**真因そのものではなかった**。再発するようなら
  `OLED_I2C_HZ`を100kHzに下げる/SDA-SCLのプルアップ強化(ハード側)も検討。
- **フラッシュ一時キャッシュ(`[player] flash_cache`)の設計判断 (2026-09-30)**: SPI接続の
  TFT液晶をOLEDに追加/代替する検討から出た機能。TFTを載せるにはSPI0かSPI1のどちらかを
  既存デバイスと共有する必要があるが、SPI1はスレーブバス(全8スレーブ共有、曲再生中ずっと
  高頻度アクセス)なので論外、残るSPI0はSDカード(`hw_config.c`のSPI0/GPIO16-19)と共有する
  ことになる。検討した選択肢:
  1. SPI0をSDカードとTFTで共有し、自前でミューテックス/排他制御を追加する。
  2. RP2040のPIOブロック(本プロジェクトでは未使用)でソフトウェアSPIを組み、TFTを
     OLEDのI2C0と同じく完全に独立したバスにする。
  3. **(採用)** 曲頭で一度だけSDカードから曲データをこの基板自身のオンボードフラッシュへ
     コピーし、以降の再生はそのコピーをXIP(メモリマップドフラッシュ読み出し)経由で読む
     ことで、**再生中はSDカードを完全にアイドルにする**。SDカードが触られるのは曲送りの
     瞬間だけになるので、SPI0はその瞬間を除けばTFT専用として自由に使え、1と2のような
     恒常的なバス排他制御が要らなくなる。
  1は実装は小さいが、曲の再生中ずっとSD読み込みとTFT描画がSPI0を取り合う恒常的な排他制御
  コードが要る。2は設計としては最もクリーンだが、PIO SPIドライバを新規に書く手間が要る。
  3はSDカード自体のサイズ制限が(1MiBのキャッシュ領域に収まらない曲は従来通りSD直読みに
  フォールバック)実用上ほぼ問題にならない(手持ちの実曲は最大でも`調査用/01_Phantasy.vgm`の
  約600KB)ことと、`vgz_inflate.c`のgzip展開が既に「SDに展開先ファイルを書いてそこから
  再生する」という同型のパターンを持っていた(`main.c`の`TEMP_VGM_PATH`)ことから、
  `vgm_player.c`側を一切変更せずに済む(FatFsのパス文字列を渡すだけなので、コピー先が
  "0:"か"1:"かを`vgm_player.c`は気にしない)という理由で採用。

  **実装**: `third_party/no-OS-FatFS-SD-SPI-RPi-Pico`はFatFsの`FF_VOLUMES=2`を既に有効にして
  いたが、その`glue.c`(diskioグルー層)は`sd_get_by_num(pdrv)`経由でSDカードにしか
  ディスパッチしない作りだったため、`glue.c`自身に「`pdrv == FLASH_DISK_PDRV`ならSDではなく
  `src/master/src/flash_disk.c`の実装へ」という分岐を追加(このファイル自身の冒頭コメントが
  「glue関数として繋ぐのが正しい拡張方法」と明記しているので、想定された拡張ポイント)。
  `flash_disk.c`はフラッシュの末尾1MiBを"1:"ボリュームとして予約し、512バイトセクタ単位の
  `disk_read`/`disk_write`を、内部で4096バイト消去ブロック単位の「読み出し→上書き→消去→
  再書き込み」に変換して見せる(FatFs側はプロジェクト全体でFF_MIN_SS=FF_MAX_SS=512固定の
  ため、フラッシュの消去粒度をFatFsに意識させない)。初回起動(または未フォーマット時)は
  `f_mkfs()`で1回だけFAT12相当にフォーマットし、クラスタサイズ=消去ブロックサイズ(4096)に
  揃えることで通常の書き込みが消去ブロックをまたがないようにしている。
  フラッシュの消去/書き込み中はXIP自体が両コアとも止まるため、OLED描画ループを走らせている
  core1を`multicore_lockout_start/end_blocking()`で退避させる必要がある(`oled_ui.c`の
  `core1_main()`が起動直後に`multicore_lockout_victim_init()`を呼ぶよう変更)。
  `main.c`はSDカードマウント後、`[player] flash_cache = yes`のときだけ`flash_disk_init()`を
  呼んでこのボリュームをマウント/フォーマットし、以降`play_one()`で毎曲
  `flash_disk_cache_file()`により(gzip展開後の)VGMをこの"1:"へコピーしてから再生する
  (コピー失敗/曲が大きすぎる場合はSDから直接再生する従来動作にフォールバック)。
  予約領域はファームウェアのサイズに関わらずフラッシュの物理末尾から逆算しているため
  (`PICO_FLASH_SIZE_BYTES - FLASH_DISK_BYTES`)、ファームウェアが将来1MiBを超えるまで
  衝突の心配はない(`flash_disk_init()`は念のため`__flash_binary_end`と比較する安全確認も
  毎起動時に行う)。このキャッシュ機能単体は実機で再生確認済み(2026-09-30)。既知の課題:
  曲間の待ちがflash_cache無効時より若干長くなる(毎曲の「SDから読んでフラッシュへ消去+
  書き込み」が`play_one()`の再生開始前に挟まるため)。ユーザーからのフィードバックにより、
  この待ち時間の調整はTFT液晶ドライバも含めた一連の機能が完成してからまとめて行う方針
  (例: コピーのチャンク/バッファサイズ見直し、消去済みブロックの再消去省略、コピーと
  次曲の先読みの重ね合わせなど)。TFT液晶ドライバ自体は次項参照。
- **SPI接続TFT液晶(ST7735)ドライバの実装 (2026-09-30)**: 上記の設計判断を受けて、OLEDの
  代替として選べるステータス表示を追加。`[player] display = oled`(既定)/`tft`で切り替え。

  **構成**: `src/master/src/st7735.c`が128x160 RGB565のフレームバッファ+全画面プッシュ型
  ドライバ(`ssd1306.c`と同じ設計思想 -- 差分描画ではなく毎回全体を転送)。5x7フォントは
  `ssd1306.c`と共有するため`font5x7.h`へ切り出し(元は`ssd1306.c`内にハードコードされていた
  テーブルをそのまま移動、重複を避けるため)。`oled_ui.c`はSSD1306/ST7735どちらのバックエンドも
  同じ4関数(`init`/`clear`/`text`/`show`)の関数ポインタテーブル越しに叩く形に一般化し、
  `render()`/`draw_wrapped()`/`draw_chips()`は一切変更していない(両パネルとも幅128pxで
  文字数/行が一致することを`_Static_assert`で保証)。

  **SPI0共有の実際の排他制御**: 設計判断の時点では「flash_cache併用でSDはほぼアイドルになる」
  という前提だったが、(a) `flash_cache`はあくまで任意設定でtftと独立に選べる、(b) 曲送り時の
  スキャン/コピー自体はSDへの実アクセスを伴う、という2点から、SD/TFTどちらのSPI0アクセスも
  素通りさせず`src/master/src/spi0_bus_lock.c`の`mutex_t`で直列化することにした
  (`pico_sync`、`critical_section_t`ではなくmutexにしたのはSDの1回の読み書きが数十msかかり
  得るため)。`third_party/no-OS-FatFS-SD-SPI-RPi-Pico`の`glue.c`のSDカード分岐すべてを
  `spi0_bus_lock()`/`unlock()`で囲み、`st7735.c`側も自分の全SPI0アクセス(初期化・コマンド・
  データ送信)を同じロックで囲んでいる。ボーレートは`hw_config.c`のSDカードと同じ20MHz固定
  (パネル用に切り替えて戻し忘れると、次のSD通信が誤ったクロックのまま走ってしまうため
  -- SDドライバは`sd_init_driver()`時に一度だけボーレートを設定し、以降の読み書きでは
  再設定しない実装だった)。

  **起動順序の見直し**: `[player] display`の選択はSDカード上の`vgmplay.ini`を読むまで
  分からないが、従来`main.c`はOLED初期化(`oled_ui_init()`、core1起動)をSDマウントより
  **前**に行っていた(マウント失敗時にも画面へ「SD mount failed」を出せるように)。
  設定を先に読んでからディスプレイを初期化する順序に組み替え: `f_mount()` →
  `player_config_autoload()`(マウント失敗時もf_openが単に失敗するだけで安全に既定値へ
  フォールバックすることを確認済み)→ `oled_ui_init()`(ここで初めて`display`の値を見て
  バックエンドを選ぶ)→ マウント失敗チェック(ここへ移動、失敗時のメッセージがOLED/TFT
  どちらでも出せるようになった -- 従来はOLED起動がマウントより先だったためOLED限定の
  恩恵だった、副次的な改善)。`[player] flash_cache`用の`flash_disk_init()`呼び出しは
  core1のロックアウト登録(`oled_ui_wait_for_core1_lockout_ready()`)に依存するため、
  従来通り`oled_ui_init()`の直後に据え置き。

  **ST7735の検出不能性**: このパネルは書き込み専用配線(MISO未使用)が一般的で、SSD1306の
  ようなI2C ACKによる「本当に配線されているか」の判定ができない。`st7735_init()`/
  `st7735_show()`は常に`true`を返す(ドキュメントコメントに明記)。したがって
  `oled_ui_answered()`はtft選択時は常にtrue、`oled_ui_reinit_count()`は常に0のままになる --
  「配線し忘れたが気づかない」を検出する手立てはログ上は無い(電源投入後に画面が真っ暗なら
  配線を疑う、という従来通りの目視確認に頼る)。

  **パネル個体差**: 安価なST7735モジュールは「タブの色」でRAMオフセット・RGB/BGR順が
  異なる。`ST7735_XSTART`/`YSTART`/`MADCTL`を調整ノブとして`st7735.h`に用意(コメントに
  症状別の調整方針を記載)。CS/DC/RSTのGPIO(既定3/4/5)は`tft_pins.h`に切り出し、
  `slave_bus.c`のCS衝突警告(`[player] skip_button`と同じ動的予約の仕組み)にも
  `[player] display = tft`のときだけ反映されるようにした。

  **テスト**: `[player] display`のパース(`oled`/`tft`、bad値の拒否)は
  `tools/host_tests/test_player_config.c`に追加、GUI/CLI側も同じキー+動的なCS予約警告+
  「flash_cache = yesを推奨」の警告を`tools/config_gui/vgmplay_config_gui.py`に実装し
  `test_vgmplay_config_gui.py`でテスト済み。`st7735.c`/`spi0_bus_lock.c`自体はRP2040の
  ハードウェアAPI(`hardware/flash.h`同様、`hardware/spi.h`・`pico/mutex.h`)に依存するため
  ホストテストの対象外(`flash_disk.c`と同様の扱い)。

  **実機確認までに見つかった不具合3件 (2026-10-01〜02)**: 単体テストツールを新規に3つ用意して
  段階的に切り分けた(`tools/st7735_test/`: MicroPythonでの単体色確認、`tools/st7735_text_test/`:
  実際の`st7735.c`をそのままリンクした文字表示単体テスト、`tools/sd_test/`: 実際の
  `hw_config.c`+FatFsをそのままリンクしたSDカード単体読み込みテスト -- いずれもmasterの
  本番ファームウェアからスレーブ・マルチコア・相手側の機能を取り除いた最小構成で、
  「本物のドライバコードをどこまで削って動かしても再現するか」を切り分けるためのもの)。

  1. **色が赤と青で反転**: MicroPythonでの単体テストで先に発覚。`ST7735_MADCTL`の
     BGR/RGBビット(0x08)が逆だった(`0xC8`→`0xC0`に修正、このプロジェクトで実際に使った
     パネルでの実測に基づく値)。
  2. **`st7735_text_test`(SDカード無しの単体ファーム)で何も映らない**: `st7735_init()`が
     `spi_init()`/`spi_set_format()`でSPI0ペリフェラル自体は設定するものの、SCK/MOSIの
     GPIOをSPI機能へ割り当てる`gpio_set_function(..., GPIO_FUNC_SPI)`を一度も呼んでいなかった
     ことが原因。本番ファームでは`main.c`の起動順序(SDマウント→設定読込→
     `oled_ui_init()`)により、SDカードドライバ(`FatFs_SPI/sd_driver/spi.c`)が先に
     同じGPIOへこの設定を済ませてしまっていたため偶然動いて見えていただけで、SDカードが
     一切無い単体ファームでは誰もこの設定をしないため何も出力されなかった。`st7735_init()`
     自身がSCK/MOSIのGPIO機能設定を行うよう修正し、何に依存しているかに関わらず
     自己完結するようにした。
  3. **本番ファーム(`master.uf2`、SD+TFT両方有効)で、TFTだけが何も映らず、かつSDの
     ディレクトリ一覧取得が`FatFs error 1`(`FR_DISK_ERR`、ディスクI/O層の実エラー)で
     失敗する**: `tools/sd_test/`単体ではSDカードの読み込みが完全に安定していたため、
     SDカード・配線そのものは健全と判明。残る違いはTFTの定期描画(core1、既定150ms間隔)が
     動いているかどうかのみだったため、描画間隔を2000msまで落として再現頻度を確認したところ
     症状が解消、500msまで戻しても実機で問題が再現しないことを確認した。
     `third_party/no-OS-FatFS-SD-SPI-RPi-Pico/FatFs_SPI/sd_driver/sd_spi.c`の
     `sd_spi_deselect()`に残っていたコメント("MMC/SDC enables/disables the DO output in
     synchronising to the SCLK... bus conflict with MMC/SDC and another SPI slave that
     shares an SPI bus")が示す通り、SDカードはCSをHIGHにしてもMISO(DO)出力を
     即座には手放さない個体があることが知られており、ライブラリ自身もCS解除直後に
     ダミーバイト1個を送る対策を既に持っている。ただしこの対策は`disk_read()`等
     **1回の**FatFs呼び出しの中でしか完結しておらず、`f_findfirst()`のように複数回に
     分けて`disk_status()`→`disk_read()`を呼ぶ高レベル処理では、その**呼び出しの合間**
     (mutexが一旦解放される瞬間)にTFTの描画(SPI0トラフィック)が割り込む余地が残っていた。
     SDカード側がこの間のバス上のSCK/MOSI活動を完全には無視しきれない個体だったために、
     次の`disk_read()`が`FR_DISK_ERR`で失敗していたと推測される。**恒久対応として
     TFTの再描画間隔をOLEDの150msから500msへ(`oled_ui.c`の`display_backend_t.redraw_ms`、
     バックエンドごとに個別設定可能にした)引き下げ、SDアクセスとの衝突頻度を下げることで
     解消**(ステータス表示の経過時間は元々1秒刻みなので、500msでも体感上の滑らかさは
     変わらない)。より確実な対策(MISO(GPIO16)へのプルアップ抵抗、またはTFTを
     RP2040のPIOで完全に独立したSPIバスに載せる設計)は、将来さらに速い更新間隔が
     必要になった場合の選択肢として残してある。

  3つとも実機で修正・確認済み(2026-10-02、SDカード上の実VGMファイルでの再生とTFT表示を
  同時に確認)。masterのクロスビルドも確認済み。

- **フォルダのカバー画像表示(JPEG/PNG、`display = tft`限定) (2026-10-02)**: VGMフォルダに
  置いた画像をTFTの上部に表示する機能。要望の時点でレイアウトは「上部に画像・下部に文字」を
  ユーザーから明示指定(当初案の「下部に画像」から逆転)。

  **対応形式の選定**: JPEG/PNG両対応を要望された。JPEGは組み込み向けの定番デコーダ
  `third_party/tjpgd`(ChaN氏のTJpgDec、FatFsと同じ作者、R0.01c、
  [elm-chan.org](https://elm-chan.org/fsw/tjpgd/)より取得、MITに近い独自ライセンス)を
  そのまま採用 -- `JD_FORMAT`だけRGB888既定からRGB565へ変更(ST7735のフレームバッファと
  直接一致、変換不要)、ベンダー元からの変更点はこの1行のみ(`third_party/tjpgd/LICENSE`に
  明記)。PNGは埋め込み向けの定番ライブラリが乏しいため自前実装: チャンク解析・スキャンライン
  フィルタ復元(None/Sub/Up/Average/Paeth)は新規に書き、DEFLATE展開だけは`.vgz`展開で
  既に使っている`third_party/miniz_tinfl`を再利用。対応範囲は意図的に限定 -- 8bit深度、
  非インターレース、グレースケール/RGB/RGBA(パレット形式・16bit・Adam7インターレースは
  非対応、デコード失敗として安全にフォールバック)。

  **パレット(color type 3)PNG対応を追加 (2026-10-04)**: 実機でカバー画像機能を
  実際に使ったユーザーから、レトロゲームのジャケット画像(`Gradius 2.png`)が
  「PNG color type 3 not supported」で空欄フォールバックになる、という報告があった。
  パレット形式はレトロゲーム素材で特によく使われる形式のため、「安全に失敗する」
  だけでなく実際に対応することにした。実装は、IHDRとIDATの間にある必須の`PLTE`
  チャンク(最大256色×RGB3バイト)を読み取って`static uint8_t s_png_palette[256*3]`
  に保持し、`png_blit_row()`で各ピクセルの値(グレースケール/RGBのような実サンプル値
  ではなく、1バイトのパレットインデックス)をこのテーブルで色に変換するだけ --
  スキャンラインのフィルタ復元(bpp=1として扱う)やチャンク解析の枠組みは既存のまま
  再利用できた。ホストテスト(`test_cover_image.c`)も、インデックス0(黒)と
  インデックス1(白)を上下半分に配置した2色のパレットPNGに置き換え、実際に
  PLTEルックアップが機能していること(インデックスをそのまま明度として読んでいたら
  白にならないはずの箇所が正しく白になること)を確認している。

  **tinflインスタンスの共有**: `.vgz`展開(`vgz_inflate.c`)とPNGのIDAT展開はどちらも
  tinflの状態(`tinfl_decompressor`約8KB + `TINFL_LZ_DICT_SIZE`=32KBの窓、計約40KB)を
  必要とするが、両者は同じcore0上で逐次・排他的にしか起きない(曲の`.vgz`展開は再生開始前、
  カバー画像のデコードもフォルダ入場時の1回のみ、同時には起きない)ため、新規
  `src/master/src/inflate_scratch.c`にこの約40KBを1個だけ持つよう共通化し、
  `vgz_inflate.c`側もそちらを使うようリファクタ(重複確保を回避)。

  **ホストテストで発見したPNGデコードのバグ**: 実装直後にPillowで生成した実画像
  (`tools/host_tests/gen_cover_test_images.py`、`cover_test_images/`に成果物をコミット)を
  使った新規ホストテスト`tools/host_tests/test_cover_image.c`を書いて実行したところ、
  **パレット画像以外の全PNGが例外なくデコード失敗**。原因はPNGのIDATストリームが
  生DEFLATEではなく**zlib形式(RFC 1950: 2バイトヘッダ+生DEFLATE+4バイトAdler32)で
  ラップされている**ことを失念していた点 -- `.vgz`のgzip展開(`vgz_inflate.c`)は
  gzip独自のヘッダ(gzipとzlibは別物)を手動でスキップしてから`tinfl_decompress()`に
  生DEFLATEだけを渡す設計だったため、同じ書き方をPNGにも踏襲してしまい、zlibヘッダの
  扱いが漏れていた。実際には`miniz_tinfl.h`に`TINFL_FLAG_PARSE_ZLIB_HEADER`という
  まさにこの用途のフラグが用意されており、1行追加するだけで解決(`cover_image.c`の
  `png_inflate_read()`)。**実機に触れる前にホストテストで即座に発見・修正できた**好例
  (このバグを実機だけで追っていたら「TFTもSDも単体では正常なのに画像だけ全滅する」という
  切り分けの難しい症状になっていたはず)。

  **スケーリング方針**: 要望通り「画面幅(128px)に合わせて縮小」をそのまま実装 -- 縦横比は
  保持したまま単一の整数間引き係数で縮小(歪みなし、拡大はしない)。結果として画面高さ
  (COVER_AREA_H=96px)を超える縦長画像は中央寄せの上下が見切れる(「幅優先」の要望を
  文字通り実装した結果の挙動として明記)。JPEGは`tjpgd`自身の1/2^N粗スケール(0〜3)で
  目標サイズに近い側まで落としてから、`cover_image.c`側で追加のニアレストネイバー間引きを
  行い正確なサイズに合わせる(tjpgdは2のべき乗でしか縮小できないため)。PNGは元々
  任意スケールのDCTベース縮小機能がないため、全スキャンラインをフィルタ復元した上で
  間引く(復元自体はどのみち全スキャンライン必要 -- Up/Average/Paeth系フィルタが前の行を
  参照するため、間引いて捨てる行もフィルタ復元だけは省略できない)。

  **メモリ**: PNG側はスキャンライン2行分(前行+現在行、最大`MAX_PNG_SRC_W`=1024px×4バイト
  (RGBA)=4KB×2)を`static`確保、JPEG側は`tjpgd`の作業領域(約3100〜4096バイト)+MCU単位の
  出力バッファを`static`確保 -- いずれもcore0のスタック(2KB)に収まらないため、この
  プロジェクト全体の既存の方針(`vgz_inflate.c`のHardFault事例以降の教訓)通り`static`に
  している。`tools/host_tests/test_cover_image.c`でのデコード検証とmasterのクロスビルドは
  確認済みだが、実機でのTFT表示確認は**まだ**(2026-10-02時点)。

  **実機確認中に再発したSDカード読み込みエラーとその対策 (2026-10-02)**: カバー画像機能を
  組み込んだ実機テストで、`f_findfirst`が`FatFs error 1`(`FR_DISK_ERR`)で失敗する現象が
  再発した。これは以前`[player] display = tft`の節で解決したはずの不具合と同一の症状
  (SDカードがCS解除後もバスを完全に手放さない個体が、TFTの描画トラフィックで混乱する)
  だが、再描画間隔を500msへ下げる対策だけでは不十分だったことが判明した:

  1. まずカバー画像のデコード処理(`cover_image_show()`)自体を疑った -- SDから何度にも
     分けて読み込むため、1曲分の短い読み込みより遥かに長くSDアクセスが続き、その間
     core1のTFT描画(500msごと)と衝突する機会が格段に増える。対策として、デコード中は
     `multicore_lockout_start/end_blocking()`(`flash_disk.c`が自分のフラッシュ書き込みで
     既に使っている仕組み)でcore1を完全に一時停止するよう変更。
  2. ところが修正後も同じエラーが再発。ユーザーから「画像読み込みとTFT書き込みが交互に
     なっているのでは、処理をブロッキング的にすれば衝突しにくいのでは」という指摘を受け、
     実際にエラーが起きている箇所(`visit_dir()`の`f_findfirst`/`f_findnext`によるフォルダ
     一覧取得)も同じ理由で脆弱だと判明 -- これも1回の呼び出しごとに個別のSDトランザクション
     (`disk_read()`)を発行し、呼び出しの合間で`spi0_bus_lock`のmutexが解放されるため、
     ファイル数の多いフォルダほどTFT描画が割り込む隙間が増える。こちらも同様に
     `multicore_lockout`でcore1を一時停止するよう修正(`main.c`の`visit_dir()`)。
  3. さらにユーザーから「曲の再生中もVGMファイルをSDから読み込み続けている件は、
     フラッシュ転送方式(`[player] flash_cache`)に統一すべきではないか、`display = tft`の
     ときは必ずそうしてほしい」という指摘があり、これが根本的な解決策だと判断した --
     フォルダ一覧取得・カバー画像デコードは`multicore_lockout`で個別に対処できるが、
     **曲の再生そのもの**も(`flash_cache`が無効だと)曲の長さ分だけ継続的にSDへアクセスし
     続けており、ここをブロッキング化する(=再生中ずっとTFT描画を止める)わけにはいかない。
     そこで`player_config_flash_cache_enabled()`(`player_config.c`)を
     `s_flash_cache_enabled || s_display_is_tft`に変更し、**`display = tft`を選んだ時点で
     `[player] flash_cache`の設定値に関わらず強制的に有効化**するようにした。これにより
     `display = tft`時は常に曲データがフラッシュへ一括コピーされてから再生され、再生中の
     SDアクセスがそもそも発生しない(＝衝突の機会自体が無くなる)。設定ファイル側の
     `flash_cache`キーは「SDアクセス頻度を減らす任意設定」から「`display = oled`のときだけ
     意味を持つ設定」に意味が変わった(`player_config.h`のコメントを更新)。
     `tools/config_gui/vgmplay_config_gui.py`も`rows_from_settings()`/`rows_from_form()`両方で
     同じOR条件を反映し、GUIでTFTを選ぶと保存されるiniファイルにも常に`flash_cache = yes`が
     書かれるようにした(チェックボックスの状態に関わらず、実際の挙動と食い違うファイルが
     生成されないように)。`tools/host_tests/test_player_config.c`と
     `tools/config_gui/test_vgmplay_config_gui.py`双方に強制動作のテストを追加。
  4. ところがflash_cache強制後もユーザーの実機テストで**全く改善が見られず**、しかも
     今度は起動直後の最初の`0:`(ルート)一覧取得からすでに`FR_DISK_ERR`が出ていた --
     1曲も再生していない段階での失敗であり、3で潰したはずの「再生中の継続アクセス」が
     原因ではあり得ない。ここでようやく`multicore_lockout_start/end_blocking()`という
     手法そのものの前提が誤っていたことに気づいた: この機構はcore1を安全な地点まで
     待ってから止めるのではなく、**コア間割り込みで即座に割り込む**(pico-sdkの実装)。
     つまりcore1が`st7735.c`の`spi_write_blocking()`の最中 -- `spi0_bus_lock()`は取得済みだが
     `spi0_bus_unlock()`はまだ、というまさにSPI転送の途中 -- でもお構いなしに割り込み、
     TFTのCSをアサートしたまま・`spi0_bus_lock`のmutexを握ったままcore1を凍結してしまう
     ことがあり得る。これこそ`sd_spi.c`の`sd_spi_deselect()`コメントが警告する「SDカードが
     バスを完全に手放さない」状態そのものであり、1・2で`multicore_lockout`を追加した箇所
     (`cover_image_show()`、`visit_dir()`)自体が対策のつもりで新たな発火点を増やしていた。
     さらに悪いことに、3で`flash_cache`を強制したことで`flash_disk.c`の
     `flash_disk_diskio_write()`(これも`multicore_lockout`を使う -- フラッシュ書き込み中は
     両コアのXIP実行を止める必要があるため、こちらは元から必要な処理)が**毎曲ごと**に
     呼ばれるようになり、しかも起動時の`flash_disk_init()`が`f_mkfs()`で「1:」ボリュームを
     初回フォーマットする際に何十セクタ分も呼ばれる -- これが起動直後、`visit_dir(0)`が
     一度も呼ばれる前に発火し、ログの「最初のルート一覧からすでに失敗」を説明する。
     **真の修正**: 個別のSPI転送を`spi0_bus_lock()`/`spi0_bus_unlock()`で囲う既存の仕組み
     (`st7735.c`がすでに全ての描画でこれを使っている)を信頼し、複数回のSD操作をまたぐ
     区間は`multicore_lockout`ではなく**この同じmutexをそのまま長く保持する**方式に変更した:
     - `cover_image_show()`と`visit_dir()`: `multicore_lockout_start/end_blocking()`を
       `spi0_bus_lock()`/`spi0_bus_unlock()`に置き換え。これだけでcore1は(割り込みでは
       なく)自分自身の次のロック取得箇所で協調的にブロックされるため、転送途中で
       止まる余地が原理的に無い。
     - `flash_disk_diskio_write()`: `multicore_lockout`自体は正当な理由(フラッシュ書き込み
       中のXIP保護)で残すが、その**前に**`spi0_bus_lock()`を取得してから
       `multicore_lockout_start_blocking()`を呼ぶよう変更(終了時は逆順で解放)。こうする
       ことで、ロックアウト割り込みが発火する時点でcore1は必ず「アイドル」か「同じmutexを
       待ってブロック中」のどちらかに限られ、SPI転送の途中で凍結されることがなくなる。
     ホスト側テスト(`test_cover_image.c`)はcore1相当のものが存在しないため、
     `spi0_bus_lock()`/`spi0_bus_unlock()`を単純な no-op としてスタブし直した
     (従来の`pico/multicore.h`シムは不要になったため削除)。

  この一連の調査は、「対症療法(描画間隔を下げる)」→「個別のクリティカルセクション
  (multicore_lockoutの追加)」→「根本原因の除去(flash_cache強制)」と段階的に対策して
  なお直らず、**対策そのものに使っていた同期プリミティブ(multicore_lockout)がこの
  用途には不適切だった**という、一段深い原因にたどり着いて初めて解決に至った
  (と期待される)。教訓: コア間の排他には、すでにその資源専用に存在する協調的な
  mutex(`spi0_bus_lock`)を一貫して使うべきで、用途の異なる非同期割り込み機構
  (`multicore_lockout`、本来はフラッシュXIP保護専用)を転用すると、意図と逆に
  危険な瞬間を作り出しうる。

  5. ところが4の修正を入れた直後の実機テストで、**エラーにすらならず起動ログがログの
     途中(スレーブ settle window完了直後、最初の`visit_dir(0)`呼び出し付近)で完全に
     停止する**という新しい症状が出た。原因は4で入れた修正そのもの: `visit_dir()`と
     `cover_image_show()`は`spi0_bus_lock()`をスコープ全体で保持するようにしたが、その
     内側で呼ぶ`f_findfirst`/`f_findnext`/`f_open`等のFatFs関数は、結局
     `third_party/.../glue.c`の`disk_read()`等を経由して**同じ`spi0_bus_lock()`を
     さらに1回ずつ取得する**(個々のSDトランザクションごとに)。`spi0_bus_lock.c`の
     mutexは通常の(再入不可の)`mutex_t`だったため、core0が自分自身がすでに保持して
     いる同じmutexへ再度`mutex_enter_blocking()`すると、所有者が自分であっても
     ブロックしたまま永遠に戻ってこない -- これがログが完全に止まった(エラーも出ない)
     理由である。**修正**: `spi0_bus_lock.c`/`spi0_bus_lock.h`を`mutex_t`から
     `recursive_mutex_t`(`pico/mutex.h`)に変更。同じコアからの再入は単にカウントを
     増やすだけで即座に成功し、最も外側の`spi0_bus_unlock()`が呼ばれて初めて本当に
     解放される。別コア(core1)からの競合は従来通りブロックされるため、本来の
     排他動作はそのまま保たれる。`visit_dir()`/`cover_image_show()`側のコードは
     変更不要(ロック関数の実装だけを差し替えれば済む)。

  6. ハングは直ったが、`FR_DISK_ERR`自体は無変化。この時点でユーザーから
     「OLEDに戻しても再現する」という報告があり(後に`vgmplay.ini`の`display`行が
     GUIで削除されていただけで実際にはTFTのままだったと判明したが)、これをきっかけに
     「**ソフトウェアのタイミング制御では一切説明が付かない**」という前提に立ち戻って
     調査し直した。鍵は、起動ログで`FR_DISK_ERR`が**毎回確実に**、`visit_dir(0)`の
     最初の呼び出しから起きている点 -- タイミング次第のレースなら時々は成功するはずで、
     100%再現するのはむしろ「毎回必ず起こる1回限りのイベント」が疑わしい。そこで
     `st7735_init()`(core1がTFT初期化のために**起動につき1回だけ**呼ぶ関数)を
     re-audit したところ、次の行が見つかった:
     ```c
     spi_init(s_spi, ST7735_SPI_BAUD_HZ);
     spi_set_format(s_spi, 8, SPI_CPOL_0, SPI_CPHA_0, SPI_MSB_FIRST);
     ```
     これは「SDカードがすでにSPI0を同じ設定で立ち上げている場合でも無害な再設定」と
     コメントされていた(レジスタの最終的な値は同じになるため)。しかし
     pico-sdkの`spi_init()`の実装を確認すると、`reset_block_num()`/
     `unreset_block_num_wait_blocking()`で**SPI0ペリフェラルブロック自体を
     リセット**している -- これは「設定値が同じだから無害」とは別の話で、
     **リセットという行為そのもの**がSCK/MOSI配線上に一瞬のグリッチを生みうる。
     しかもこの呼び出しは、`main()`がSDカードから`vgmplay.ini`を読み終えた
     直後、`oled_ui_init()`がcore1を起動した瞬間に**必ず・一度だけ**実行される
     ため、`sd_spi.c`の`sd_spi_deselect()`コメントが警告する「MMC/SDCはCS解除後も
     SCLK/DIを聞き続けていることがある」という性質と重なると、SDカードがまだ
     直前のトランザクションの余韻で聞いているところへ、ペリフェラルリセットに
     よる不定なクロック/データがそのまま飛び込み、カードの内部状態を一撃で
     壊してしまう -- これなら「毎回・確実に・最初のアクセスから」失敗する理由が
     完全に説明できる。これまでの`multicore_lockout`→`spi0_bus_lock`→
     `recursive_mutex`という一連の修正は、すべて「2つの当事者が同時にバスへ
     出る」ことを防ぐ排他制御だったが、この不具合は**排他の問題ではなく
     単発のハードウェアリセット**が原因であり、タイミング制御では原理的に
     直らなかった。

     **修正**: `st7735_init()`に`spi0_already_configured`引数を追加し、SDカードの
     マウントが`main()`内でこの呼び出しより前に成功していれば(実機では常にそう)、
     `spi_init()`/`spi_set_format()`/`gpio_set_function()`(SCK・MOSI分)を
     **スキップ**するようにした(CS/DC/RSTのGPIO初期化とパネル自体のリセット・
     コマンドシーケンスは従来通り実行)。SDカードが無い/マウント失敗時のみ
     (`tools/st7735_text_test/`含む)従来通りフルの自己初期化を行う。
     `oled_ui_init()`に`bool sd_spi0_ready`引数を追加し、`main()`の
     `f_mount("0:")`の結果をそのまま渡すよう変更(`oled_ui.c`内の静的変数
     `s_sd_spi0_ready`経由でcore1の`backend_st7735_init()`へ伝達)。

  6の修正後もユーザーの実機テストで**症状が一切改善せず**、しかもユーザー自身が
  重大な手がかりに気づいた: `vgmplay.ini`に`display`キーを一切書いていない
  (GUIでOLEDを選ぶとこのキー自体が省略される)はずなのに、起動ログには
  `display: [player] display = tft`と出ていた。「iniにdisplayが無くてもTFTになって
  いるようだが確認してほしい」という指摘を受け、まず`[player] display =`が
  無ければ確実に`oled`になることをコードで再確認(`s_display_is_tft`はデフォルト
  `false`で、`display`キーの行だけがそれを変更する)。次にビルド日時を起動時に
  出力する仕組み(`printf("build: %s %s\n", __DATE__, __TIME__)`、10秒待機版では
  待機後に出力)を追加し、Google Driveの同期遅延で古いファームウェアを試して
  いないかを切り分け -- ビルド日時は最新と確認できた。続いて`player_config_load()`
  のini解析直後に`s_display_is_tft`等の実際の値を出力する診断ログを追加したところ、
  ユーザーが貼った実際の`vgmplay.ini`(`[player]`に`display`も`flash_cache`も一切
  無く、キー総数は`shuffle/skip_button/preview/preview_seconds/recursive/root_dir/

  `config: 28 setting(s) applied`(キー総数と完全一致 -- `display`行が実際に
  パースされていれば29になるはずで、一致しないことが「displayキーは解析時に
  一度もマッチしていない」ことの動かぬ証拠)と出ているにも関わらず、続けて
  `config: resolved display=tft flash_cache=no`と出力された。つまり、**iniの
  `display`キーが実際に解析された形跡が無いのに、解析関数を抜けた時点で
  `s_display_is_tft`はすでに`true`になっていた**。コード上`s_display_is_tft`を
  変更できる箇所は`display`キーのマッチ節ただ1か所しかないため、ここでようやく
  「排他制御やSPI0まわりの問題では原理的に説明できない、メモリ破壊」を疑った。

  `player_config_autoload()`→`player_config_load()`→`player_config_apply()`という
  入れ子呼び出し(`main()`が一度だけ呼ぶ)の各関数が、`FIL`(FatFsは`FF_FS_TINY=0`
  設定のため512バイトの`FF_MAX_SS`セクタバッファを内蔵しており見た目よりずっと
  大きい)・`DIR`・`FILINFO`(`FF_USE_LFN`有効のため256バイトの長いファイル名
  バッファを内蔵)・`char pick[256]`・`char path[260]`をいずれも**スタックローカル**
  として持っていたことに着目し、`arm-none-eabi-gcc -fstack-usage`で実測したところ
  (2026-10-03):

  | 関数 | スタックフレーム実測値 |
  |---|---|
  | `player_config_apply()` | 184 bytes |
  | `player_config_load()` | 648 bytes |
  | `player_config_autoload()` | 1528 bytes |

  3つは入れ子で呼ばれるため、最深部での合計は**2360 bytes** -- `main()`自身の
  フレームや各呼び出しの戻り先保存などのオーバーヘッドを足す前の時点で、すでに
  core0の2KBスタック予算を超過していた。このオーバーフローが、core0のスタック
  領域のすぐ先にある何らかの静的変数を書き潰しており、たまたまそれが
  `s_display_is_tft`だった、というのが真相だった。これは本プロジェクトが過去に
  一度経験した「core0スタックオーバーフローが隣接メモリ(当時はcore1のスタック)を
  破壊する」バグ(`vgz_inflate.c`のHardFault事例、本ファイル上記参照)と**全く同じ
  クラス**のバグであり、`player_config.c`自体は今回のTFT/カバー画像機能より前から
  存在するコードだったが、`s_display_is_tft`/`s_flash_cache_enabled`という新しい
  静的変数がBSS上のたまたま衝突する位置に追加されたことで、今回初めて
  **行動に影響する形で**顕在化したと考えられる。

  重要な点: 1〜6で行った一連のSPI0バス排他制御・`st7735_init()`の再初期化スキップ
  修正は、**どれ一つとして今回のバグの原因ではなかった**。`display = tft`が
  iniの指定と無関係に常にONになっていた以上、「`display = tft`時のSD/TFTバス
  競合」という前提そのものが毎回誤って成立していただけで、実際にはユーザーの
  カードはOLED運用のつもりだった。とはいえ1〜6の修正(recursive mutexによる
  デッドロック解消、`spi0_bus_lock`の一貫した使用、`st7735_init()`の不要な
  ペリフェラルリセット回避)自体は、実際に`display = tft`を選んだ場合に備えた
  正当な改善であり、無駄ではないためそのまま残している。

  **修正**: `player_config_autoload()`/`player_config_load()`の`FIL`/`DIR`/
  `FILINFO`/`pick`/`path`を、`main.c`の`visit_dir()`で既に確立されていたのと
  同じパターンで`static`に変更(この呼び出し連鎖はcore0から一度だけ、
  再入・並行呼び出しなしで実行されるため安全)。修正後に再度`-fstack-usage`で
  実測したところ、`player_config_load()`は648→40 bytes、`player_config_autoload()`
  は1528→32 bytesまで縮小し、入れ子時の合計は2360→256 bytesとなった
  (`player_config_apply()`の184 bytesは今回変更していない -- 256 bytes自体が
  2KB予算の1/8程度で十分な余裕があるため)。

  併せて追加した診断用の`printf`(ビルド日時、autoload前後の`display`/
  `flash_cache`状態)は、この投稿時点ではまだ`player_config.c`に残っている --
  実機でのこの修正の確認が取れ次第、削除する予定。

  8. スタック修正後も実機で`FatFs error 1`(`Illegal command CMD:17 response
     0x4`)が再現し続け、しかも`display = oled`(TFTのコードを一切通らない)
     でも全く同じセクタ(66048)で同じエラーが出ることが判明 -- これでようやく
     「TFT関連ではない」ことが実機でも確定した。SPIクロックを20MHz→4MHzに、
     コンパイラ最適化を`-O3`→`-Og`に、それぞれ切り分けのために変えてみたが
     どちらも結果は変わらず(同じセクタ・同じエラー)、ソフトウェア側の要因は
     ここで一通り除外できた。この過程でユーザーから鋭い指摘があった:
     「OLED指定時もTFTのCSは触っているか?」。確認すると、`display = oled`
     選択時は`st7735_init()`が一切呼ばれないため、TFTのCS/DC/RST
     (GPIO3/4/5)は`gpio_init`すらされず**フローティングのまま**だった --
     もしTFTモジュールが物理的に繋がったままOLEDでテストしていた場合、CSが
     不定電位でTFTが誤って「選択状態」になり、共有SCK/MOSI線上のSD宛て
     トラフィックをTFTも一緒に聞いてしまう可能性がある。防御的に、OLED選択時
     もTFT CSを明示的にGPIO出力・HIGH固定する修正を`oled_ui_init()`に追加した
     (`src/master/src/oled_ui.c`)。

     **最終的な解決(2026-10-04)**: この防御的ソフト修正だけでは実機の症状は
     変わらなかったが、ユーザーが**TFT CS(GPIO3)・SD MISO(GPIO16)・SD CS
     (GPIO17)それぞれに10kΩのプルアップ抵抗(3.3Vへ、Pico 36番ピン(3V3(OUT))
     から共有給電)を追加**したところ、読み込み・再生とも正常動作するように
     なった。つまり最終的な原因は、SD/TFT共有バス上で**どちらのチップも明示的に
     駆動していない瞬間の電位がフローティングになっていたこと**という、
     ソフトウェアでは原理的に直せない電気的な問題だった。これまでの
     1〜8の一連の修正(recursive mutexによるデッドロック解消、`spi0_bus_lock`の
     一貫した使用、`st7735_init()`の不要なペリフェラルリセット回避、
     core0スタックオーバーフロー修正、OLED時のTFT CS固定)はいずれも
     正当な改善として残っているが、どれも最後のプルアップ抵抗が無ければ
     この特定の症状は解決しなかった。

  **実機で動作確認済み、と2026-10-04時点では判断したが、後日(2026-10-05)この
  症状が回路を一切変更せずに再発し、調査を継続することになった。詳細は本節の
  末尾の「最終的な根本原因 (2026-10-05)」を参照。**プルアップ抵抗自体は無駄
  ではなかった(後述の真因に対してノイズマージンを多少広げる効果があった)が、
  それだけでは確実な解決にならなかった。

  **カバー画像のパレット(color type 3)PNG対応 (2026-10-04)**: 上記の解決後、
  実機で実際に使ったレトロゲームのジャケット画像がパレット形式のPNGで、
  従来の「対応形式一覧」から除外され空欄にフォールバックしていた
  (`PNG color type 3 not supported`)。パレット形式はレトロゲーム素材で
  特によく使われるため、`cover_image.c`にIHDRとIDATの間の`PLTE`チャンク
  (最大256色×RGB3バイト、`static uint8_t s_png_palette[256*3]`)を読み取る
  処理を追加し、`png_blit_row()`で各ピクセルの値(実サンプル値ではなく1バイトの
  パレットインデックス)をこのテーブルで色に変換するよう対応した。
  スキャンラインのフィルタ復元やチャンク解析の既存の枠組みはそのまま再利用
  できた(インデックスはbpp=1として扱えば十分)。ホストテスト
  (`tools/host_tests/test_cover_image.c`)のパレット画像フィクスチャも、
  単色の「対応していないことを確認するテスト」から、上下2色
  (インデックス0=黒、インデックス1=白)でPLTEルックアップが実際に機能して
  いることを確認するテストに置き換えた。

  **最終的な根本原因 (2026-10-05)**: プルアップ抵抗の追加後も`FR_DISK_ERR`が
  回路変更なしに再発し、`display = oled`(TFTのコードを一切通らない)でも
  同一の症状が出ることから、これまでのTFT/SPI0共有という前提そのものを
  疑い直した。本番ファームでの切り分け(`config: disk_read`の生ログ、
  `oled_ui_init()`と`slave_bus_init()`の間に挿入した中間チェックポイント)で、
  **失敗が発生するタイミングがテストごとに変わる**(ある回は`slave_bus_init()`
  直後から、別の回は長い"keepalive"成功の後で初めて)ことが分かり、単一の
  決定的なコードパスではなく**タイミング依存の現象**だと判断した。

  ここで専用の単体テストツール`tools/sd_display_interleave_test/`を新規作成し、
  本番ファームの複雑さ(設定解析・スレーブバス・settle windowなど)を排除して
  1つの疑問だけを検証できるようにした:
  1. **1コアで「描画→SD読込」を順番に繰り返す**(OLED版・TFT版とも): 数千回
     失敗ゼロ → 単純な交互アクセス自体は無関係。
  2. **core1を実際に起動し、非同期・無停止で描画し続けながらcore0がSDを
     叩き続ける**(真の並行アクセス): 数分間、OLED版・TFT版とも失敗ゼロ →
     TFT/SPI0の共有自体も無関係と確定(これでTFT関連の調査は完全に無罪放免
     となった)。
  3. **さらにSPI1でのスレーブボード通信(`slave_bus_reset()`)もループに追加**:
     **OLED版・TFT版ともほぼ即座に、かつ一貫して失敗するようになった**
     (`sd_ok=0`のまま`sd_fail`だけが増え続ける)。表示デバイスの種類に関係なく
     再現したことから、**TFTとは完全に無関係**で、SPI1の通信そのものがSPI0
     (SDカード)を壊していることが確定した。

  SPI1はGPIO10(SCK)/GPIO11(MOSI)に加え、既定のチップ配置で**GPIO12/13/14/15
  をチップセレクトに使っており、これらはSPI0のGPIO16(MISO)/17(CS)/18(SCK)/
  19(MOSI)と隣接**している(`docs/circuit.md`参照)。この物理的な近さと、
  SPI1が4MHzで駆動されること(`vgm_spi_protocol.h`の`VGM_SPI_BAUD_HZ`)を
  踏まえると、**SPI1の信号の速い立ち上がり/立下りエッジが、隣接するSPI0の
  線へクロストーク(電磁結合)している**という説明が最も筋が通る。

  **修正**: `slave_bus_init()`で、SPI1のSCK/MOSI(GPIO10/11)と、有効な
  全チップのCSピンに対して、`gpio_set_slew_rate(..., GPIO_SLEW_RATE_SLOW)`
  (スルーレート制限)と`gpio_set_drive_strength(..., GPIO_DRIVE_STRENGTH_2MA)`
  (ドライブ強度を最低の2mAに)を適用(`src/master/src/slave_bus.c`)。
  SPI1は短い配線・4MHzという余裕のあるクロックのため、信号品質への実害は
  想定していない。この修正を`tools/sd_display_interleave_test`に適用して
  再テストしたところ、**OLED版・TFT版とも`sd_fail`が0のまま**に戻ったことを
  実機で確認済み。本番ファームにも同じ修正を適用した。

  **これまでの一連の調査(1〜8、プルアップ抵抗を含む)の位置づけ**:
  TFT/SPI0バス共有に関する修正(recursive mutexによるデッドロック解消、
  `spi0_bus_lock`の一貫した使用、`st7735_init()`の不要なペリフェラルリセット
  回避、core0スタックオーバーフロー修正、OLED時のTFT CS固定)は、**今回の
  `FR_DISK_ERR`再発の根本原因ではなかった**が、実際に`display = tft`を選んだ
  場合に備えた正当な改善として引き続き有効であり、無駄ではない。プルアップ
  抵抗(GP3/GPIO16/GPIO17)も、SPI1クロストークに対するノイズマージンを
  多少広げていた可能性があり(フローティング状態や弱い駆動の信号ほどノイズの
  影響を受けやすいため)、完全な解決ではなかったものの無意味ではなかったと
  考えられる。また`sd_card.c`の「illegal commandでも即時再試行する」変更も、
  今回の根本原因ではなかったが、害のない防御的改善として残している。

  調査の過程で作成した`tools/sd_display_interleave_test/`は、今後同種の
  SPI0/SPI1/表示デバイス間の干渉を疑う際の再利用可能な切り分けツールとして
  リポジトリに残している。

  単体テストツールでの修正確認に続き、**本番ファーム(`master.uf2`)でも実機で
  最終確認済み(2026-10-05)**: `recursive = yes`で実際のVGMファイルが見つかり、
  `FR_DISK_ERR`を一切出さずに再生(`[TIME]`が正常に進行)。あわせて見つかった
  2件の別件(`root_dir`/`recursive`の設定による「ファイルが見つからない」、
  TFTバックライト配線)はどちらもソフトウェアとは無関係で、ユーザー側の設定・
  配線修正で解決した。これで2026-10-02から続いた`FR_DISK_ERR`調査は完結した。

- **`display = tft`のflash_cache強制を撤廃 (実機確認済み, 2026-10-06)**: 上記の通り
  `FR_DISK_ERR`の本当の原因はSPI1→SPI0クロストークであり、TFTや`flash_cache`の
  有無とは無関係だったと判明した。ところが`player_config_flash_cache_enabled()`
  の`display = tft`強制(`s_flash_cache_enabled || s_display_is_tft`)は、まだ
  本当の原因が分かっていなかった時点の「TFT描画とSD連続ストリーミングがバスを
  奪い合う」という(今では誤りと分かった)仮説のために導入したものだった。
  ユーザーから「この強制は本当に必要なのか、試行錯誤の名残ではないか」という
  指摘があり、SPI1クロストーク対策(スルーレート制限)が入った今、強制を外して
  `display = tft` + `flash_cache = no`(SDから曲全体をストリーミング、TFTは
  並行して再描画し続ける)が実機で安定するかを検証することにした。
  `player_config_flash_cache_enabled()`を`return s_flash_cache_enabled;`に戻し
  (`display`との連動を削除)、`main.c`のログ行、`player_config.h`/
  `firmware/vgmplay.ini`のコメント、`tools/config_gui/vgmplay_config_gui.py`の
  対応するOR条件、および両方のテストスイート(`test_player_config.c`の
  n17/n18、`test_vgmplay_config_gui.py`の`test_display_roundtrip_and_tft_validation`)
  を合わせて更新した。**実機で確認済み(2026-10-06)**: `display = tft` +
  `flash_cache = no`の組み合わせで複数曲を再生し、`FR_DISK_ERR`は一度も発生せず、
  TFTの画面表示も正常だった。SPI1クロストーク対策だけで`FR_DISK_ERR`は再発しない
  ことが確定したため、flash_cache強制は不要と判断し撤廃を確定した。`flash_cache`
  機能自体は(任意設定の)デバッグ/用途限定機能として引き続き残している
  (SDカードのSPIバスを完全に空けたい場合などに有効)。万一将来また同種の問題が
  出た場合は、`player_config_flash_cache_enabled()`を
  `s_flash_cache_enabled || s_display_is_tft`に戻すだけで元の(安全側の)挙動に
  復帰できる。

実機(RP2040ボード)がない状態でも検証できる範囲はホスト側でテスト済みです:

- `tools/host_tests/`: `src/master/src/vgm_player.c`/`vgz_inflate.c` を実ソースのまま
  (FatFsとpico-sdkの薄いstdioシム経由で)ホストでビルドし、合成VGM/gzipファイルに対して実行。
  ヘッダ解析・コマンド振り分け(YM2151/YM2203/SCCの`0xD2`領域デコード、Sega PCMの`0xC0`register
  writeとPCMデータブロックのアップロードを含む)・未対応コマンドの正しい読み飛ばし
  (libvgmの長さテーブルに合わせて修正した`0x40-0x4E`範囲を含む)・データブロックスキップ・
  ループポイントへのシーク・gzipストリーミング展開(32KB窓の折り返しを含む)を確認済み。
  `test_vgm_segapcm_block.c`はSega PCMのROMイメージブロック(0x67 type=0x80)処理を検証:
  先頭8バイトヘッダの除去、開始アドレスへの`UPLOAD_RESET`シーク、`size-8`バイトのデータ転送、
  転送後もパーサがストリーム同期を保つこと
- `tools/probes/`: ymfm (YM2612/YM2413/YM2151/YM2203) の実際の出力サンプルレートと振幅レンジを
  ホストで実測し、各`chip_*.cpp`のスケーリング定数の根拠にしている
- `tools/host_tests/test_segapcm_render.c`: `chip_segapcm.c`はymfmに依存しない素のCコードなので、
  ホストで直接ビルド+実行し、アドレスの16.8固定小数点アキュムレータの進み方・サンプル読み出し・
  チャンネル無効化が仕様通りであることを確認済み

一方、RP2040実機での動作(SPIタイミング、PWM音質、FM音源勢のリアルタイム性能、Sega PCMアップロード
の実測所要時間など)は未検証です。9つのファームウェア(`master`と8スレーブ)はいずれも実際に
arm-none-eabi-gccでクロスビルドが通ることを確認済みです。

## 7. ビルド方法

```sh
# pico-sdkはこのリポジトリの外(Google Drive同期対象外の場所)に置く
git clone --branch 2.1.1 https://github.com/raspberrypi/pico-sdk.git ~/pico-sdk
cd ~/pico-sdk && git submodule update --init --depth 1 lib/tinyusb lib/mbedtls lib/cyw43-driver lib/lwip lib/btstack lib/cmsis

export PICO_SDK_PATH=~/pico-sdk
cmake -S . -B ~/build-vgmplay   # ビルド出力もリポジトリ外に置く
cmake --build ~/build-vgmplay -j$(nproc)
```

生成物: `~/build-vgmplay/src/master/master.uf2`,
`~/build-vgmplay/src/slave_sn76489/slave_sn76489.uf2`,
`~/build-vgmplay/src/slave_ym2612/slave_ym2612.uf2`,
`~/build-vgmplay/src/slave_ay8910/slave_ay8910.uf2`,
`~/build-vgmplay/src/slave_ym2413/slave_ym2413.uf2`,
`~/build-vgmplay/src/slave_ym2151/slave_ym2151.uf2`,
`~/build-vgmplay/src/slave_ym2203/slave_ym2203.uf2`,
`~/build-vgmplay/src/slave_scc/slave_scc.uf2`,
`~/build-vgmplay/src/slave_segapcm/slave_segapcm.uf2`。各Pico/RP2040-ZeroをBOOTSELボタンを押しながら
USB接続してUF2ドライブとしてマウントし、対応する`.uf2`をコピーすれば書き込み完了です。

SDカードのルート直下に`.vgm`/`.vgz`ファイルを置いてください。ファイル名を大文字小文字を区別せず
ソートした順(`src/master/src/main.c`で列挙後に`qsort`)に再生し、末尾まで行くと最初の曲に戻ります。
数値順に並べたい場合はファイル名の番号をゼロ埋め(`01`,`02`,…`10`)してください(単純な文字列比較の
ため`10`は`2`より前になります)。1周あたり最大`MAX_FILES`件(既定256)/名前バッファ`NAMES_BUF_SZ`
(既定12KB)まで。

## 8. ログの確認方法

スレーブは`stdio`を**UARTとUSB CDCの両方**で有効化しています(各`CMakeLists.txt`の
`pico_enable_stdio_uart`/`pico_enable_stdio_usb`)。**masterはUSB CDCのみ**です — GPIO0/1を
OLEDステータス表示のI2C0に転用したため`pico_enable_stdio_uart(master 0)`にしてあります
(`docs/circuit.md`1章)。書き込み・給電に使うUSBケーブルをそのまま挿した状態で、以下で
ログが見られます。

「音が出ない」等、SPI疎通そのものを疑う場合はまず`tools/spi_bringup_test/`
(`firmware/debug/spi_bringup_test_master.uf2`/`spi_bringup_test_slave.uf2`)を試してください。
VGM解析・チップエミュレーション・マルチコア連携を全部取り除いた最小構成で、マスターが送った
生バイトとスレーブが受信した生バイトをそのまま突き合わせられます(詳細は`firmware/debug/README.md`)。

### 8.1 master

**常時ログ**: 起動時のバナー、SDマウント成否、再生中のファイル名、vgz展開エラー、VGMパース
エラーなど(`src/master/src/main.c`と`vgm_player.c`のprintf呼び出し)。

**OLED (任意)**: SSD1306 (I2C0, GPIO0 SDA / GPIO1 SCL) を繋ぐと、再生中のファイル名・経過時間
(MM:SS、ループをまたいでも加算)・使用チップ名を表示します。描画は core1 が担当し、全画面転送
(約23ms)を core0 の再生タイミングから切り離しています。配線と仕様は `docs/circuit.md` 1.1 章、
実装は `src/master/src/oled_ui.c` / `ssd1306.c`。パネルが無い/ACKしない場合は自動で無効化され、
再生には影響しません。

**詳細ログ(オプトイン)**: `VGM_MASTER_VERBOSE_LOG`というCMakeオプションで、VGMファイルから
読み取った生の値(`[VGM ] 0x50 dd=0x9F`のように、コマンドとその引数バイト)と、実際にSPIへ
送信した値(`[SPI ] cs=GPIO12 opcode=0x02 reg=0x00 data=0x9F`のように、宛先CS・オペコード・
reg・data)を1コマンドごとに出せます。スレーブ側の`VGM_SLAVE_VERBOSE_LOG`ログと突き合わせれば、
「VGM解析」「SPI送信(マスター)」「SPI受信(スレーブ)」のどの段階で値が変わってしまっているかを
切り分けられます。スレーブ側と同様、大量のログ出力が`wait_samples()`のタイミングを乱しうるので
デバッグ専用です。

```sh
cmake -S . -B ~/build-vgmplay-verbose -DVGM_MASTER_VERBOSE_LOG=ON
cmake --build ~/build-vgmplay-verbose --target master
```

**USB CDC (追加配線不要、推奨)**

書き込みに使うUSBケーブルをPCに挿したまま、シリアルターミナルで開くだけです。

```sh
# Linux/ChromeOS: 認識されたデバイスを確認 (例: /dev/ttyACM0)
ls /dev/ttyACM*
screen /dev/ttyACM0    # 抜けるには Ctrl-A, K, Y
# または
picocom /dev/ttyACM0
```

Windows/macOSでは、デバイスマネージャ/`ls /dev/tty.usbmodem*`等でポート名を確認し、PuTTYや
`screen`で開いてください。ボーレートはUSB CDCでは実質無視されるので適当な値(例: 115200)で
構いません。

**UART (デフォルトで無効)**

GPIO0/1 は OLED 用 I2C0 に割り当てているため、master の UART ログはビルドで無効化しています
(`src/master/CMakeLists.txt` の `pico_enable_stdio_uart(master 0)`)。OLED を使わず物理 UART で
ログを取りたい場合は、そこを `1` に戻し、`src/master/src/main.c` の `oled_ui_init()` 呼び出しを
外す(または OLED を接続しなければ自動で無効化されるのでそのままでも可)。その上で
GPIO0(TX)/GPIO1(RX)/GND を USB-TTL シリアル変換アダプタ(3.3V対応)の RX/TX/GND にクロス接続
(master の TX→アダプタの RX)し、115200bps 8N1 で開きます。master は送信専用なので TX と GND
だけでもログは見られます。

### 8.2 スレーブ (RP2040-Zero / Pico)

スレーブも同じUSB CDC/UARTの仕組みでログを見られますが、masterと違い**core1が44.1kHz〜166kHz
というシビアなリアルタイムループでPWM出力を生成している**ため、ログの出し方に制約があります。

- **常時ログ(デフォルトで出る、音声への影響なし)**: 起動時のバナー(`[SN76489] audio engine
  running at 44100 Hz`のような1行)、`RESET`、`MUTE`。これらは曲の切り替わり時などごく低頻度
  にしか発生しないので、printfのブロッキング時間が音声のタイミングを乱す心配はほぼありません。
- **詳細ログ(オプトイン、音声が乱れる前提のデバッグ専用)**: レジスタ書き込み1件ごとに1行
  ログを出す`VGM_SLAVE_VERBOSE_LOG`というCMakeオプションを用意しています。マスターから来る
  SPIフレームを本当に受け取れているか、値は正しいかを配線確認したいときに使ってください。
  ただしUART/USB CDCへの出力は1行あたり数百µs〜数msかかるため、**有効にすると音声のタイミングが
  確実に乱れます**(音を聴く用途では無効のまま使ってください)。Sega PCMのROMアップロードだけは
  1バイトごとではなく4096バイトごとの進捗ログになります(全バイト出すと1曲で数万行になるため)。

```sh
# 詳細ログを有効にした別ビルドを用意する例 (通常ビルドとは別ディレクトリにするのが無難)
export PICO_SDK_PATH=~/pico-sdk
cmake -S . -B ~/build-vgmplay-verbose -DVGM_SLAVE_VERBOSE_LOG=ON
cmake --build ~/build-vgmplay-verbose --target slave_sn76489   # 確認したいスレーブだけでよい
# できた slave_sn76489.uf2 を書き込んで配線確認 → 終わったら firmware/ の通常版に戻す
```

`firmware/`に置いてある`.uf2`はすべて`VGM_SLAVE_VERBOSE_LOG=OFF`(デフォルト)でビルドしたもの
です。詳細ログ版は配線確認用の一時的なビルドとして使い、本番の書き込みには使わないでください。

**注意**: どちらの方法でも、電源投入直後の最初の数行(起動バナーなど)はターミナルの接続タイミング
によっては表示されないことがあります。メインループは曲の再生ごとにログを出すので、そのまま
見ていれば追いつけます。

## 9. 未実装・今後の拡張候補

- スレーブ側のクロックプリセットをVGMヘッダの実クロックに完全追従させる(現状は全チップとも
  2〜3値程度のプリセットから一番近いものを選ぶだけ。2026-08-27時点でプリセット選択自体は
  全チップで機能するようになったが、プリセットに無い任意のHz値には対応しない)
- 汎用DACストリーム制御 (0x90-0x95) の対応 (YM2612 DAC の 0x8n 方式は2026-09-07に対応済み、§5参照。
  0x90-0x95 のセットアップ駆動型ストリームは未対応)
- Sega PCMで**リベース後もなお192KBを超えてスパンする曲**への対応(2026-08-30のROMウィンドウ
  リベースで、512KB空間のどこにあっても使用スパンが192KB未満なら鳴るようになった。それでも
  足りない曲はPico 2ビルドで`SEGAPCM_ROM_BUDGET`を拡大するのが次の手 — RP2350は520KB RAM)、および
  アップロードの高速化(現状1バイト/フレーム。CSを張ったまま複数バイトを連続送信するバルク転送
  モードを別途設ければ、数百ms〜数秒のロード待ちを大幅に短縮できる見込み)
- SCC+/052539の非共有波形モード対応
- 一時停止ボタン(現状スキップボタンのみ実装。`src/master/src/main.c`にpause実装の余地あり)
- サンプルクロックのハード同期 (design doc §5の拡張案: 44.1kHz基準パルスをGPIOで全スレーブへ配線)
- SPIフレームへのCRC/パリティ追加 (現状ノーチェック。ノイズの多い配線では要検討)
- **1スレーブへの複数チップ統合**(軽量チップ同士に限る、例: SN76489+AY-3-8910)。
  提案段階・未実装。設計案は[docs/multi-chip-slave-design.md](multi-chip-slave-design.md)参照
