# 回路構成

master (Raspberry Pi Pico) 1台 + slave (RP2040-Zero) 最大8台(+ 任意でSN76489の2台目)+
アナログミキサーの実体配線図。[VGM_multi_MCU_design.md](../VGM_multi_MCU_design.md) の構成方針を
そのまま実装したもの。

以前 GPIO0/1 は UART デバッグログ (TX/RX) に使っていましたが、ログは書き込み用USBケーブル経由の
USB CDC でそのまま見られる ([design-notes.md 8.1](design-notes.md#81-master)) ため、GPIO0/1 は
OLED 用の I2C0 に転用しました (`src/master/CMakeLists.txt` の `pico_enable_stdio_uart(master 0)`)。
物理 UART でもログを取りたい場合の戻し方は design-notes.md 8.1 を参照。

チップ⇔CS番号の対応、および各チップの有効/無効は **SDカードルートの `vgmplay.ini`** で
再ビルドなしに変更できます(次項 1.2)。既定値は `src/master/src/slave_bus.c` 冒頭のテーブル。
使わないチップを無効にすれば、そのVGMコマンドは静かに無視され、CS用GPIOも解放されます
(8スレーブ全部を同時に組む必要はなく、実際に使うVGMファイルが必要とするチップの分だけで十分)。
ログの見方は [design-notes.md](design-notes.md#8-ログの確認方法)参照。

### 1.1 OLED ステータス表示 (SSD1306, 任意)

再生中のファイル名・経過時間・使用チップ名を 128x64 の SSD1306 (I2C) に表示します。無くても
再生には一切影響しません (起動時に ACK が無ければ自動で無効化)。

| SSD1306 ピン | 接続先 (Pico) | 物理ピン番号 |
|---|---|---|
| GND | GND | 3番 (GPIO0/1 の隣) |
| VCC | 3V3(OUT) | 36番 |
| SCL | GPIO1 | 2番 |
| SDA | GPIO0 | 1番 |

- I2C アドレスは `0x3C` 前提 (`src/master/src/oled_ui.c` の `OLED_ADDR`)。`0x3D` の個体は書き換え。
- クロックは 400kHz。多くのモジュールは基板上に 4.7kΩ プルアップを持つのでそのままで動きます。
  無ければ SDA/SCL を 3V3 へ 4.7k〜10k で個別にプルアップ (ファーム側でも内蔵プルアップを有効化
  していますが弱いため)。
- 描画は **core1** が担当し、約23msかかる全画面転送を core0 の `wait_samples()` タイミングから
  切り離しています (再生テンポに影響させないため)。表示の更新は約150ms間隔。
- 経過時間はループ地点をまたいでも巻き戻らず加算され続けます (`vgm_player_elapsed_seconds()`)。

### 1.1b TFT ステータス表示 (ST7735 / ILI9341 / ST7796, 任意, OLEDの代替)

`[player] tft_panel`(既定`st7735`)で駆動するコントローラを選べます。3機種ともピン
(CS=GPIO3 / DC=GPIO4 / RST=GPIO5、SCK=GPIO18 / MOSI=GPIO19)と配線は同じです。

| `tft_panel` | 解像度(縦持ち) | 描画方式 | カバーアート領域 | テキスト(5x7 フォント) |
|---|---|---|---|---|
| `st7735`(既定) | 128x160 | 全画面フレームバッファ(約40KB) | 上部128x96 | 1倍、21列、8行 |
| `ili9341` | 240x320 | 16pxバンド転送(フレームバッファなし) | 上部240x160 | 2倍、20列、10行 |
| `st7796` | 320x480 | 16pxバンド転送(フレームバッファなし) | 上部320x240 | 2倍、26列、15行 |

- 大画面パネルのSPI転送は`TFT_PANEL_SPI_HZ`(既定でSDカードと同じ20MHz)で行います。
  データシート上の書き込みサイクル上限(約66ns、約15MHz)より保守的に見えますが、
  同じSPIバスをSDカードと共有しながらST7796を40MHz(さらに62.5MHzの例も)、ILI9341を
  26MHzで安定動作させている他プロジェクトの実績(2026-10-07、他セッションへの問い合わせで
  確認)があるため、20MHzのままにしています。
- 大画面パネルの初期化シーケンスは、ゲイン/パワー系コマンド(E0/E1/E8/C0-C5等)もコマンド
  セット2アンロック(0xF0)も反転コマンド(0x20/0x21)も送らない最小構成です
  (`tft_big.c`)。これは実機でST7796(・一部ILI9341)を動かしている他プロジェクト2件への
  問い合わせで得た、独立に一致する知見に基づきます(2026-10-07)。この2件はいずれも
  横長(ランドスケープ)配線での実績で、このプロジェクトは縦長(ポートレート)で使うため
MADCTL(`ILI9341_MADCTL`/`ST7796_MADCTL`、既定`0x48`)の値は当初未確認だったが、**ST7796・
  ILI9341ともこの既定値のまま実機で画面全体に正しく表示されることを確認済み
  (ST7796: 2026-10-07、ILI9341: 2026-10-08)**。行・列が入れ替わる/上下左右が反転する場合は
  MVビットを立てずにMY/MX/BGR(0x08/0x48/0x88/0xC8)を試してください。色だけが赤青入れ替わって
  見える(位置はずれない)場合はMADCTLのBGRビット(0x08)が逆です -- 反転コマンド
  (`ST7796_INVERT`)の出番ではありません。

  ILI9341の実機確認では、配線(ピンヘッダをピンソケットへ直挿し -- ジャンパ線ですらない)の
  接触不良で何も映らない/表示が崩れる状態が再現し、挿し直すと正常に戻るという、かなり
  デリケートな個体差があった(同じ配線でST7735は終始問題なく表示できていたため、マスター側
  ではなくILI9341モジュール/コネクタ側の接触の問題だった)。大画面パネルで「全く映らない」
  「表示が斜めに崩れる」といった症状が出たら、ソフトウェアより先に配線の挿し直しを疑うと良い。

`vgmplay.ini`の`[player] display = tft`にすると、OLED(I2C0)の代わりにSPI接続のST7735
(128x160が前提、`src/master/src/st7735.h`)にステータスを表示します。表示内容・core1担当
という設計はOLEDと同じで、`src/master/src/oled_ui.c`が両者を共通のインターフェース経由で
切り替えています(更新間隔はバックエンドごとに個別設定、下記参照)。実機確認済み
(2026-10-02、SDカード上の実VGMファイル再生とTFT表示を同時に確認)。

| ST7735 ピン | 接続先 (Pico) | 備考 |
|---|---|---|
| GND | GND | |
| VCC | 3V3(OUT) | |
| SCL(SCK) | GPIO18 | **SDカードのSPI0 SCKと共用**(同じ物理線) |
| SDA(MOSI) | GPIO19 | **SDカードのSPI0 MOSIと共用**(同上) |
| CS | GPIO3 | このパネル専用のソフトウェア制御CS |
| DC | GPIO4 | データ/コマンド切替 |
| RST | GPIO5 | リセット |
| BL(バックライト) | 3V3 | 通常は常時点灯で問題なし(GPIO制御は今のところ未実装) |
| MISO | 未接続 | このドライバは書き込み専用(読み出しコマンドを使わない) |

- **SDカードとSPI0の物理線(SCK/MOSI)を共有**します。CSが別なので通常のSPIマルチデバイス
  配線そのものですが、ソフトウェア側にも排他制御(`src/master/src/spi0_bus_lock.h`、
  core0のSDアクセスとcore1のTFT描画が同時にバスへ出ないようミューテックスで直列化)が
  入っています。それでも実機では、SDカード側がCS解除後もMISOを完全には手放さない個体が
  あること(`third_party/.../sd_spi.c`の`sd_spi_deselect()`のコメント参照)が原因で、
  TFTの描画(SPI0トラフィック)がSDの読み込みの合間に割り込んで干渉し、SDの読み込みが
  `FR_DISK_ERR`で失敗する不具合が実機で見つかった(2026-10-02)。対策は3段構え:
  (1) TFTの再描画間隔をOLEDの150msより大幅に下げてある(既定500ms、`oled_ui.c`の
  `display_backend_t.redraw_ms`)。(2) ~~`display = tft`にすると`[player] flash_cache`が
  (このキー自体の設定に関わらず)強制的に有効になる~~ -- 曲の再生中はSDカードから
  延々とVGMデータを読み続けるため、たとえ描画間隔を下げても衝突の機会が曲の長さ分だけ
  残ってしまうという理屈だった(`player_config_flash_cache_enabled()`参照)。**この強制は
  2026-10-06に撤廃**(後述の本当の原因=SPI1クロストークがこの理屈と無関係に
  見つかったため、`display = tft` + `flash_cache = no`で実機確認 -- 複数曲の
  再生で`FR_DISK_ERR`は再発せず、TFT表示も正常だった。`flash_cache`機能自体は
  デバッグ/用途限定の任意設定として残している。[design-notes.md](design-notes.md)参照)。
  (3) フォルダの一覧取得処理とカバー画像デコード(1.1c参照)、および`flash_cache`自体の
  コピー処理(`flash_disk.c`)という、複数回に分かれたSD/フラッシュ操作をまたぐ区間は、
  `st7735.c`がTFTへの個々の書き込みで使っているのと**同じ`spi0_bus_lock()`ミューテックス**
  (`recursive_mutex_t` -- 同じコアからの入れ子取得も許す。SD読み込み自体が内部で1回ずつ
  この同じロックを取り直すため、再入不可の普通のmutexだと自分自身を待って永久に止まって
  しまう)を、その区間ずっと保持することでcore1のTFT描画を協調的に待たせます(詳しい
  経緯・切り分けの過程は[design-notes.md](design-notes.md)参照 -- 当初試した
  `multicore_lockout`による強制停止は、core1がSPI転送の途中でも非同期割り込みで
  凍結してしまいうるため、かえってバスを壊れた状態のまま止める危険があり不採用)。
  (4) **`st7735_init()`(core1が起動時に一度だけ呼ぶ)は、SDカードがすでにSPI0を
  同じ設定で立ち上げ済みのときは`spi_init()`/`spi_set_format()`を呼び直しません**
  -- レジスタの最終値は同じでも、pico-sdkの`spi_init()`は内部でSPI0ペリフェラル
  自体をリセットするため、SDカードの直前のトランザクション直後にこれを呼ぶと
  SCK/MOSI線に一瞬のグリッチが入り、(1)〜(3)のような排他制御では防げない
  一撃でSDカードを壊れた状態にしてしまうことが判明したためです(2026-10-02)。

  **(1)〜(4)はいずれも正当な改善ですが、実際にユーザーの実機で再現していた
  `FR_DISK_ERR`の原因ではありませんでした**(2026-10-03〜05の調査で判明)。
  途中、`player_config.c`の設定読み込み処理のcore0スタックオーバーフローが
  一度「真の原因」に見えたが(詳細は[design-notes.md](design-notes.md))、
  修正後も症状が再発し、さらに`display = oled`(TFTを一切使わない)でも
  同じ症状が出ることが最終的に分かった。**本当の原因はTFT/SPI0とは無関係**で、
  チップのスレーブボードと通信するSPI1(GPIO10/11、CS=GPIO12/13/14/15/20/21/
  22/26/27)の信号が、物理的に隣接するSPI0(GPIO16-19、SDカード)へクロス
  トークしていたことだった -- 専用の単体テスト`tools/sd_display_interleave_test/`
  で、TFT/SPI0共有を完全に除外したうえでSPI1のスレーブ通信だけを加えると
  即座に再現することを確認した。**修正**: `slave_bus_init()`でSPI1のSCK/MOSI
  と全チップのCSピンに`gpio_set_slew_rate(GPIO_SLEW_RATE_SLOW)`+
  `gpio_set_drive_strength(GPIO_DRIVE_STRENGTH_2MA)`を適用(`slave_bus.c`)。
  (1)(3)(4)は、実際に`display = tft`を選んだ場合に備えて有効なままにしている
  ((2)のflash_cache強制のみ上記の通り2026-10-06に撤廃、実機確認済み)。詳しい経緯は
  [design-notes.md](design-notes.md)参照。

  さらに速い更新間隔が必要になった場合は、
  MISO(GPIO16)への10kΩ程度の
  プルアップ抵抗(3V3へ)を試すか、TFTをRP2040のPIOで完全に独立したSPIバスに載せる
  設計への変更を検討してください。
- ボーレートはSDカードと同じ20MHz固定(`hw_config.c`と揃えてあり、パネル用に切り替えません --
  切り替えて戻し忘れると次のSDアクセスが誤ったクロックで走ってしまうため)。
- このパネルは書き込み専用配線(MISO未使用)が一般的なため、OLEDのI2C ACKのような
  「本当に配線されているか」の検出ができません -- 何も配線していなくても初期化は「成功」した
  ように振る舞います(`oled_ui_answered()`は常にtrueになる、`st7735_init()`のコメント参照)。
- 安価なST7735モジュールは「タブの色」によってRAMオフセットやRGB/BGRの並びが微妙に異なります。
  縁に黒帯が出る、または赤と青が入れ替わって見える場合は`src/master/src/st7735.h`の
  `ST7735_XSTART`/`ST7735_YSTART`/`ST7735_MADCTL`を調整してください(コメントに詳細)。
- CS/DC/RSTのGPIO番号は現時点では`vgmplay.ini`で変更できません(固定、`oled_ui.c`の
  `TFT_CS_GPIO`等)。配線の都合で別のGPIOが必要になったら対応します。

#### 1.1c フォルダのカバー画像表示 (JPEG/PNG, `display = tft`限定)

`display = tft`のとき、VGMファイルと同じフォルダに`.jpg`/`.jpeg`/`.png`画像を1枚置いておくと、
そのフォルダに入った時(再生中の全曲を通して)1回だけ、TFT画面の上部96px(`src/master/src/
st7735.h`の`COVER_AREA_H`)に表示します。下部の64px(文字情報: 曲名・経過時間・チップ一覧)は
従来通りの位置を保ちます。フォルダ内に複数の画像があるときはファイル名順で最初の1枚を使用
(`sn76489`等のチップセクションと同じ大文字小文字無視)。再生中は毎フレーム再描画されず(画像の
デコードは1回だけ)、曲送り時にSDカードへアクセスする頻度を不必要に増やしません。

- 対応形式: ベースラインJPEG(`third_party/tjpgd`、ChaN氏のTJpgDec)、PNG(8bit深度、
  非インターレース、グレースケール/RGB/RGBA/パレット(color type 3、PLTEチャンクを
  読んでインデックスをRGBに変換、1/2/4bit/pixelのビット詰めにも対応 -- 小さい
  パレットは8bit未満に詰められることが多いため) -- レトロゲームのジャケット画像は
  パレット形式が多いため対応しました(2026-10-04/05)。16bit深度・Adam7インター
  レース・パレット以外でのビット深度8未満のみ非対応で、デコード失敗として扱い
  空欄にフォールバック、クラッシュしない)。
- 画面幅(128px)に合わせて縮小表示(アスペクト比は維持、拡大はしない)。横に長い画像は
  上下に余白ができ(レターボックス)、逆に幅縮小後もなお縦に長い画像は表示エリアの上下が
  見切れます(「画面幅に合わせる」を優先する仕様)。
- デコードはcore0(再生ループ)で行われますが、SDカードから何度にも分けて読み込む
  処理がcore1のTFT描画(SPI0)と衝突しないよう、デコード中は`spi0_bus_lock()`を
  ずっと保持してcore1の描画を協調的に待たせます(フォルダ一覧取得処理も同様 -- 実機で
  見つかった`FR_DISK_ERR`不具合への対策、1.1b参照)。
- 詳しい設計判断・実装の経緯(ホスト側テストで発見したPNGデコードのバグ等)は
  [design-notes.md](design-notes.md)参照。

### 1.2 設定ファイル `vgmplay.ini` (任意)

SDカードのルート(.vgm/.vgz と同じ場所)に `vgmplay.ini` を置くと、**再ビルドなしで**チップごとの
有効/無効と CS ピンの GPIO 番号を変更できます。適用結果は起動時に USB CDC / UART ログへ出ます
(`slave bus: SN76489 cs=GPIO12 …`)。すぐ使えるひな形が `firmware/vgmplay.ini` にあります。

**ファイル名**: まず `vgmplay.ini` を探し、無ければ `vgmplay*.ini` にマッチする最初のファイル
(名前順、大小無視)を読みます。SDカードごとに搭載チップに合わせた設定を作るとき、
`vgmplay_scc.ini` `vgmplay_outrun.ini` のように名前で区別できて分かりやすいためです。
`vgmplay*.ini` が1つも無ければ `src/master/src/slave_bus.c` の既定値を使います。
(`vgmplay.ini` と `vgmplay_xxx.ini` の両方があるときは `vgmplay.ini` が優先。)

```ini
; チップ1種につき1セクション。キーは大文字小文字を区別しない。
[sn76489]
enabled = yes        ; yes/no/1/0/on/off/true/false
cs      = 12          ; このスレーブの CS を配線したマスター側 GPIO (0-28)
gap     = 40          ; 任意: 1バイトごとの CS パルス間隔 [µs](バイト欠落時に増やす)

[ym2151]
enabled = no          ; 無効にするとその VGM コマンドは無視され、CS用GPIOも解放
```

- `enabled = no` にしたチップ(またはそもそもスレーブを用意していないチップ)を**使う VGM/VGZ は
  再生されず自動でスキップ**されます(そのパートだけ欠けた状態で鳴らすのではなく、曲ごと飛ばす)。
  スキップ時は USB CDC ログに `skipping <名前> -- needs disabled/absent chip(s): <チップ名>` が出ます。
  カード内の全曲がスキップ対象だと `No playable songs` を表示して数秒おきに再スキャンします。

- セクション名は `-` `_` 空白と大小を無視: `[AY-3-8910]` `[ay8910]` `[Sega PCM]` はいずれも可。
  使える名前: `sn76489` `ym2413` `ym2612` `ay8910`(=`ay-3-8910`)`ym2151` `ym2203`
  `scc`(=`k051649`)`segapcm`。
- `;` または `#` で始まる行はコメント。行末コメントも可。
- `gap = 0` は **バースト転送**(3バイトを1回のCSで連続送信、バイトごとのパルス/待ちなし)。
  1フレームが約8倍速くなり、書き込みの密な曲でも master が追いつきます。ただし連続3バイトを
  確実にクロックインできる配線でのみ安全(初期のブリングアップ基板ではバイト2/3が落ちたため
  既定はバイトごとパルス)。パートがもたつく場合に試し、音の潰れ/ノイズが出たら戻してください。
- CS を `0-1`(OLED)、スキップボタンのGPIO(既定`2`、`[player] skip_button`で変更可 --
  警告は変更後のGPIOに追随します)、`10-11`(スレーブバス)、`16-19`(SD)に割り当てると
  警告ログを出します(動作は続行)。範囲外(29以上)の値は無視。
- 書き換えたら SD を挿し直して電源再投入。
- チップごとの設定とは別に、`[player]`セクションで曲送りボタンのGPIO変更(`skip_button`)、
  試聴モード(`preview`/`preview_seconds`)、SDカード内フォルダの再帰走査(`recursive`、
  フォルダを訪れる順序は`shuffle_folders`で曲順の`shuffle`とは独立にシャッフルできる)、
  スキャン開始フォルダの変更(`root_dir`。`recursive = yes`と組み合わせると「指定フォルダの
  中だけを再帰的に再生」できる)、ループ回数の変更(`loop_count`。既定2回、0で曲送りボタンが
  押されるまで無限ループ、1でループなし)、フラッシュ一時キャッシュ(`flash_cache`。既定no。
  yesにすると曲頭でこの基板自身のオンボードフラッシュへ曲データをコピーし、再生中はSDカードを
  アイドルにする -- 詳細な設計判断は[design-notes.md](design-notes.md)参照)、ステータス表示の
  切り替え(`display`。既定`oled`、`tft`でSPI接続のST7735に切り替え -- 1.1b参照)も設定できます。
  詳細は`src/master/src/player_config.h`のコメント、またはひな形`firmware/vgmplay.ini`の
  コメントを参照してください。
- テキストエディタで直接書けますが、GUI エディタもあります:
  `python3 tools/config_gui/vgmplay_config_gui.py`(Python 標準ライブラリのみ、
  [tools/config_gui/README.md](../tools/config_gui/README.md))。

### 1.3 SN76489の2台目 (Dual Chip Support、任意)

VGM仕様の["Dual Chip Support"](https://vgmrips.net/wiki/VGM_Specification#Dual_Chip_Support)に
対応しています。同じ曲の中で2個のSN76489を鳴らすVGMファイルは、1台目宛のコマンド`0x50 dd`とは
別に、2台目宛のコマンド`0x30 dd`(データ形式は`0x50`と同じ)を使います。

- **ハードウェアは1台目と全く同じ**です。もう1枚RP2040-Zeroを用意し、`slave_sn76489.uf2`を
  書き込んで(新規ビルド不要、1台目と同じイメージ)、CSだけマスターのGPIO27に配線してください
  (1台目はGPIO12)。SPI RX/SCK/PWM出力の配線は1台目と同じパターンです(2章参照)。
- ソフト側は`vgmplay.ini`に`[sn76489_2]`セクション(既定: `enabled = yes`, `cs = 27`)を追加すれば
  有効になります。2台目を組んでいない場合、この既定のままでも実害はありません(GPIO27に
  何も繋がっていないだけで、他のチップと同様に静かに無視されます)。組んだ場合のCSピン変更は
  他のチップと同じ`enabled`/`cs`/`gap`/`volume`キーで行えます。
- クロックはVGMヘッダのSN76489用フィールド(1個のみ)を2台とも共有するので、個別設定はありません。
- 曲がDual Chip Supportを宣言しているか(ヘッダのSN76489クロックのbit30)は自動判定され、
  OLEDの使用チップ表示にも「SN76489#2」として出ます。

## 2. スレーブ (RP2040-Zero) ピン割り当て

8種のスレーブファームウェアすべて同じピン配置です(スレーブ間でボードを使い回せます)。

| 機能 | GPIO | 備考 |
|---|---|---|
| SPI RX (マスターMOSIから) | GPIO8 | SPI1 RX |
| SPI CS (マスターから、個体ごとに配線) | GPIO9 | SPI1 CSn |
| SPI SCK (マスターから) | GPIO10 | SPI1 SCK |
| 音声出力 (PWM) | GPIO11 | 2段RC LPF経由でミキサーへ |
| デバッグログ TX | GPIO0 | UART0, 115200bps (任意、配線しなくても動作に支障なし) |
| デバッグログ RX | GPIO1 | 同上 (スレーブも受信は使わないので配線任意) |

RP2040-Zeroはピンヘッダに出ているのが GPIO0〜15 と GPIO26〜29 だけなので(GPIO16はオンボード
WS2812、17〜25/23〜25近辺は非公開)、スレーブのSPIは実機で配線できる GPIO8/9/10 (SPI1 グループ)
に割り当てています。GPIO0/1 はUARTログ、GPIO11 (SPI1 TX相当、このスレーブでは未使用) はPWM音声出力で、いずれもヘッダに出ています。
`gpio_set_function(pin, GPIO_FUNC_SPI)` は各ピン固有のSPI機能を選ぶため、GPIO8→SPI1 RX、
GPIO9→SPI1 CSn、GPIO10→SPI1 SCK となり、`slave_spi_rx_run()` には spi_index=1 を渡します
(`src/slave_*/src/main.c`)。マスター側(Raspberry Pi Pico、全ピン利用可)の配線は変更不要で、
変わるのはマスター⇔各スレーブ間の結線のスレーブ端だけです。ログの見方は
[design-notes.md §8.2](design-notes.md#82-スレーブ-rp2040-zero--pico)参照。

## 4. Sega PCMスレーブについて (ROMアップロード)

Sega PCMは実機ではマスクROMにサンプルを持つ設計のため、他の7スレーブと違い曲の再生前に
サンプルデータをSPI経由でアップロードする必要があります。

- スレーブ側に約192KBの固定バッファを確保(1曲分のサンプルとしては十分すぎる程度。vgmrips.netの
  実例調査ではOut Run/Space Harrier/After Burner IIなどで1曲あたり20〜130KB程度)
- 曲の頭でVGMの`0x67`データブロック(type=0x80)を検出すると、マスターがそのブロック先頭8バイトの
  ヘッダ(全ROMサイズ+ROM内開始アドレス)を読み取り、`VGMSPI_OP_PCM_UPLOAD_RESET`で開始アドレスの
  256バイト境界へシーク→端数(`start & 0xFF`)を0x80(無音)で埋めてバイト単位に合わせてから、
  実データを1バイトずつSPIフレームで転送(`VGMSPI_OP_PCM_UPLOAD_BYTE`)。1曲のROMが複数ブロックに
  分かれていてもそれぞれ正しいアドレスに配置されます(密に詰めたripは開始アドレスが256の倍数で
  ないことがあり、以前はこのズレが連続ノイズになっていた)。1フレームごとにCSをパルスする方式(design-notes.md §2参照)のため1バイトあたり
  約65µsかかり、**曲の頭に数秒〜(192KBフルの場合)最大12〜13秒程度のロード時間**が発生します
  (実機のROM読み込みに近い体験として許容)
- **ROMウィンドウのリベース**: マスターは再生前に曲の全`0x67` type-0x80ブロックを事前スキャンし、
  最小開始アドレスを64KB単位に切り下げた値を`VGMSPI_OP_SEGAPCM_ROM_BASE`でスレーブへ通知。
  スレーブは以降すべてのサンプルアドレスからこのベースを引いてバッファに収めます。これにより、
  512KB級ROM(OutRun等)でサンプルがROM空間の上位(例:Magical Sound Showerは0x40000〜0x56000)に
  あっても、**曲が実際に使う範囲が192KB未満なら鳴ります**。ベースを引いてなお192KBを超える分、
  および範囲外アドレスは静かに切り捨て(クラッシュはしない)
- 曲頭でVGMヘッダ0x3C(Sega PCMインターフェースレジスタ)からバンク設定をデコードして
  `VGMSPI_OP_SEGAPCM_BANK`でスレーブへ転送。各chのCTRLレジスタ上位ビットのバンク番号で
  絶対ROMアドレスを再生します(上記リベース後の192KBウィンドウに収まる範囲まで。超過分は無音)
- アップロードに数秒かかるため、マスターは転送完了後に再生タイミングの基準時刻をリセットします
  (これをしないと曲が途中から始まったように聞こえる)
- 詳細は[design-notes.md](design-notes.md)参照

## 5. スレーブ1台分の音声出力段 (PWM → RCフィルタ)

PWMキャリアは sysclk/1024 ≈ 122kHz (10bit分解能)。2段RCで確実にキャリアを除去します。

```
GPIO11 (PWM, 0-3.3V) --[R 1kΩ]--+--[R 1kΩ]--+---> ミキサーの入力抵抗へ
                                |           |
                              [C 10nF]    [C 10nF]
                                |           |
                               GND         GND
```

fc ≈ 1/(2π×1k×10n) ≈ 16kHz。可聴帯域上限に近いですが -40dB/decade (2段)で122kHzキャリアは十分減衰します。
もう少しキャリア除去を優先したい場合は R=2.2kΩ, C=10nF (fc≈7.2kHz) に変更してください。

### 5.1 手持ちのコンデンサでの代替値 (τ=RC を保てば同じ特性)

R・Cの個々の値ではなく **積 τ=RC** がフィルタの特性(fc、ひいてはキャリアの減衰量)を決めます。
10nF(または2.2kΩ+10nFの代替値)がちょうど手元にない場合、下表のように**Rを反比例させて
組み合わせれば同じτ**を再現できます(2段とも同じR・Cを使う前提)。逆に、Rはそのままでコンデンサだけ
容量の異なる品に差し替えると fc が想定より大きくズレてキャリアが減衰しきらないので避けてください。

**グループA: 元設計相当 (τ≈10µs, fc≈16kHz)**

| 手持ちのC | 組み合わせるR | 実際のτ | 実際のfc |
|---|---|---|---|
| 10nF (元の指定値) | 1kΩ | 10.0µs | 15.9kHz |
| 22nF (0.022µF) | 470Ω | 10.3µs | 15.4kHz |
| 15nF | 680Ω | 10.2µs | 15.6kHz |
| 3.3nF | 3.3kΩ | 10.9µs | 14.6kHz |
| 1.5nF | 6.8kΩ | 10.2µs | 15.6kHz |

**グループB: キャリア除去優先 (τ≈22µs, fc≈7.2kHz) — ノイズが強く出る場合はこちらを推奨**

| 手持ちのC | 組み合わせるR | 実際のτ | 実際のfc |
|---|---|---|---|
| 10nF | 2.2kΩ (元の代替値) | 22.0µs | 7.23kHz |
| 22nF (0.022µF) | **1kΩ (追加購入不要)** | 22.0µs | 7.23kHz |
| 15nF | 1.5kΩ | 22.5µs | 7.08kHz |
| 3.3nF | 6.8kΩ | 22.4µs | 7.09kHz |
| 1.5nF | 15kΩ | 22.5µs | 7.08kHz |

**ミキサーへの負荷(音量低下)の目安**: フィルタ2段目のRが後段のミキサー入力抵抗`Rin`と
比較して大きいほど、電圧分割で信号自体も減衰します(`減衰[dB] = 20×log10(Rin/(R+Rin))`)。
オペアンプ加算(§6, Rin=10kΩ)なら概ね軽微、1〜2台向けの簡易抵抗混合(Rin=2.2kΩ)は
Rが大きい組み合わせほど目立ちます。

| R | オペアンプ Rin=10kΩ との組 | 簡易抵抗混合 Rin=2.2kΩ との組 |
|---|---|---|
| 470Ω | -0.4dB | -1.7dB |
| 680Ω | -0.6dB | -2.3dB |
| 1kΩ | -0.8dB | -3.3dB |
| 1.5kΩ | -1.2dB | -4.5dB |
| 2.2kΩ | -1.7dB | -6.0dB |
| 3.3kΩ | -2.5dB | -8.0dB |
| 6.8kΩ | -4.5dB | -12.2dB |
| 15kΩ | -8.0dB | -17.9dB |

**自分で計算する場合**: 目標のτ(10µsまたは22µs)を手持ちのCで割ればRが求まります
(`R = τ / C`)。計算結果に一番近い標準抵抗値(E12系列: …,470,560,680,820,1k,1.2k,1.5k,1.8k,2.2k,
2.7k,3.3k,3.9k,4.7k,5.6k,6.8k,8.2k,10k,…)を選べば十分です(数%のズレは実用上問題になりません)。

## 6. アナログ加算ミキサー (オペアンプ反転加算回路)

4スレーブ分をレールtoレール単電源オペアンプ1〜2個で加算し、DC成分をカップリングコンデンサで除去します。

```
                              Rf 10k
                        +----/\/\/\----+
                        |              |
 slave0 --[Cin 1µF]--[Rin 10k]--+      |
 slave1 --[Cin 1µF]--[Rin 10k]--+      |
 slave2 --[Cin 1µF]--[Rin 10k]--+--(-)\|
 slave3 --[Cin 1µF]--[Rin 10k]--+      >----+---> ミキサー出力 (Vref中心で振れる)
                                   (+)/
                                    |
                          Vref(=VCC/2): 10k+10k分圧 + 10µF以上でデカップリング
```

- 各スレーブのRC出力(5章)を **カップリングコンデンサ `Cin`(1µF程度)** → `Rin=10kΩ` 経由でオペアンプの
  反転入力ノードに接続。`Cin` を入れて交流だけ加算することで、各スレーブのRC出力DC中心(それぞれの
  VCC/2 ≈ 1.65V)と `Vref` の不一致による出力オフセットを防ぐ。`Cin`+`Rin` は fc ≈ 16Hz のHPFになる
- 帰還抵抗 `Rf=10kΩ` (Rin=Rfなら1入力あたりゲイン1倍。振り切れるようなら `Rf` を 6.8kΩ 等に下げる)
- **チップごとの音量差は、そのチップの `Rin` だけ変えて補正する**(各入力ゲインは `Rf/Rin` で独立。
  例: 小さく聞こえるチップの `Rin` を 10kΩ→5.6kΩ で約 +5dB)。ソースやファーム側のスケーリングは触らない
- 非反転入力には `VCC/2` の基準電圧 (抵抗分圧+デカップリングコンデンサ) を与え、単電源オペアンプでも
  ミキサー出力がレール中央に来るようにする
- **オペアンプは単電源(3.3V/5V)ならレールtoレール品を使う** (MCP6002 / TLV9002 / LMV358 等)。TL072 は
  本来両電源向けで、単電源だと出力がレール近くまで振れず入力同相範囲も狭い。TL072 を使うなら ±5〜±9V の
  両電源にし、その場合 `Vref` 回路は不要で非反転入力はGND直結
- 電源ピン直近に 0.1µF のパスコンを入れる
- ミキサー出力はDCブロック用コンデンサ (例: 1µF) を介してボリューム(10kΩ Aカーブ)→ヘッドホンアンプ
  (例: PAM8403 などの小型D級アンプIC) またはヘッドホンジャックへ

スレーブが1〜2台だけの構成なら、オペアンプなしで単純な抵抗混合(各出力からRin=2.2kΩ程度で1点に
まとめ、その先にDCブロックコンデンサのみ)でも実用上問題ない音量が得られます。3台以上は、出力どうしが
互いに負荷になってクロストークとレベル低下(概ね 1/N)が出るため、上記のオペアンプ加算を推奨。

## 7. 電源

- 各RP2040-Zeroはボード上のレギュレータでUSB 5V→3.3Vを生成するため、共有5Vバス(USBハブ経由、または
  5V電源+分配)から給電すれば個別レギュレータは不要
- マスターのPicoも同じ5Vバスから給電可(VBUSピン経由)。GND共通化を忘れないこと
- オペアンプ段は単電源(3.3V or 5V)＋レールtoレール品(MCP6002等)で動作させ、上記の`VCC/2`基準電圧回路で
  対応。両電源(±5〜±9V)にする場合は`VCC/2`回路不要で非反転入力はGND直結、TL072等も使用可
